<h2 id="cors란">CORS란?<a class="anchor after" aria-hidden="true" tabindex="-1" href="#cors란"><span class="anchor-icon">#</span></a></h2>
<p><img src="/assets/img/posts/browser/access-control-allow-origin.png" alt="access-control-allow-origin" loading="lazy" decoding="async" width="1444" height="116" srcset="/assets/img/posts/browser/nextImageExportOptimizer/access-control-allow-origin-opt-640.WEBP 640w, /assets/img/posts/browser/nextImageExportOptimizer/access-control-allow-origin-opt-1080.WEBP 1080w, /assets/img/posts/browser/nextImageExportOptimizer/access-control-allow-origin-opt-1920.WEBP 1920w" sizes="(max-width: 640px) 100vw, 1000px"></p>
<p>위의 그림의 <code>CORS policy</code> 오류 메시지는 CORS 정책을 위반할 때 발생하게 됩니다. CORS는 Cross-Origin Resource Sharing의 약자입니다. 교차 출처 리소스 공유로 번역될 수 있는데, 브라우저에서 다른 출처의 리소스를 공유하는 방법입니다.</p>
<h3 id="url-구조">URL 구조<a class="anchor after" aria-hidden="true" tabindex="-1" href="#url-구조"><span class="anchor-icon">#</span></a></h3>
<p>다른 출처의 출처가 무엇인지 살펴봐야 하는데, 출처가 무엇인지 알기 위해서 먼저 URL의 구조를 살펴보아야 합니다. URL 구조는 아래 그림과 같습니다.</p>
<p><img src="/assets/img/posts/browser/url.png" alt="URL 구조" loading="lazy" decoding="async" width="952" height="204" srcset="/assets/img/posts/browser/nextImageExportOptimizer/url-opt-640.WEBP 640w, /assets/img/posts/browser/nextImageExportOptimizer/url-opt-1080.WEBP 1080w" sizes="(max-width: 640px) 100vw, 1000px"></p>
<p>프로토콜의 HTTP는 80번, HTTPS는 443번 포트를 사용하는데, 80번과 443번 포트는 생략이 가능합니다.</p>
<h3 id="출처origin란">출처(Origin)란?<a class="anchor after" aria-hidden="true" tabindex="-1" href="#출처origin란"><span class="anchor-icon">#</span></a></h3>
<p>출처(Origin)란 URL 구조에서 살펴본 Protocal, Host, Port를 합친 것을 말합니다. 브라우저 개발자 도구의 콘솔 창에 <code>location.origin</code>를 실행하면 출처를 확인할 수 있습니다.</p>
<p><img src="/assets/img/posts/browser/location_origin.png" alt="location.origin" loading="lazy" decoding="async" width="400" height="80" srcset="/assets/img/posts/browser/nextImageExportOptimizer/location_origin-opt-640.WEBP 640w" sizes="(max-width: 640px) 100vw, 1000px"></p>
<h3 id="같은-출처-vs-다른-출처">같은 출처 VS 다른 출처<a class="anchor after" aria-hidden="true" tabindex="-1" href="#같은-출처-vs-다른-출처"><span class="anchor-icon">#</span></a></h3>
<p>같은 출처인지 다른 출처인지 이해를 돕기 위해 예제를 하나 살펴보도록 하겠습니다. 현재 웹페이지의 주소가 <code>https://beomy.github.io/tech/</code>일 때 같은 출처인지 다른 출처인지 아래 테이블과 같은 결과를 얻을 수 있습니다.</p>

<h2 id="동일-출처-정책same-origin-policy이란">동일 출처 정책(Same-Origin Policy)이란?<a class="anchor after" aria-hidden="true" tabindex="-1" href="#동일-출처-정책same-origin-policy이란"><span class="anchor-icon">#</span></a></h2>
<p><a href="https://www.postman.com/">Postman</a>으로 API를 테스트하거나, 다른 서버에서 API를 호출할 때는 멀쩡히 잘 동작하다가 브라우저에서 API를 호출할 때만 <code>CORS policy</code> 오류가 발생해서 당혹스러울 때가 있으셨을 수도 있습니다. 그 이유는 브라우저가 동일 출처 정책(Same-Origin Policy, SOP)를 지켜서 다른 출처의 리소스 접근을 금지하기 때문입니다. 하지만 실제로 웹페이지는 상당히 자주 다른 출처의 리소스를 사용해야 합니다. 예를 들어 <code>beomy.github.io</code>라는 도메인 주소를 사용하는 웹페이지에서 <code>beomy-api.github.io</code>라는 API 서버로 데이터를 요청해서 화면을 그린다면 이 웹페이지는 동일 출처 정책을 위반한 것이 됩니다.</p>
<h3 id="동일-출처-정책의-장점">동일 출처 정책의 장점<a class="anchor after" aria-hidden="true" tabindex="-1" href="#동일-출처-정책의-장점"><span class="anchor-icon">#</span></a></h3>
<p>동일 출처 정책을 지키면 외부 리소스를 가져오지 못해 불편하지만, 동일 출처 정책은 <a href="https://ko.wikipedia.org/wiki/%EC%82%AC%EC%9D%B4%ED%8A%B8_%EA%B0%84_%EC%8A%A4%ED%81%AC%EB%A6%BD%ED%8C%85">XSS</a>나 <a href="https://ko.wikipedia.org/wiki/%EC%82%AC%EC%9D%B4%ED%8A%B8_%EA%B0%84_%EC%9A%94%EC%B2%AD_%EC%9C%84%EC%A1%B0">XSRF</a> 등의 보안 취약점을 노린 공격을 방어할 수 있습니다. 하지만 현실적으로는 외부 리소스를 참고하는 것은 필요하기 때문에 외부 리소스를 가져올 수 있는 방법이 존재해야 합니다. 외부 리소스를 사용하기 위한 SOP의 예외 조항이 CORS입니다.</p>
<h2 id="cors-동작원리">CORS 동작원리<a class="anchor after" aria-hidden="true" tabindex="-1" href="#cors-동작원리"><span class="anchor-icon">#</span></a></h2>
<p>CORS의 동작 방식은 단순 요청 방법과 예비 요청을 먼저 보내는 방법 2가지 방법이 있습니다.</p>
<h3 id="simple-request">Simple request<a class="anchor after" aria-hidden="true" tabindex="-1" href="#simple-request"><span class="anchor-icon">#</span></a></h3>
<p>단순 요청 방법은 서버에게 바로 요청을 보내는 방법입니다. 아래 그림은 자바스크립트에서 API를 요청할 때 브라우저와 서버의 동작을 나타내는 그림입니다.</p>
<p><img src="/assets/img/posts/browser/cors_simle_request.png" alt="단순 요청" loading="lazy" decoding="async" width="1239" height="558" srcset="/assets/img/posts/browser/nextImageExportOptimizer/cors_simle_request-opt-640.WEBP 640w, /assets/img/posts/browser/nextImageExportOptimizer/cors_simle_request-opt-1080.WEBP 1080w, /assets/img/posts/browser/nextImageExportOptimizer/cors_simle_request-opt-1920.WEBP 1920w" sizes="(max-width: 640px) 100vw, 1000px"></p>
<p>단순 요청은 서버에 API를 요청하고, 서버는 <code>Access-Control-Allow-Origin</code> 헤더를 포함한 응답을 브라우저에 보냅니다. 브라우저는 <code>Access-Control-Allow-Origin</code> 헤더를 확인해서 CORS 동작을 수행할지 판단합니다.</p>
<h4 id="simple-request-조건">Simple request 조건<a class="anchor after" aria-hidden="true" tabindex="-1" href="#simple-request-조건"><span class="anchor-icon">#</span></a></h4>
<p>서버로 전달하는 요청(request)이 아래의 3가지 조건을 만족해야 서버로 전달하는 요청이 단순 요청으로 동작합니다.</p>
<ul>
<li>요청 메서드(method)는 GET, HEAD, POST 중 하나여야 합니다.</li>
<li>Accept, Accept-Language, Content-Language, Content-Type, DPR, Downlink, Save-Data, Viewport-Width, Width를 제외한 헤더를 사용하면 안 됩니다.</li>
<li>Content-Type 헤더는 application/x-www-form-urlencoded, multipart/form-data, text/plain 중 하나를 사용해야 합니다.</li>
</ul>
<p>첫 번째 조건은 어렵지 않은 조건이지만 2번, 3번 조건은 까다로운 조건입니다. 2번 조건은 사용자 인증에 사용되는 <code>Authorization</code> 헤더도 포함되지 않아 까다로운 조건이며, 3번 조건은 많은 REST API들이 <code>Content-Type</code>으로 <code>application/json</code>을 사용하기 때문에 지켜지기 어려운 조건입니다.</p>
<h3 id="preflight-request">Preflight request<a class="anchor after" aria-hidden="true" tabindex="-1" href="#preflight-request"><span class="anchor-icon">#</span></a></h3>
<p>Preflight 요청은 서버에 예비 요청을 보내서 안전한지 판단한 후 본 요청을 보내는 방법입니다. 아래 그림은 Preflight 요청 동작을 나타내는 그립입니다.</p>
<p><img src="/assets/img/posts/browser/cors_preflight_request.png" alt="Preflight request 요청" loading="lazy" decoding="async" width="1187" height="612" srcset="/assets/img/posts/browser/nextImageExportOptimizer/cors_preflight_request-opt-640.WEBP 640w, /assets/img/posts/browser/nextImageExportOptimizer/cors_preflight_request-opt-1080.WEBP 1080w, /assets/img/posts/browser/nextImageExportOptimizer/cors_preflight_request-opt-1920.WEBP 1920w" sizes="(max-width: 640px) 100vw, 1000px"></p>
<p><code>GET</code>, <code>POST</code>, <code>PUT</code>, <code>DELETE</code> 등의 메서드로 API를 요청했는데, 크롬 개발자 도구의 네트워크 탭에 <code>OPTIONS</code> 메서드로 요청이 보내지는 것을 보신 적 있으시다면 CORS를 경험하셨던 것입니다. Preflight 요청은 실제 리소스를 요청하기 전에 <code>OPTIONS</code>라는 메서드를 통해 실제 요청을 전송할지 판단합니다.</p>
<p><code>OPTIONS</code> 메서드로 서버에 예비 요청을 먼저 보내고, 서버는 이 예비 요청에 대한 응답으로 <code>Access-Control-Allow-Origin</code> 헤더를 포함한 응답을 브라우저에 보냅니다. 브라우저는 단순 요청과 동일하게 <code>Access-Control-Allow-Origin</code> 헤더를 확인해서 CORS 동작을 수행할지 판단합니다.</p>
<h2 id="cors-에러-해결-방법">CORS 에러 해결 방법<a class="anchor after" aria-hidden="true" tabindex="-1" href="#cors-에러-해결-방법"><span class="anchor-icon">#</span></a></h2>
<p>앞에서 이야기 한 CORS 동작 원리를 보면, 서버에서 <code>Access-Control-Allow-Origin</code> 헤더를 포함한 응답을 브라우저에 보내는 방식으로 CORS 에러를 해결할 수 있습니다. 프론트엔드 개발자가 CORS 에러를 확인했다면, 서버에 <code>Access-Control-Allow-Origin</code> 등 CORS를 해결하기 위한 몇 가지 응답 헤더를 포함해 달라고 요청해야 합니다.</p>
<p>Node.js의 Express는 <code>cors</code>라는 서드 파트 미들웨어를 지원합니다. 이 라이브러리에서 CORS 응답 헤더를 추가해 주기 때문에, 개발자가 별도의 CORS 응답 헤더를 추가해 주지 않아도 됩니다. 다른 프레임워크에서도 CORS를 해결해 주는 라이브러리가 존재합니다.</p>
<h3 id="http-응답-헤더">HTTP 응답 헤더<a class="anchor after" aria-hidden="true" tabindex="-1" href="#http-응답-헤더"><span class="anchor-icon">#</span></a></h3>
<p>라이브러리를 사용하면 간단하게 CORS를 해결할 수 있지만, CORS를 해결하기 위한 응답 헤더가 무엇이 있는지 하나씩 살펴보도록 하겠습니다.</p>
<h4 id="access-control-allow-origin-origin--">Access-Control-Allow-Origin: &#x3C;origin> | *<a class="anchor after" aria-hidden="true" tabindex="-1" href="#access-control-allow-origin-origin--"><span class="anchor-icon">#</span></a></h4>
<p><code>Access-Control-Allow-Origin</code> 헤더에 작성된 출처만 브라우저가 리소스를 접근할 수 있도록 허용합니다.</p>
<h5 id="사용-방법">사용 방법<a class="anchor after" aria-hidden="true" tabindex="-1" href="#사용-방법"><span class="anchor-icon">#</span></a></h5>
<p>아래와 같이 응답 헤더가 작성되었다면 <code>https://beomy.github.io</code> 페이지에서 브라우저는 서버 응답으로 온 리소스를 접근할 수 있습니다.</p>
<pre><code>Access-Control-Allow-Origin: https://beomy.github.io
</code></pre>
<p>아래와 같이 <code>*</code>(와일드 카드)가 작성되었다면, 브라우저는 출처에 상관없이 모든 리소스에 접근할 수 있습니다.</p>
<pre><code>Access-Control-Allow-Origin: *
</code></pre>

<h4 id="access-control-allow-methods-method-method">Access-Control-Allow-Methods: &#x3C;method>[, &#x3C;method>]*<a class="anchor after" aria-hidden="true" tabindex="-1" href="#access-control-allow-methods-method-method"><span class="anchor-icon">#</span></a></h4>
<p>브라우저에서 보내는 요청 헤더에 포함된 <code>Access-Control-Request-Method</code> 헤더에 대한 응답 결과입니다. 리소스 접근을 허용하는 HTTP 메서드를 지정해 주는 헤더입니다.</p>
<h5 id="사용-방법-1">사용 방법<a class="anchor after" aria-hidden="true" tabindex="-1" href="#사용-방법-1"><span class="anchor-icon">#</span></a></h5>

<pre><code>Access-Control-Allow-Methods: GET, PUT
</code></pre>

<p><code>Access-Control-Allow-Origin</code>는 <code>*</code>로 모든 출처를 허용한 상태이고, 브라우저의 요청 헤더에 포함된 <code>Access-Control-Request-Method</code> 헤더 값을 그대로 <code>Access-Control-Allow-Methods</code> 헤더에 추가해 주었습니다. <code>Access-Control-Request-Method</code> 헤더는 HTTP 요청 헤더에서 설명하도록 하겠습니다.</p>
<h4 id="access-control-expose-headers-header-name-header-name">Access-Control-Expose-Headers: &#x3C;header-name>[, &#x3C;header-name>]*<a class="anchor after" aria-hidden="true" tabindex="-1" href="#access-control-expose-headers-header-name-header-name"><span class="anchor-icon">#</span></a></h4>
<p>서버에서 응답 헤더에 <code>Access-Control-Expose-Headers</code>를 추가해 줘야 브라우저의 자바스크립트에서 헤더에 접근할 수 있습니다.</p>
<h5 id="사용-방법-2">사용 방법<a class="anchor after" aria-hidden="true" tabindex="-1" href="#사용-방법-2"><span class="anchor-icon">#</span></a></h5>
<p>아래와 같이 <code>,</code>로 구분하여 여러 개의 헤더를 넣을 수 있습니다.</p>
<pre><code>Access-Control-Expose-Headers: X-My-Custom-Header, X-Another-Custom-Header
</code></pre>

<h4 id="access-control-allow-headers-header-name-header-name">Access-Control-Allow-Headers: &#x3C;header-name>[, &#x3C;header-name>]*<a class="anchor after" aria-hidden="true" tabindex="-1" href="#access-control-allow-headers-header-name-header-name"><span class="anchor-icon">#</span></a></h4>
<p>브라우저에서 보내는 요청 헤더에 포함된 <code>Access-Control-Request-Headers</code> 헤더에 대한 응답 결과입니다.</p>
<h5 id="사용-방법-3">사용 방법<a class="anchor after" aria-hidden="true" tabindex="-1" href="#사용-방법-3"><span class="anchor-icon">#</span></a></h5>
<p>자바스크립트에서 커스텀 헤더를 서버에 전달하게 되면, <code>OPTIONS</code> 요청 헤더의 <code>Access-Control-Request-Headers</code> 헤더에 커스텀 헤더 이름이 추가됩니다. 서버에서는 <code>Access-Control-Request-Headers</code>에 작성된 값을 보고 <code>Access-Control-Allow-Headers</code> 응답 헤더에 커스텀 헤더 이름을 명시해 주어야 합니다.</p>
<pre><code>Access-Control-Allow-Headers: X-Custom-Request
</code></pre>

<h4 id="access-control-max-age-delta-seconds">Access-Control-Max-Age: &#x3C;delta-seconds><a class="anchor after" aria-hidden="true" tabindex="-1" href="#access-control-max-age-delta-seconds"><span class="anchor-icon">#</span></a></h4>
<p>preflight 요청 결과를 캐시 할 수 있는 시간을 나타냅니다.</p>
<h5 id="사용-방법-4">사용 방법<a class="anchor after" aria-hidden="true" tabindex="-1" href="#사용-방법-4"><span class="anchor-icon">#</span></a></h5>
<p>아래와 같이 초 단위로 캐시 시간을 설정합니다.</p>
<pre><code>Access-Control-Max-Age: 60
</code></pre>
<p>위의 코드는 60초 동안 preflight 요청을 캐시 하는 코드입니다. 60초 동안 <code>OPTIONS</code> 메서드를 사용하는 예비 요청을 보내지 않습니다.</p>

<h3 id="http-요청-헤더">HTTP 요청 헤더<a class="anchor after" aria-hidden="true" tabindex="-1" href="#http-요청-헤더"><span class="anchor-icon">#</span></a></h3>
<p>CORS를 위해서, 브라우저에서 서버로 요청하는 헤더를 살펴보도록 하겠습니다. 요청 헤더들은 별도로 명시해 주지 않아도 브라우저에서 <code>OPTIONS</code> 요청에 추가합니다.</p>
<h4 id="origin-origin">Origin: &#x3C;origin><a class="anchor after" aria-hidden="true" tabindex="-1" href="#origin-origin"><span class="anchor-icon">#</span></a></h4>
<p><code>Origin</code> 헤더는 요청하는 대상의 출처를 나타냅니다. API를 호출하는 페이지의 출처 값이 저장됩니다.</p>
<h4 id="access-control-request-method-method">Access-Control-Request-Method: &#x3C;method><a class="anchor after" aria-hidden="true" tabindex="-1" href="#access-control-request-method-method"><span class="anchor-icon">#</span></a></h4>
<p><code>Access-Control-Request-Method</code> 헤더는 실제 요청이 어떤 HTTP 메서드를 사용하는지 서버에 알려주기 위해 사용됩니다.</p>
<h4 id="access-control-request-headers-field-name-field-name">Access-Control-Request-Headers: &#x3C;field-name>[, &#x3C;field-name>]<a class="anchor after" aria-hidden="true" tabindex="-1" href="#access-control-request-headers-field-name-field-name"><span class="anchor-icon">#</span></a></h4>
<p><code>Access-Control-Request-Headers</code> 헤더는 브라우저에서 보내는 커스텀 헤더 이름을 서버에 알려주기 위해 사용됩니다.</p>
<h2 id="기타-해결-방법">기타 해결 방법<a class="anchor after" aria-hidden="true" tabindex="-1" href="#기타-해결-방법"><span class="anchor-icon">#</span></a></h2>
<p>서버에서 응답 헤더들을 추가하는 방법 이외의 CORS를 우회하는 방법을 이야기해보도록 하겠습니다.</p>
<h3 id="jsonp">JSONP<a class="anchor after" aria-hidden="true" tabindex="-1" href="#jsonp"><span class="anchor-icon">#</span></a></h3>
<p>JSONP(JSON with Padding)는 <code>&#x3C;script></code> 요소가 외부 출처 리소스를 가져올 수 있는 특징을 사용하는 방법입니다. 아래 코드와 같은 방법으로 사용할 수 있습니다.</p>

<h3 id="프록시-서버">프록시 서버<a class="anchor after" aria-hidden="true" tabindex="-1" href="#프록시-서버"><span class="anchor-icon">#</span></a></h3>
<p>프론트엔드와 백엔드 사이에 프록시 서버를 두는 방법으로 CORS를 해결할 수도 있습니다. 개발 환경에서 CORS를 해결해야 한다면, Webpack Dev Server 등의 라이브러리를 사용해서 프록시 설정을 하는 방법도 있습니다.</p>
<h2 id="부록">부록<a class="anchor after" aria-hidden="true" tabindex="-1" href="#부록"><span class="anchor-icon">#</span></a></h2>
<h3 id="requestcredentials">Request.credentials<a class="anchor after" aria-hidden="true" tabindex="-1" href="#requestcredentials"><span class="anchor-icon">#</span></a></h3>
<p><code>fetch</code> 메서드의 <code>credentials</code> 옵션은 <code>Access-Control-Allow-Credentials</code> 헤더와 연관된 옵션입니다. <code>credentials</code> 옵션은 아래와 같이 3개의 값을 가질 수 있습니다.</p>





















<table><thead><tr><th>옵션 값</th><th>설명</th></tr></thead><tbody><tr><td>same-origin (기본값)</td><td>같은 출처 간 요청에만 인증 정보를 전달함</td></tr><tr><td>include</td><td>모든 요청에 인증 정보를 전달함</td></tr><tr><td>omit</td><td>인증 정보를 전달하지 않음</td></tr></tbody></table>
<p><code>same-origin</code>은 기본 값으로, 같은 출처 간에 쿠키 등의 인증 정보 전달이 가능합니다. <code>include</code>는 출처에 상관없이 모든 요청에 쿠키 등의 인증 정보를 전달할 수 있습니다. <code>omit</code>은 쿠키 등의 인증 정보를 전달하지 않습니다.</p>
<p>아래와 같은 자바스크립트 코드를 출처가 <code>localhost:5000</code>인 페이지에서 실행할 경우,</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="js"><code><span class="line"><span style="color:#622CBC;--shiki-dark:#DBB7FF">fetch</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">(</span><span style="color:#032563;--shiki-dark:#ADDCFF">'http://localhost:3001/cors'</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">, {</span></span>

<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">  credentials: </span><span style="color:#032563;--shiki-dark:#ADDCFF">'include'</span></span>

<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">})</span></span></code></pre>

<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="js"><code><span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">router.</span><span style="color:#622CBC;--shiki-dark:#DBB7FF">options</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">(</span><span style="color:#032563;--shiki-dark:#ADDCFF">'/cors'</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">, (</span><span style="color:#702C00;--shiki-dark:#FFB757">req</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">, </span><span style="color:#702C00;--shiki-dark:#FFB757">res</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">, </span><span style="color:#702C00;--shiki-dark:#FFB757">next</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">) </span><span style="color:#A0111F;--shiki-dark:#FF9492">=></span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> {</span></span>
