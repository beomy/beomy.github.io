15:Tab87,<p>HTTP, HyperText Transfer Protocol은 인터넷에서 하이퍼텍스트(HyperText)를 전송(Transfer)하기 위한 통신 규약(Protocol)입니다. 이번 포스트에서 HTTP가 무엇인지 살펴보도록 하겠습니다.</p>
<p>이번 포스트는 HTTP/1.* 버전을 기준으로 작성되었습니다. HTTP/2, HTTP/3에 대한 포스팅은 <a href="/tech/etc/http-version/">[ETC] HTTP 버전</a>에서 확인할 수 있습니다.</p>
<h2 id="http란">HTTP란<a class="anchor after" aria-hidden="true" tabindex="-1" href="#http란"><span class="anchor-icon">#</span></a></h2>
<p>HTTP는 W3(World Wide Web)에서 정보를 주고 받을 수 있는 프로토콜로, 클라이언트와 서버 사이에 이루어지는 요청/응답(request/response) 프로토콜입니다. 예를 들어 웹 브라우저가 HTTP를 통해 서버로부터 웹 페이지(HTML)나 이미지를 요청하면 서버는 이 요청에 응답하여 필요한 정보를 전달합니다.</p>
<h2 id="http-특징">HTTP 특징<a class="anchor after" aria-hidden="true" tabindex="-1" href="#http-특징"><span class="anchor-icon">#</span></a></h2>
<p>HTTP는 아래와 같이 간단함, 확장성, 무상태, 비연결성 4가지 특징을 가집니다.</p>
<ul>
<li><strong>간단함</strong>: HTTP의 요청/응답 메시지 구조를 보면 알 수 있듯이 사람이 읽을 수 있도록 만들어진 프로토콜입니다.</li>
<li><strong>확장성</strong>: HTTP/1.0에 도입된 HTTP 헤더를 사용하면 프로토콜을 쉽게 확장할 수 있습니다. 새로운 기능을 위한 새로운 헤더에 대해 클라이언트와 서버가 서로 합의가 이루어진다면 도입할 수 있는 확장성을 가집니다.</li>
<li><strong>무상태</strong>: HTTP는 통신 상태나 이전 호출 결과 등을 저장하지 않습니다. 상태 저장이 필요한 경우 쿠키나 세션 등을 사용해야 합니다.</li>
<li><strong>비연결성</strong>: HTTP는 클라이언트와 서버가 연결을 맺은 후 클라이언트의 요청에 서버가 응답을 마치면 연결이 끊어지게 됩니다. 이런 특징은 연결을 계속 유지할 때 필요한 자원을 줄일 수 있지만 매 요청 마다 연결을 맺어야 하는 오버헤드가 발생하게 됩니다. HTTP 버전이 올라가면서 이런 오버헤드는 최적화 되었습니다.</li>
</ul>
<h2 id="http-요청-메시지">HTTP 요청 메시지<a class="anchor after" aria-hidden="true" tabindex="-1" href="#http-요청-메시지"><span class="anchor-icon">#</span></a></h2>
<p>클라이언트가 서버에게 보내는 요청 메시지의 구조와 요청 메서드, 요청 헤더에 대해 살펴보겠습니다.</p>
<h3 id="요청-메시지-구조">요청 메시지 구조<a class="anchor after" aria-hidden="true" tabindex="-1" href="#요청-메시지-구조"><span class="anchor-icon">#</span></a></h3>

<p>각 줄의 끝은 <code>&#x3C;CR>&#x3C;LF></code>로 끝나야 합니다. 캐리지 리턴(Carriage Return)과 라인 피드(Line Feed) 외에 다른 화이트 스페이스가 포함되면 안됩니다.</p>
<blockquote>
<p><strong>캐리지 리턴(Carriage Return)과 라인 피드(Line Feed)</strong></p>
<p>캐리지 리턴과 라인 피드는 타자기에서 사용하는 용어로, 캐리지 리턴(줄여서 CR)은 현재 위치를 나타내는 커서를 맨 앞으로 이동시킨다 라는 뜻입니다. 라인 피드(줄여서 LF)는 커서의 위치를 아랫줄로 이동시킨다는 뜻입니다.</p>
<p>타자기에서 다음 줄로 이동 할 때, 타자기의 커서를 맨 앞으로 이동한 후 종이를 위로 올려줘야 합니다. 즉 CR 후 LF를 해야 다음 줄로 이동하게 됩니다. 타자기와 동일하게 PC에서도 CR + LF 이 두 동작을 합쳐서 Enter 동작을 하게 됩니다.</p>
</blockquote>
<p>메시지 본문이 있는 POST 요청 메시지를 보면서 아래 그림과 같이 4가지 구조로 나누어 볼 수 있습니다.</p>

<p><code>POST /http.html HTTP/1.1</code> 이 부분이 요청 라인입니다. 요청 라인의 구조는 아래 그림과 같습니다.</p>

<p>요청 라인은 요청 메서드, 요청하는 서버의 URL, HTTP 버전, 줄 바꿈을 위한 CR + LF 순서로 작성됩니다. 요청 메서드는 대소문자를 구분(GET과 get은 다름)합니다.</p>

<h4 id="빈-라인empty-line">빈 라인(Empty line)<a class="anchor after" aria-hidden="true" tabindex="-1" href="#빈-라인empty-line"><span class="anchor-icon">#</span></a></h4>
<p><code>&#x3C;CR>&#x3C;LF></code>으로만 구성된 줄입니다.</p>
<h4 id="메시지-본문message-body---선택">메시지 본문(Message body) - 선택<a class="anchor after" aria-hidden="true" tabindex="-1" href="#메시지-본문message-body---선택"><span class="anchor-icon">#</span></a></h4>
<p>요청 메시지의 본문은 데이터를 담아 서버에 요청을 보내도 보내지 않아도 되는 선택적인 부분입니다. 메시지 본문에 어떤 형태의 데이터가 담겨 있는지는 <code>Content-Type</code> 헤더를 통해 알 수 있습니다.</p>
<h3 id="요청-메서드">요청 메서드<a class="anchor after" aria-hidden="true" tabindex="-1" href="#요청-메서드"><span class="anchor-icon">#</span></a></h3>

<p><strong>안전한 메서드</strong></p>
<p>해당 메서드를 사용한 요청이 서버에 영향을 주지 않는 요청 메서드를 안전한 메서드라고 합니다. GET, HEAD, OPTIONS, TRACE 메서드를 안전한 메서드라고 하는데 안전한 메서드는 읽기 전용(서버 데이터에 영향을 주지 않는) 메서드 입니다. 그 외 POST, PUT, DELETE, CONNECT, PATCH 메서드는 서버 데이터를 변경하기 위해 사용되는 메서드이므로 안전하지 않는 메서드로 분류됩니다.</p>
</blockquote>
<blockquote>
<p><strong>멱등 메서드</strong></p>
<p>여러 번 요청을 보내도 결과가 동일한 메서드를 멱등 메서드라고 합니다. 예를 들어 A라는 요청 메시지를 10번 보냈을 때와 1번만 보냈을 때 두 요청의 서버 결과가 동일한 경우를 말합니다.</p>
<p>서버에 영향을 주지 않는 GET 메서드나 특정 데이터를 대체하는 PUT 메서드, 특정 데이터를 삭제하는 DELETE 메서드는 10번 호출 해도 동일한 결과가 나타나기 때문에 멱등 메서드입니다. 반면 데이터를 추가하는 POST 메서드의 경우 10번 호출할 경우 10번 데이터가 추가 되기 때문 멱등 메서드가 아닙니다.</p>
</blockquote>
<blockquote>
<p><strong>캐시 가능한 메서드</strong></p>
<p>재사용 될 수 있는 요청에 대한 응답의 경우 캐시가 가능합니다. GET, HEAD, POST 메서드의 경우 캐시가 가능한 요청입니다.</p>
<p>이미지를 가져오는 요청의 경우 화면을 새로 고침 할 때 마다 이미지를 네트워크를 통해 가져오는 것은 비효율적이기 때문에 캐시 해 두기 좋습니다. 아래 그림과 같이 크롬 개발자 도구의 네트워크 탭에서 Size 필드에 <code>(memory cache)</code>로 보이는 이미지는 캐시 되었기 때문에 네트워크를 통해 가져오지 않는 것을 볼 수 있습니다.</p>

<p>아래 그림에서 <code>cache-control</code>, <code>expires</code> 등의 응답 헤더를 사용하여 캐시를 제어할 수 있습니다.</p>

</blockquote>
<p>요청 메서드를 하나씩 살펴보도록 하겠습니다.</p>
<h4 id="get">GET<a class="anchor after" aria-hidden="true" tabindex="-1" href="#get"><span class="anchor-icon">#</span></a></h4>
<p>GET은 가져오다 라는 뜻으로 단어의 뜻처럼 서버에서 데이터를 가져오기 위해 사용되는 메서드입니다. GET 메서드 요청은 데이터를 가져오기만 하고 데이터를 수정(혹은 생성)하는 등의 다른 역할을 해서는 안됩니다.</p>
<p>GET 메서드 요청은 URL에 요청에 필요한 정보를 담기 때문에 북마크나 링크 공유가 가능합니다. 또한 캐시가 가능하기 때문에 동일한 GET 메서드 요청을 할 경우 네트워크 비용을 줄일 수 있습니다.</p>
<h4 id="head">HEAD<a class="anchor after" aria-hidden="true" tabindex="-1" href="#head"><span class="anchor-icon">#</span></a></h4>
<p>HEAD 메서드 요청은 GET 메서드 요청을 했을 때 응답 받을 헤더를 요청하는 메서드입니다. HEAD 메서드 요청에 대한 응답에는 메시지 본문이 포함되지 않습니다. 하지만 <code>Content-Length</code> 헤더처럼 응답 메시지 본문의 정보를 담는 헤더는 포함될 수 있습니다.</p>
<p>서버가 정상 동작하는지 확인(Health Check)하거나 <code>Content-Length</code> 헤더를 확인하여 응답 받을 메시지의 크기를 알아내는 등의 헤더 정보를 통한 메타 정보를 조회할 때 유용한 메서드입니다.</p>
<h4 id="post">POST<a class="anchor after" aria-hidden="true" tabindex="-1" href="#post"><span class="anchor-icon">#</span></a></h4>
<p>POST 메서드는 보통 서버에 새로운 데이터를 생성할 때 사용되지만, 메일을 보내야 하는 요청 같은 CRUD(Create, Read, Update, Delete)로 정의하기 힘든 요청에도 POST 메서드를 사용하기도 합니다.</p>
<p>POST 메서드 요청은 서버에 새로운 데이터를 추가하기 때문에 안전한 메서드가 아닙니다. 또한 매번 요청할 때마다 서버에 새로운 데이터를 추가하기 때문에 멱등 메서드 역시 아닙니다.</p>
<p>HTML의 <code>&#x3C;form></code> 태그의 <code>action</code> 속성으로 POST로 설정하면 <code>&#x3C;form></code> 태그 안에 <code>&#x3C;input></code> 태그 데이터들이 메시지 본문에 담겨 POST 메서드 요청을 하게 됩니다.</p>
<p>POST 메서드 요청은 <code>Cache-Control</code> 헤더나 <code>Expires</code> 헤더가 정확히 정의되어 있다면 캐시가 가능합니다.</p>
<h4 id="put">PUT<a class="anchor after" aria-hidden="true" tabindex="-1" href="#put"><span class="anchor-icon">#</span></a></h4>
<p>PUT 메서드 요청은 요청 데이터에 해당되는 데이터가 서버에 존재한다면 서버 데이터 값을 요청 데이터로 대체 하고, 데이터가 존재하지 않는다면 데이터를 생성합니다. 데이터를 생성하게 되면 응답 코드로 <code>201 (Created)</code>를 응답해야 하고, 수정이 되었다면 응답 코드로 <code>200 (OK)</code> 또는 <code>204 (No Content)</code>를 응답해야 합니다.</p>
<p>데이터가 없다면 생성하고 있다면 대체 하기 때문에 N번 요청을 하더라도 동일한 결과가 나타나는 멱등 메서드입니다. 하지만 PUT 메서드 요청은 캐시 되지 않습니다.</p>
<h4 id="delete">DELETE<a class="anchor after" aria-hidden="true" tabindex="-1" href="#delete"><span class="anchor-icon">#</span></a></h4>
<p>DELETE 메서드 요청은 데이터를 삭제하기 위해 사용되는 메서드입니다.</p>
<h4 id="connect">CONNECT<a class="anchor after" aria-hidden="true" tabindex="-1" href="#connect"><span class="anchor-icon">#</span></a></h4>
<p>CONNECT 메서드는 클라이언트가 프록시를 통해 서버와 SSL 통신을 할 때 사용됩니다. HTTP의 CONNECT 메서드는 HTTP 터널링의 가장 일반적인 형태입니다.</p>
<h4 id="options">OPTIONS<a class="anchor after" aria-hidden="true" tabindex="-1" href="#options"><span class="anchor-icon">#</span></a></h4>
<p>OPTIONS 메서드는 유효한 요청인지 확인하기 위한 예비 요청(Preflight request)으로 사용되는 메서드입니다. CORS에서 사용되는 예비 요청에 대한 자세한 내용은 <a href="/tech/browser/cors/#preflight-request">[Browser] CORS란?</a>을 참고 부탁드립니다.</p>
<h4 id="trace">TRACE<a class="anchor after" aria-hidden="true" tabindex="-1" href="#trace"><span class="anchor-icon">#</span></a></h4>
<p>TRACE 메서드는 웹 브라우저가 보내는 HTTP 요청을 HTTP 응답의 body에 담아 응답하는 역할을 합니다. 아래 그림과 같이 HTTP 요청을 보내고 응답을 받습니다.</p>
<p><img src="/assets/img/posts/etc/http_trace.png" alt="HTTP TRACE" loading="lazy" decoding="async" width="1220" height="1025" srcset="/assets/img/posts/etc/nextImageExportOptimizer/http_trace-opt-640.WEBP 640w, /assets/img/posts/etc/nextImageExportOptimizer/http_trace-opt-1080.WEBP 1080w, /assets/img/posts/etc/nextImageExportOptimizer/http_trace-opt-1920.WEBP 1920w" sizes="(max-width: 640px) 100vw, 1000px"></p>
<p>HTTP 요청 데이터를 HTTP 응답의 body에 담아 응답하기 때문에 요청 메시지가 변조되었는지 확인하기 위한 용도로 사용되는 메서드입니다.</p>
<h4 id="patch">PATCH<a class="anchor after" aria-hidden="true" tabindex="-1" href="#patch"><span class="anchor-icon">#</span></a></h4>
<p>PATCH 메서드는 데이터를 업데이트 한다는 의미에서 PUT 메서드와 유사하지만 PUT 메서드는 전체 수정(대체), PATCH 메서드는 부분 수정을 의미합니다. PATCH 메서드는 수정하려고 하는 데이터를 찾을 수 있는 식별자와 수정하려는 값만 요청 데이터에 담아 보내면 되기 때문에, PUT 메서드 보다 네트워크 비용을 줄 일 수 있습니다.</p>
<p>PATCH 메서드는 PUT 메서드와 달리 멱등 메서드가 아닙니다. 예를 들어 블로그의 방문자 수를 카운트 해야 할 경우 새로운 데이터를 추가하는 것도, 전체 데이터를 교체하는 것도 아니기 때문에 PATCH 메서드를 사용할 수 있는데, 방문자 수를 카운트하는 PATCH 메서드를 10번 호출한다면 10명의 방문자가 카운트 되어 호출 할 때 마다 다른 결과가 나타나기 때문에 멱등 메서드가 아니게 됩니다.</p>
<h3 id="요청-헤더">요청 헤더<a class="anchor after" aria-hidden="true" tabindex="-1" href="#요청-헤더"><span class="anchor-icon">#</span></a></h3>
<p>요청 헤더는 <code>Host</code>와 같은 표준 헤더와 <code>X-Request-With</code>와 같은 Custom의 약자인 <code>X-</code>로 시작하는 비표준 헤더가 있습니다. 요청 헤더는 자유롭게 만들어 사용할 수 있기 때문에 <code>X-</code>로 시작하지 않는 비표준 헤더를 만들어 사용할 수 있습니다.</p>
<p><a href="https://en.wikipedia.org/wiki/List_of_HTTP_header_fields#Request_fields">요청 헤더 목록</a>에서 표준 헤더와 자주 사용되는 비표준 헤더의 목록을 더 자세히 확인할 수 있습니다.</p>
<h2 id="http-응답-메시지">HTTP 응답 메시지<a class="anchor after" aria-hidden="true" tabindex="-1" href="#http-응답-메시지"><span class="anchor-icon">#</span></a></h2>

<h3 id="응답-메시지-구조">응답 메시지 구조<a class="anchor after" aria-hidden="true" tabindex="-1" href="#응답-메시지-구조"><span class="anchor-icon">#</span></a></h3>

<p><code>HTTP/1.1 200 OK</code> 이 부분이 상태 라인입니다. 상태 라인의 구조는 아래 그림과 같습니다.</p>

<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="http"><code><span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">Content-Type</span><span style="color:#A0111F;--shiki-dark:#FF9492">:</span><span style="color:#032563;--shiki-dark:#ADDCFF"> text/html; charset=UTF-8</span></span>

<h4 id="빈-라인empty-line-1">빈 라인(Empty line)<a class="anchor after" aria-hidden="true" tabindex="-1" href="#빈-라인empty-line-1"><span class="anchor-icon">#</span></a></h4>
<p>요청 메시지의 빈 라인과 동일하게 <code>&#x3C;CR>&#x3C;LF></code>으로만 구성된 줄입니다.</p>
<h4 id="메시지-본문message-body---선택-1">메시지 본문(Message body) - 선택<a class="anchor after" aria-hidden="true" tabindex="-1" href="#메시지-본문message-body---선택-1"><span class="anchor-icon">#</span></a></h4>
<p>응답 메시지의 본문은 요청 메시지와 동일하게 보내도 보내지 않아도 되는 선택적인 부분입니다. 메시지 본문에 어떤 형태의 데이터가 담겨 있는지는 <code>Content-Type</code> 헤더를 통해 알 수 있습니다.</p>
<h3 id="응답-코드">응답 코드<a class="anchor after" aria-hidden="true" tabindex="-1" href="#응답-코드"><span class="anchor-icon">#</span></a></h3>
<p>응답 코드는 클라이언트의 요청에 대한 서버의 결과를 나타내는 3자리 정수입니다. <code>404 Not Found</code>와 같이 응답 코드와 응답 결과에 대한 이유를 함께 클라이언트로 전달합니다. 응답 결과에 대한 이유는 권장 사항이기 때문에 서버에서 전달 받은 문구가 아닌, 클라이언트에서 서비스에 따라 적당한 문구를 사용자에서 얼마든지 제공할 수 있습니다.</p>
<p>응답 코드는 아래와 같이 크게 5가지로 그룹 지을 수 있습니다. <a href="https://en.wikipedia.org/wiki/List_of_HTTP_status_codes">응답 코드 목록</a>에서 더 자세한 응답 코드 설명을 참고 바랍니다.</p>
<ul>
<li><code>1xx</code> (응답 정보): 요청이 접수되어 요청이 진행 중인 것을 나타내는 코드 영역입니다.</li>
<li><code>2xx</code> (성공): 요청이 성공적으로 수행되었다는 것을 나타내는 코드 영역입니다.</li>
<li><code>3xx</code> (리다이렉션): 요청을 완료하려면 추가 조치가 필요하다는 것을 나타내는 코드 영역입니다.</li>
<li><code>4xx</code> (클라이언트 에러): 요청에 잘못된 내용이 포함되어 있어 요청을 수행할 수 없다는 것을 나타내는 코드 영역입니다.</li>
<li><code>5xx</code> (서버 에러): 올바른 요청을 보냈지만 서버가 수행하지 못했다는 것을 나타내는 코드 영역입니다.</li>
</ul>
<h3 id="응답-헤더">응답 헤더<a class="anchor after" aria-hidden="true" tabindex="-1" href="#응답-헤더"><span class="anchor-icon">#</span></a></h3>
<p>응답 헤더는 요청 헤더와 동일하게 <code>Content-Type</code>과 같은 표준 헤더와 Custom의 약자인 <code>X-</code>로 시작하는 비표준 헤더가 있습니다. 응답 헤더 역시 자유롭게 만들어 사용할 수 있기 때문에 <code>X-</code>로 시작하지 않는 비표준 헤더를 만들어 사용할 수 있습니다.</p>
<p><a href="https://en.wikipedia.org/wiki/List_of_HTTP_header_fields#Response_fields">응답 헤더 목록</a>에서 표준 헤더와 자주 사용되는 비표준 헤더의 목록을 더 자세히 확인할 수 있습니다.</p>
<h2 id="부록">부록<a class="anchor after" aria-hidden="true" tabindex="-1" href="#부록"><span class="anchor-icon">#</span></a></h2>
<h3 id="get-메서드-요청에서-body">GET 메서드 요청에서 Body<a class="anchor after" aria-hidden="true" tabindex="-1" href="#get-메서드-요청에서-body"><span class="anchor-icon">#</span></a></h3>
<p>보통 GET 메서드 요청은 메시지 본문(Message body)을 사용하지 않고 <code>https://beomy.github.io/?id=1234</code>에서 <code>?id=1234</code>와 같이 URL의 <code>?</code>문자 뒤에 오는 쿼리를 사용하여 데이터를 서버로 전달하는 방법을 사용합니다. GET 메서드 요청은 URL에 데이터를 담아야 한다는 내용은 <a href="https://datatracker.ietf.org/doc/html/rfc2616#section-9.3">RFC2616의 9.3 GET</a>에 아래와 같이 명시 되어 있습니다.</p>
<blockquote>
<p>The GET method means retrieve whatever information (in the form of an entity) is identified by the Request-URI.</p>
</blockquote>
<p>그리고 <a href="https://datatracker.ietf.org/doc/html/rfc2616#section-4.3">RFC2616의 4.3 Message Body</a>에 아래와 같이 메시지 본문에 대해 설명하고 있습니다.</p>
<blockquote>
<p>if the request method does not include defined semantics for an entity-body, then the message-body SHOULD be ignored when handling the request.</p>
</blockquote>
<p>이 설명에 의하면 GET 메서드의 데이터는 쿼리를 통해 전달되기 때문에 GET 요청에서 메시지 본문은 무시되어 서버에 전달되지 않게 됩니다. 이 설명은 <a href="https://datatracker.ietf.org/doc/html/rfc7230#section-3.3">RFC7230의 3.3 Message Body</a>에서 삭제 되고, 아래와 같은 설명이 추가 되었습니다.</p>
<blockquote>
<p>Request message framing is independent of method semantics, even if the method does not define any use for a message body.</p>
</blockquote>
<p>메서드의 의미와 메서드 본문의 의미가 독립적으로 구분되면서 GET 메서드 요청에도 메시지 본문을 사용하는 것이 가능해졌습니다. 하지만 클라이언트나 서버에서 GET 메서드의 메시지 본문을 무시하는 경우가 종종 있기 때문에, GET 메서드에서 메시지 본문을 사용할 때 주의가 필요합니다.</p>
<h3 id="http-헤더">HTTP 헤더<a class="anchor after" aria-hidden="true" tabindex="-1" href="#http-헤더"><span class="anchor-icon">#</span></a></h3>
<p>HTTP 헤더는 클라이언트와 서버가 요청/응답에 대한 부가적인 정보를 전달할 수 있도록 해줍니다. HTTP 헤더는 대소문자를 구분하지 않는 헤더 이름과 콜론(<code>:</code>), 그 다음에 오는 헤더 값(헤더 값 앞에 붙은 빈 문자열은 무시됩니다)으로 이루어져있습니다. 비표준 헤더는 Custom의 약자인 <code>X-</code>를 붙여 사용했지만(<a href="https://tools.ietf.org/html/rfc6648">RFC 6648</a>) 비표준 헤더가 표준이 됬을 때 <code>X-</code>를 제거해야 하는 불편함이 있어 2012년 6월 폐기 되었습니다.</p>
<h4 id="컨텍스트에-따른-그룹">컨텍스트에 따른 그룹<a class="anchor after" aria-hidden="true" tabindex="-1" href="#컨텍스트에-따른-그룹"><span class="anchor-icon">#</span></a></h4>
<p>HTTP 요청/응답 컨텍스트에 따라 Request 헤더, Response 헤더, Representation 헤더, Payload 헤더 4가지로 분류할 수 있습니다.</p>
<ul>
<li><a href="https://developer.mozilla.org/en-US/docs/Glossary/Request_header">Request 헤더</a>: 대표적으로 <code>Accept-</code>로 시작하는 헤더들 입니다. 요청 메시지에 대한 정보를 담는 헤더로 서버에서 응답 메시지를 만들 때 사용됩니다. 요청 메시지에 포함된 헤더를 모두 Request 헤더로 생각할 수 있지만, 요청 메시지에 포함된 헤더가 모두 Request 헤더는 아닙니다. 예를 들어 <code>Content-Type</code> 헤더의 경우 Representation 헤더입니다.</li>
<li><a href="https://developer.mozilla.org/en-US/docs/Glossary/Response_header">Response 헤더</a>: <code>Location</code>이나 <code>Server</code> 헤더와 같이 서버의 정보나 위치 등을 담는 헤더입니다. Request 헤더와 동일하게 응답에는 <code>Content-Type</code> 헤더를 포함 할 수 있기 때문에 응답 메시지에 포함된 헤더들이 모두 Response 헤더는 아닙니다.</li>
<li><a href="https://developer.mozilla.org/en-US/docs/Glossary/Representation_header">Representation 헤더</a>: <code>Content-Type</code>, <code>Content-Encoding</code> 헤더와 같이 HTTP 메시지 본문에 담긴 데이터의 정보를 담는 헤더입니다. Representation 헤더는 요청과 응답 메시지에 모두 포함될 수 있습니다.</li>
<li><a href="https://developer.mozilla.org/en-US/docs/Glossary/Payload_header">Payload 헤더</a>: 페이로드(payload)는 전송되는 데이터를 말합니다. payload 헤더는 전송을 위한(또는 전송되는 데이터)를 위한 헤더입니다. payload 헤더로는 전송되는 데이터 길이를 나타내는 <code>Content-Length</code>, 어떠한 형태로 전송 되는지 나타내는 <code>Transfer-Encoding</code> 등이 있습니다.</li>
</ul>
<h4 id="프록시-처리-방법에-따른-그룹">프록시 처리 방법에 따른 그룹<a class="anchor after" aria-hidden="true" tabindex="-1" href="#프록시-처리-방법에-따른-그룹"><span class="anchor-icon">#</span></a></h4>
<p>프록시 서버에서 헤더를 어떻게 처리하느냐에 따라 End-To-End 헤더, Hop-by-Hop 헤더로 분류할 수 있습니다.</p>
<ul>
<li>End-to-End 헤더(종단간 헤더): 최종 수신자(요청 메시지의 경우 서버, 응답 메시지의 경우 클라이언트)에게 전송되는 헤더입니다. 중간 중간에 있는 프록시 서버는 이런 헤더를 수정하지 않고 그대로 재전송해야 하고, 캐시 해야 합니다. <code>Content-Encoding</code> 헤더는 End-to-End 헤더입니다.</li>
<li>Hop-by-Hop 헤더(홉간 헤더): 한번의 전송(한번의 홉)에만 유효한 헤더입니다. 프록시 서버는 이 헤더를 재전송하거나 캐시 하면 안됩니다. <code>Connection</code>, <code>Keep-Alive</code>, <code>Proxy-Authenticate</code>, <code>Proxy-Authorization</code>, <code>TE</code>, <code>Trailer</code>, <code>Transfer-Encoding</code>, <code>Upgrade</code> 헤더가 홉간 헤더입니다.</li>
</ul>
<blockquote>
<p><strong>Hop</strong></p>
<p>홉(Hop)은 깡충깡충 뛰다 라는 뜻을 가진 단어입니다. 클라이언트와 서버 사이에는 게이트웨이나 캐시 역할을 하는 프록시, 라우터, 모뎀 등 많은 것들이 있습니다. 네트워크에서 이야기하는 홉은 데이터가 이런 노드(게이트웨이, 프록시, 라우터, 모뎀 등등..)를 건너가는 모습을 비유적으로 표현한 단어입니다. 아래 그림을 참고하면 홉이 무엇인지 좀 더 쉽게 이해 하실 수 있습니다.</p>

</blockquote>
<h4 id="content-encoding과-transfer-encoding-헤더"><code>Content-Encoding</code>과 <code>Transfer-Encoding</code> 헤더<a class="anchor after" aria-hidden="true" tabindex="-1" href="#content-encoding과-transfer-encoding-헤더"><span class="anchor-icon">#</span></a></h4>
<p><code>Content-Encoding</code>과 <code>Transfer-Encoding</code> 헤더는 비슷하지만 약간의 차이가 있습니다. <code>Content-Encoding</code>은 전달할 데이터를 어떠한 형태로 메시지 본문에 저장 할 지를 나타내고, <code>Transfer-Encoding</code>은 어떠한 형태로 전송 할 지를 나타냅니다. <code>Content-Encoding</code>은 저장에 <code>Transfer-Encoding</code>은 전송에 초점이 있습니다.</p>
<p>메시지 본문에 데이터가 어떤 형태로 저장되어 있는지 서버 끝 단(혹은 브라우저)까지 전송되어야 하기 때문에 <code>Content-Encoding</code> 헤더는 End-to-End 헤더입니다. 반면에 <code>Transfer-Encoding</code> 헤더는 데이터 전송에 초점이 있기 때문에 서버와 서버 간(홉 간)에 어떠한 형태로 전송되는지는 알면 되는 Hop-by-Hop 헤더입니다.</p>
