<p><strong>TL;DR</strong></p>
<ul>
<li>Helm과 Argo CD를 쓰는 환경이라면 <code>kubectl apply</code>를 실행하는 것이 아니라 <strong>git에 커밋을 하면 배포됩니다</strong>. 커밋한 YAML을 Argo CD가 읽어 클러스터에 적용합니다.</li>
<li><strong>Helm</strong>은 쿠버네티스 YAML을 템플릿으로 만드는 도구입니다. <strong>chart</strong>는 Helm이 읽는 폴더입니다. 빈자리를 둔 YAML 템플릿과 그 자리에 넣을 values 파일이 들어 있습니다.
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="text"><code><span class="line"><span>web/                    # 이 폴더 하나가 chart</span></span>
<span class="line"><span>  Chart.yaml            # chart 이름, 버전</span></span>
<span class="line"><span>  values.yaml           # 기본값</span></span>
<span class="line"><span>  values-dev.yaml       # dev 에서 기본값과 다른 값만</span></span>
<span class="line"><span>  values-prod.yaml      # prod 에서 기본값과 다른 값만</span></span>
<span class="line"><span>  templates/            # 값 자리를 비워 둔 YAML</span></span>
<span class="line"><span>    deployment.yaml</span></span>
<span class="line"><span>    service.yaml</span></span>
<span class="line"><span>    ingress.yaml</span></span></code></pre>
<ul>
<li><code>templates/</code>: Deployment, Service, Ingress 같은 YAML을 넣어 두는 폴더입니다. 환경마다 달라지는 자리만 <code>{{ .Values.image.tag }}</code>처럼 비워 둡니다.
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="yaml"><code><span class="line"><span style="color:#66707B;--shiki-dark:#BDC4CC"># templates/deployment.yaml 일부</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">replicas</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: {{ </span><span style="color:#032563;--shiki-dark:#ADDCFF">.Values.replicaCount</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> }}          </span><span style="color:#66707B;--shiki-dark:#BDC4CC"># 환경마다 다르다 → values</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">image</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#032563;--shiki-dark:#ADDCFF">web:{{ .Values.image.tag }}</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">readinessProbe</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">:                               </span><span style="color:#66707B;--shiki-dark:#BDC4CC"># 환경이 달라도 같다 → 템플릿에 고정</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">  httpGet</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: { </span><span style="color:#024C1A;--shiki-dark:#72F088">path</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#032563;--shiki-dark:#ADDCFF">/api/health/ready</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">, </span><span style="color:#024C1A;--shiki-dark:#72F088">port</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#032563;--shiki-dark:#ADDCFF">http</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> }</span></span></code></pre>
</li>
<li><code>values.yaml</code>: 그 빈자리에 들어갈 기본값입니다. 이미지 태그, Pod 수, 메모리, 도메인 같은 값을 키로 적습니다.
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="yaml"><code><span class="line"><span style="color:#66707B;--shiki-dark:#BDC4CC"># values.yaml</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">replicaCount</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#023B95;--shiki-dark:#91CBFF">2</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">image</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">:</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">  tag</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#032563;--shiki-dark:#ADDCFF">"1.2.3"</span></span></code></pre>
</li>
<li><code>values-dev.yaml</code>, <code>values-prod.yaml</code>: 환경마다 기본값과 다른 값만 적습니다. 여기 없는 키는 <code>values.yaml</code>의 값을 그대로 씁니다.</li>
<li>프로브, <code>preStop</code>처럼 환경이 달라도 같은 설정은 템플릿에 고정하고, 메모리 limit, Pod 수, 도메인, 환경 변수처럼 환경마다 다른 것만 values로 뺍니다.</li>
<li>템플릿의 빈자리에 values 값을 채워 완성된 YAML을 만드는 것을 <strong>렌더링</strong>이라고 합니다. 템플릿은 하나지만 어떤 values 파일로 채우느냐에 따라 dev용 YAML, prod용 YAML이 따로 나옵니다.</li>
</ul>
</li>
<li><strong>Argo CD</strong>는 git을 지켜보다가 클러스터가 git과 다르면 git대로 맞추는 컨트롤러입니다. 배포는 <code>values-prod.yaml</code>의 이미지 태그를 바꿔 커밋하면 되고, 그 커밋을 revert하면 롤백이 됩니다.</li>
</ul>
</blockquote>
<p>Helm과 Argo CD를 쓰는 환경에서는 완성된 YAML을 손으로 쓰지 않고, <code>kubectl apply</code>도 사람이 실행하지 않습니다. 이 글에서는 Deployment, Service, Ingress 설정이 어떤 파일에 적히고 어떤 경로로 클러스터에 들어가는지를 살펴봅니다.</p>
<h2 id="배포-흐름-한눈에-보기">배포 흐름 한눈에 보기<a class="anchor after" aria-hidden="true" tabindex="-1" href="#배포-흐름-한눈에-보기"><span class="anchor-icon">#</span></a></h2>
<p>Helm과 Argo CD로 서버 하나를 배포하는 흐름은 다음과 같습니다.</p>
<p><img src="/assets/img/posts/etc/k8s_gitops_flow.svg" alt="git 에 올린 YAML 이 Argo CD 를 거쳐 클러스터에 반영되는 흐름" loading="lazy" decoding="async" width="1080" height="280"></p>
<ol>
<li>코드가 머지되면 CI가 Docker 이미지를 빌드해 레지스트리(이미지 저장소. AWS에서는 ECR)에 올립니다.</li>
<li>배포를 시작하면 CI가 매니페스트 저장소(쿠버네티스 YAML과 chart를 모아 둔 git 저장소)의 <code>values-prod.yaml</code>에서 이미지 태그를 새 태그로 바꿔 커밋합니다.</li>
<li>Argo CD가 그 커밋을 읽어 Helm chart의 템플릿에 values 값을 채워 완성된 YAML을 만들고, 그 YAML을 API 서버에 적용합니다.</li>
<li>Deployment 컨트롤러가 롤링 업데이트를 시작하고, 새 Pod가 프로브를 통과하면 이전 Pod가 내려갑니다.</li>
</ol>
<p>Deployment, Service, Ingress, HPA 같은 YAML은 이 그림에서 Helm chart 안의 <strong>템플릿</strong>이 됩니다. 그 YAML 안의 값 중 환경마다 다른 것만 <strong>values 파일</strong>에 따로 적고, 템플릿에는 그 자리를 비워 둡니다. 사람이 <code>kubectl apply</code>를 실행하던 자리는 <strong>Argo CD</strong>가 대신합니다.</p>
<h2 id="helm이-무엇인가">Helm이 무엇인가<a class="anchor after" aria-hidden="true" tabindex="-1" href="#helm이-무엇인가"><span class="anchor-icon">#</span></a></h2>
<p>Helm은 쿠버네티스 YAML을 템플릿으로 만들어, 값만 바꿔 여러 번 설치할 수 있게 하는 패키지 관리자입니다. <strong>chart</strong>는 그 템플릿과 기본값을 정해진 폴더 구조로 묶은 것입니다. npm에 빗대면 Helm이 npm이고 chart가 패키지입니다.</p>
<p>Helm이 왜 필요한지는 환경이 둘 이상이 되면 바로 드러납니다. dev, stage, prod 세 환경에 같은 서버를 올리면 Deployment, Service, Ingress, ConfigMap 네 장이 환경마다 필요합니다. 그런데 환경마다 다른 값은 이미지 태그, Pod 수, 메모리, 도메인, API 주소 정도이고 나머지는 같습니다.</p>
<p>YAML을 세 벌 복사해 두면 프로브 설정 하나를 고칠 때도 세 파일을 모두 고쳐야 하고, 한 곳을 빠뜨리면 환경마다 설정이 달라집니다. Helm은 공통 부분을 템플릿 한 벌에 두고, 환경마다 다른 값만 별도 파일에 둡니다.</p>
<h3 id="chart의-구조">chart의 구조<a class="anchor after" aria-hidden="true" tabindex="-1" href="#chart의-구조"><span class="anchor-icon">#</span></a></h3>
<p>chart는 정해진 구조의 폴더 하나입니다. <code>helm create web</code>으로 뼈대를 만들 수 있지만, 생성되는 템플릿이 꽤 복잡합니다. 아래처럼 필요한 것만 남기고 시작하는 편이 읽기 쉽습니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="text"><code><span class="line"><span>web/</span></span>

<h3 id="템플릿과-values">템플릿과 values<a class="anchor after" aria-hidden="true" tabindex="-1" href="#템플릿과-values"><span class="anchor-icon">#</span></a></h3>
<p>템플릿은 평범한 YAML에 <code>{{ }}</code>로 값 자리를 비워 둔 것입니다. <code>.Values</code>는 values 파일의 내용이고, <code>.Release.Name</code>과 <code>.Chart.AppVersion</code>처럼 Helm이 채워 주는 값도 있습니다. <code>templates/service.yaml</code>을 예로 보면 다음과 같습니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="yaml"><code><span class="line"><span style="color:#66707B;--shiki-dark:#BDC4CC"># templates/service.yaml</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">apiVersion</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#032563;--shiki-dark:#ADDCFF">v1</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">kind</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#032563;--shiki-dark:#ADDCFF">Service</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">metadata</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">:</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">  name</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: {{ </span><span style="color:#032563;--shiki-dark:#ADDCFF">.Release.Name</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> }}</span></span>

<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">  type</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#032563;--shiki-dark:#ADDCFF">ClusterIP</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">  selector</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">:</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">    app</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: {{ </span><span style="color:#032563;--shiki-dark:#ADDCFF">.Release.Name</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> }}</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">  ports</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">:</span></span>
<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">    - </span><span style="color:#024C1A;--shiki-dark:#72F088">name</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#032563;--shiki-dark:#ADDCFF">http</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">      port</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#023B95;--shiki-dark:#91CBFF">80</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">      targetPort</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#032563;--shiki-dark:#ADDCFF">http</span></span></code></pre>
<p><code>.Release.Name</code>은 설치할 때 붙이는 이름입니다. 이 chart를 <code>web</code>이라는 이름으로 설치하면 Service 이름도 <code>web</code>이 됩니다. Deployment와 Pod 라벨도 같은 값으로 렌더링되므로 서로 어긋날 일이 없습니다. 이름과 라벨이 왜 맞아야 하는지는 <a href="#%EB%B6%80%EB%A1%9D-yaml-%EC%9D%BD%EB%8A%94-%EB%B2%95">부록</a>에 정리했습니다.</p>
<p>렌더링은 템플릿의 <code>{{ }}</code> 자리에 values 값을 채워 완성된 YAML을 만드는 것입니다. 템플릿 파일 하나에서 YAML 하나가 나오므로 <code>templates/deployment.yaml</code>에서 Deployment가, <code>templates/service.yaml</code>에서 Service가 나옵니다. 템플릿은 하나인데 values 파일을 바꿔 끼우면 dev용 YAML과 prod용 YAML이 따로 나옵니다.</p>
<p>values는 chart를 만드는 사람이 키 이름을 정하는 평범한 YAML입니다. <code>replicaCount</code>는 쿠버네티스에 없는 단어이고, 템플릿에서 <code>replicas: {{ .Values.replicaCount }}</code>로 연결해 줘야 의미가 생깁니다. 그래서 values 파일만 보고는 무엇이 어디로 가는지 알 수 없고, 템플릿과 짝지어 읽어야 합니다.</p>
<blockquote>
<p><strong>템플릿 문법에서 자주 보이는 네 가지</strong></p>
<ul>
<li><code>{{ .Values.x }}</code>: 값을 끼워 넣습니다.</li>
<li><code>{{- if }}</code> … <code>{{- end }}</code>: 조건에 따라 줄을 넣거나 뺍니다.</li>
<li><code>toYaml</code>: values의 한 덩어리를 YAML 그대로 옮깁니다.</li>
<li><code>nindent 12</code>: 그 덩어리 앞에 줄바꿈을 하나 넣고 12칸 들여씁니다.</li>
</ul>
<p><code>{{-</code>의 <code>-</code>는 앞의 줄바꿈과 공백을 지우라는 뜻으로, 없으면 빈 줄이 남습니다. <code>{{-</code>가 지운 줄바꿈을 <code>nindent</code>가 다시 넣어 주므로 <code>{{-</code>와 <code>nindent</code>는 세트로 씁니다.</p>
</blockquote>
<p><code>values-prod.yaml</code>처럼 환경별 파일을 주면 <code>values.yaml</code>의 기본값 위에 키 단위로 덮어씁니다. <code>image.tag</code>만 적으면 <code>image.repository</code>는 기본값이 그대로 남으므로, 환경별 파일에는 기본값과 다른 키만 적으면 됩니다.</p>
<h3 id="렌더링과-설치">렌더링과 설치<a class="anchor after" aria-hidden="true" tabindex="-1" href="#렌더링과-설치"><span class="anchor-icon">#</span></a></h3>
<p>Helm 명령은 <code>helm &#x3C;동사> [NAME] [CHART] [flags]</code> 형식입니다. NAME과 CHART는 이 순서로 적어야 하고, flags는 <code>-</code>로 시작하므로 어디에 와도 됩니다. 자주 쓰는 동사는 <code>template</code>, <code>upgrade --install</code>, <code>history</code>, <code>rollback</code> 넷입니다.</p>
<h4 id="helm-template-렌더링">helm template: 렌더링<a class="anchor after" aria-hidden="true" tabindex="-1" href="#helm-template-렌더링"><span class="anchor-icon">#</span></a></h4>
<p>템플릿과 값이 합쳐진 결과는 <code>helm template</code>으로 확인합니다. <code>helm template</code>은 클러스터에 아무것도 보내지 않고 완성된 YAML만 출력합니다. 그래서 chart를 고친 뒤 의도대로 렌더링되는지 확인할 때 가장 자주 씁니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="bash"><code><span class="line"><span style="color:#702C00;--shiki-dark:#FFB757">helm</span><span style="color:#032563;--shiki-dark:#ADDCFF"> template</span><span style="color:#032563;--shiki-dark:#ADDCFF"> web</span><span style="color:#032563;--shiki-dark:#ADDCFF"> ./web</span><span style="color:#023B95;--shiki-dark:#91CBFF"> -n</span><span style="color:#032563;--shiki-dark:#ADDCFF"> web</span><span style="color:#023B95;--shiki-dark:#91CBFF"> -f</span><span style="color:#032563;--shiki-dark:#ADDCFF"> ./web/values-prod.yaml</span><span style="color:#023B95;--shiki-dark:#91CBFF"> --set</span><span style="color:#032563;--shiki-dark:#ADDCFF"> image.tag=</span><span style="color:#023B95;--shiki-dark:#91CBFF">1.2.4</span></span></code></pre>
<ul>
<li><code>web</code> (NAME): release(설치 단위) 이름입니다. 템플릿의 <code>.Release.Name</code>에 들어가므로 Deployment, Service 이름이 모두 <code>web</code>이 됩니다.</li>
<li><code>./web</code> (CHART): chart 폴더입니다.</li>
<li><code>-n web</code> (flags): 네임스페이스입니다. <code>.Release.Namespace</code>에 들어갑니다.</li>
<li><code>-f ./web/values-prod.yaml</code> (flags): <code>values.yaml</code> 위에 덮어쓸 환경별 values 파일입니다.</li>
<li><code>--set image.tag=1.2.4</code> (flags): 값 하나를 명령줄에서 덮어씁니다. 파일보다 우선하므로 <code>values-prod.yaml</code>에 적힌 태그가 있어도 이 값이 들어갑니다.</li>
</ul>
<h4 id="helm-upgrade---install-클러스터에-적용">helm upgrade --install: 클러스터에 적용<a class="anchor after" aria-hidden="true" tabindex="-1" href="#helm-upgrade---install-클러스터에-적용"><span class="anchor-icon">#</span></a></h4>
<p>Helm에서 설치(install)는 렌더링한 YAML을 API 서버에 보내 클러스터에 객체를 만드는 것으로, <code>kubectl apply</code>가 하는 일과 같습니다. 직접 설치할 때는 <code>helm upgrade --install</code>을 씁니다. <code>--install</code>을 붙이면 처음에는 설치하고, 이미 설치되어 있으면 업데이트합니다. 처음 설치만 하는 <code>helm install</code>도 있지만, <code>upgrade --install</code>이 그 경우까지 포함하므로 보통 <code>upgrade --install</code>만 씁니다. 이렇게 설치된 결과를 <strong>release</strong>라고 부릅니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="bash"><code><span class="line"><span style="color:#702C00;--shiki-dark:#FFB757">helm</span><span style="color:#032563;--shiki-dark:#ADDCFF"> upgrade</span><span style="color:#023B95;--shiki-dark:#91CBFF"> --install</span><span style="color:#032563;--shiki-dark:#ADDCFF"> web</span><span style="color:#032563;--shiki-dark:#ADDCFF"> ./web</span><span style="color:#023B95;--shiki-dark:#91CBFF"> -n</span><span style="color:#032563;--shiki-dark:#ADDCFF"> web</span><span style="color:#023B95;--shiki-dark:#91CBFF"> --create-namespace</span><span style="color:#023B95;--shiki-dark:#91CBFF"> -f</span><span style="color:#032563;--shiki-dark:#ADDCFF"> ./web/values-prod.yaml</span><span style="color:#023B95;--shiki-dark:#91CBFF"> --set</span><span style="color:#032563;--shiki-dark:#ADDCFF"> image.tag=</span><span style="color:#023B95;--shiki-dark:#91CBFF">1.2.4</span></span></code></pre>
<p><code>--create-namespace</code>는 네임스페이스가 없으면 만들라는 뜻입니다. 나머지는 <code>helm template</code>과 같습니다.</p>
<h4 id="helm-history-helm-rollback-기록과-되돌리기">helm history, helm rollback: 기록과 되돌리기<a class="anchor after" aria-hidden="true" tabindex="-1" href="#helm-history-helm-rollback-기록과-되돌리기"><span class="anchor-icon">#</span></a></h4>
<p>Helm에는 별도 데이터베이스가 없습니다. 대신 release마다 어떤 값으로 어떤 YAML을 보냈는지를 클러스터 안의 Secret(비밀번호처럼 노출되면 안 되는 값을 담는 객체)에 버전별로 남겨 둡니다. <code>helm history</code>로 그 기록을 보고, <code>helm rollback</code>으로 이전 버전의 YAML을 다시 적용합니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="bash"><code><span class="line"><span style="color:#702C00;--shiki-dark:#FFB757">helm</span><span style="color:#032563;--shiki-dark:#ADDCFF"> history</span><span style="color:#032563;--shiki-dark:#ADDCFF"> web</span><span style="color:#023B95;--shiki-dark:#91CBFF"> -n</span><span style="color:#032563;--shiki-dark:#ADDCFF"> web</span><span style="color:#66707B;--shiki-dark:#BDC4CC">          # 1, 2, 3 ... 버전별 배포 기록</span></span>
<span class="line"><span style="color:#702C00;--shiki-dark:#FFB757">helm</span><span style="color:#032563;--shiki-dark:#ADDCFF"> rollback</span><span style="color:#032563;--shiki-dark:#ADDCFF"> web</span><span style="color:#023B95;--shiki-dark:#91CBFF"> 2</span><span style="color:#023B95;--shiki-dark:#91CBFF"> -n</span><span style="color:#032563;--shiki-dark:#ADDCFF"> web</span><span style="color:#66707B;--shiki-dark:#BDC4CC">       # 2번 버전의 YAML 을 다시 적용. 기록에는 새 버전으로 쌓인다</span></span></code></pre>
<p>다만 뒤에서 볼 Argo CD를 쓰면 설치와 되돌리기 명령을 사람이 실행하지 않습니다. Argo CD가 <code>helm template</code>으로 YAML을 뽑아 직접 적용하므로, 손에 익혀야 하는 것은 <code>helm template</code> 하나입니다.</p>
<h2 id="서버-설정을-chart에-옮기기">서버 설정을 chart에 옮기기<a class="anchor after" aria-hidden="true" tabindex="-1" href="#서버-설정을-chart에-옮기기"><span class="anchor-icon">#</span></a></h2>
<p>Next.js 서버 하나를 띄우는 데 필요한 설정을 하나씩 chart에 옮기면서, 무엇을 템플릿에 고정하고 무엇을 values로 빼는지 살펴보겠습니다. 기준은 <strong>환경이 달라도 같은 값은 템플릿에, 환경마다 다른 값은 values에</strong> 두는 것입니다. values로 빼는 키가 많아질수록 템플릿만 봐서는 완성된 YAML을 알 수 없게 되므로, 실제로 환경마다 다른 것만 뺍니다. 아래 표의 values 키 이름은 이 chart에서 정한 것입니다. 그중 <code>replicaCount</code>, <code>image.*</code>, <code>autoscaling.*</code>은 <code>helm create</code>가 만드는 뼈대의 관례를 따랐습니다.</p>

<p>Deployment YAML에는 <code>spec</code>이 바깥과 안쪽에 하나씩 있습니다. 바깥 <code>spec</code>은 Deployment 자체의 설정으로, Pod를 몇 개 유지하고 어떤 방식으로 교체할지를 적습니다. 안쪽 <code>spec.template</code>은 Pod 하나의 설계도로, 어떤 컨테이너를 어떤 설정으로 띄울지를 적습니다. <code>template</code> 아래 내용은 Pod YAML에서 <code>apiVersion</code>과 <code>kind</code>를 뺀 것과 같아서, <code>spec</code> 아래에 다시 <code>metadata</code>와 <code>spec</code>이 나오는 모양이 됩니다. Deployment는 이 설계도를 복사해 <code>replicas</code> 수만큼 Pod를 만듭니다.</p>
<blockquote>
<p><strong><code>image</code> 태그는 왜 values에 두고 <code>latest</code>는 피하나</strong></p>
<p>이미지 태그는 배포할 때마다 바뀌는 값이고, 배포가 곧 이 값을 바꾸는 커밋이므로 반드시 values에 둡니다. 태그를 <code>latest</code>로 두거나 생략하는 것도 피합니다. 태그가 그대로면 새 이미지를 올려도 YAML은 바뀐 것이 없습니다. 쿠버네티스는 YAML이 바뀌지 않으면 Pod를 교체하지 않으므로 새 이미지가 배포되지 않습니다. 게다가 태그가 <code>latest</code>거나 없으면 <code>imagePullPolicy</code> 기본값이 <code>Always</code>가 되어 컨테이너가 시작될 때마다 레지스트리를 조회합니다. 그래서 재시작 시점에 따라 Pod마다 다른 이미지가 도는 일도 생깁니다.</p>
</blockquote>
<blockquote>
<p><strong><code>NODE_OPTIONS</code>는 왜 <code>resources</code>와 함께 values에 두나</strong></p>
<p><code>NODE_OPTIONS</code>의 <code>--max-old-space-size</code>는 Node.js 힙 상한으로, 보통 메모리 limit의 75% 정도로 잡습니다. limit에 따라 정해지는 값이라 prod에서 limit을 올리면 힙 상한도 같이 올려야 합니다. 둘을 values에 나란히 두면 한 파일에서 같이 고치게 되어 한쪽만 바꾸는 실수를 줄일 수 있습니다. 환경 변수 값은 문자열이어야 하므로, 템플릿에서는 <code>quote</code>로 값에 따옴표를 씌워 문자열로 넘깁니다.</p>
</blockquote>
<blockquote>
<p><strong><code>checksum/config</code> 어노테이션은 무엇인가</strong></p>
<p>ConfigMap만 바꿔서는 서버에 반영되지 않는 문제를 해결하는 장치입니다.</p>
<ul>
<li>환경 변수는 Pod가 시작될 때 ConfigMap에서 한 번 읽어 옵니다. 그래서 ConfigMap 값을 바꿔도 이미 떠 있는 Pod는 옛날 값을 그대로 가지고 있습니다.</li>
<li>Pod가 새로 뜨려면 롤링 업데이트가 일어나야 하는데, 롤링 업데이트는 Deployment의 <code>template</code>이 바뀔 때만 일어납니다. ConfigMap은 Deployment 밖의 객체라 아무리 바꿔도 <code>template</code>은 그대로입니다.</li>
<li>그래서 ConfigMap 내용의 해시값을 <code>template</code>의 어노테이션에 적어 둡니다. ConfigMap이 바뀌면 해시값이 바뀌고, 해시값이 바뀌면 <code>template</code>이 바뀐 것이 되어 롤링 업데이트가 일어납니다. Helm 공식 문서에서 권장하는 방법입니다.</li>
</ul>
</blockquote>
<h3 id="hpa와-replicas">HPA와 replicas<a class="anchor after" aria-hidden="true" tabindex="-1" href="#hpa와-replicas"><span class="anchor-icon">#</span></a></h3>
<p>HPA를 쓰면 Deployment의 <code>replicas</code>를 빼야 합니다. 적어 두면 <code>kubectl apply</code>를 할 때마다 HPA가 조절해 둔 Pod 수가 그 값으로 되돌아가기 때문입니다. Argo CD에서는 HPA가 Pod 수를 바꾸는 순간 git과 어긋난 것으로 보고 git 값으로 되돌리므로, 이 되돌림이 더 자주 일어납니다. chart에서는 <code>replicas</code>를 넣을지 뺄지를 조건으로 처리합니다. <code>autoscaling.enabled</code>가 참이면 Deployment에서 <code>replicas</code> 줄이 빠지고 HPA가 렌더링되며, 거짓이면 반대입니다. dev는 Pod 두 개로 고정하고 prod만 HPA를 켜는 식의 구성이 values 한 줄로 정해집니다.</p>

<h3 id="ingress와-alb-어노테이션">Ingress와 ALB 어노테이션<a class="anchor after" aria-hidden="true" tabindex="-1" href="#ingress와-alb-어노테이션"><span class="anchor-icon">#</span></a></h3>
<p>Ingress는 어느 도메인의 어느 경로를 어느 Service로 보낼지를 적는 객체이고, 실제 트래픽을 받는 것은 그 선언을 보고 만들어진 ALB입니다. 그런데 "ALB를 사내망에만 열어라", "헬스체크는 이 경로로 해라" 같은 ALB 전용 옵션은 Ingress 스펙에 적을 자리가 없습니다. 대신 <code>metadata.annotations</code>에 <code>alb.ingress.kubernetes.io/</code> 접두어가 붙은 키로 적습니다. AWS Load Balancer Controller가 그 어노테이션을 읽어 ALB에 반영합니다. 아래 템플릿의 어노테이션 다섯 줄이 모두 이런 ALB 옵션입니다.</p>
<p>다섯 줄 중 환경마다 다른 것은 <code>scheme</code> 하나입니다. dev는 사내망에서만 열고(<code>internal</code>) prod는 인터넷에 여는(<code>internet-facing</code>) 경우가 많아 values로 뺐습니다. 헬스체크 경로와 주기, 타깃 타입은 환경이 달라도 같으므로 템플릿에 고정했습니다. 도메인은 어노테이션이 아니라 <code>spec.rules.host</code>에 적는데, 이것도 환경마다 다르므로 values로 뺐습니다.</p>
<p>등록 해제 대기 시간(<code>deregistration_delay.timeout_seconds</code>)은 내려가는 Pod로 가는 새 요청을 ALB가 끊은 뒤, 진행 중인 요청이 끝나기를 기다리는 시간입니다. 이 값이 <code>terminationGracePeriodSeconds</code>보다 길면 Pod가 먼저 죽어 버리므로, 유예 시간을 넘지 않게 잡아야 합니다. 그래서 Deployment와 Ingress 템플릿이 같은 values 키를 읽어 둘 다 45초가 되게 했습니다. 고칠 곳이 한 군데라 둘이 어긋날 일이 없습니다.</p>

<h3 id="configmap과-환경-변수">ConfigMap과 환경 변수<a class="anchor after" aria-hidden="true" tabindex="-1" href="#configmap과-환경-변수"><span class="anchor-icon">#</span></a></h3>
<p>환경 변수는 Deployment의 <code>env</code>에 하나씩 적을 수도 있습니다. 하지만 API 주소나 기능 플래그처럼 환경마다 다르고 개수도 늘어나는 값은 ConfigMap이라는 별도 객체에 모아 둡니다. Deployment에서는 <code>envFrom</code>으로 그 ConfigMap을 통째로 불러옵니다. <code>env</code>가 이름과 값을 하나씩 적는 필드라면, <code>envFrom</code>은 ConfigMap이나 Secret의 키 전부를 환경 변수로 넣는 필드입니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="yaml"><code><span class="line"><span style="color:#66707B;--shiki-dark:#BDC4CC"># Deployment 의 컨테이너 설정</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">env</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">:                              </span><span style="color:#66707B;--shiki-dark:#BDC4CC"># 하나씩</span></span>
<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">  - </span><span style="color:#024C1A;--shiki-dark:#72F088">name</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#032563;--shiki-dark:#ADDCFF">NODE_ENV</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">    value</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#032563;--shiki-dark:#ADDCFF">production</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">envFrom</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">:                          </span><span style="color:#66707B;--shiki-dark:#BDC4CC"># 통째로</span></span>
<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">  - </span><span style="color:#024C1A;--shiki-dark:#72F088">configMapRef</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">:</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">      name</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#032563;--shiki-dark:#ADDCFF">web-config</span><span style="color:#66707B;--shiki-dark:#BDC4CC">            # 이 ConfigMap 의 키 전부</span></span>
<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">  - </span><span style="color:#024C1A;--shiki-dark:#72F088">secretRef</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">:</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">      name</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#032563;--shiki-dark:#ADDCFF">web-secret</span><span style="color:#66707B;--shiki-dark:#BDC4CC">            # 이 Secret 의 키 전부</span></span>
<span class="line"><span style="color:#023B95;--shiki-dark:#91CBFF">---</span></span>
<span class="line"><span style="color:#66707B;--shiki-dark:#BDC4CC"># ConfigMap web-config</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">data</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">:</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">  API_BASE_URL</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#032563;--shiki-dark:#ADDCFF">https://api.example.com</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">  FEATURE_X</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#032563;--shiki-dark:#ADDCFF">"true"</span></span></code></pre>
<p>이렇게 두면 컨테이너 안에는 <code>NODE_ENV</code>, <code>API_BASE_URL</code>, <code>FEATURE_X</code>와 <code>web-secret</code>의 키들이 모두 환경 변수로 들어가고, 어느 쪽에서 왔는지는 구분되지 않습니다. ConfigMap에 키를 추가하면 Deployment를 고치지 않아도 환경 변수가 늘어납니다.</p>
<blockquote>
<p><strong><code>web-secret</code>은 어디서 오나</strong></p>
<p>비밀 값은 chart에 넣지 않습니다. Secret의 <code>data</code>는 base64 인코딩일 뿐 암호화가 아니라서 git에 올리면 그대로 노출되기 때문입니다. 대신 AWS Secrets Manager 같은 외부 저장소에 값을 둡니다. External Secrets Operator 같은 컨트롤러가 그 값을 읽어 클러스터 안에 <code>web-secret</code>이라는 Secret을 만듭니다. Deployment는 그 이름만 <code>secretRef</code>로 참조합니다.</p>
</blockquote>
<p>ConfigMap의 <code>data</code>에 들어갈 키와 값은 환경마다 다르므로 values에 적습니다. 이 chart에서는 values의 <code>config</code> 아래에 적은 내용이 그대로 <code>data</code>가 되도록 템플릿을 만들었습니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="yaml"><code><span class="line"><span style="color:#66707B;--shiki-dark:#BDC4CC"># templates/configmap.yaml</span></span>

<p>환경 변수는 전부 문자열이므로 values에서도 <code>"true"</code>, <code>"3000"</code>처럼 따옴표를 붙여야 합니다. 따옴표 없이 적으면 YAML이 불리언이나 숫자로 읽어 적용이 거부됩니다.</p>
<h3 id="values-파일">values 파일<a class="anchor after" aria-hidden="true" tabindex="-1" href="#values-파일"><span class="anchor-icon">#</span></a></h3>

<h2 id="argo-cd가-무엇인가">Argo CD가 무엇인가<a class="anchor after" aria-hidden="true" tabindex="-1" href="#argo-cd가-무엇인가"><span class="anchor-icon">#</span></a></h2>
<p>Argo CD는 git 저장소에 있는 매니페스트(또는 chart)와 클러스터의 실제 상태를 계속 비교하고, 다르면 git대로 맞추는 컨트롤러입니다. 사람이 <code>kubectl apply</code>나 <code>helm upgrade</code>를 실행하는 자리를 대신합니다.</p>
<h3 id="push와-pull">push와 pull<a class="anchor after" aria-hidden="true" tabindex="-1" href="#push와-pull"><span class="anchor-icon">#</span></a></h3>
<p>완성된 YAML을 누가 어디서 API 서버에 보내느냐에 따라 배포 방식은 세 가지로 나뉩니다.</p>

























<div class="table-scroll"><table><thead><tr><th>방법</th><th>누가 보내나</th><th>클러스터 자격 증명이 있는 곳</th></tr></thead><tbody><tr><td>내 컴퓨터에서 <code>kubectl apply</code> / <code>helm upgrade</code></td><td>사람</td><td>개발자 노트북</td></tr><tr><td>CI(GitHub Actions)에서 <code>kubectl apply</code> / <code>helm upgrade</code></td><td>CI 러너</td><td>CI 시크릿</td></tr><tr><td>Argo CD</td><td>클러스터 안의 컨트롤러</td><td>클러스터 안</td></tr></tbody></table></div>
<p>앞의 둘은 바깥에서 클러스터로 미는 <strong>push</strong> 방식이고, Argo CD는 클러스터 안에서 git을 보고 가져오는 <strong>pull</strong> 방식입니다. push 방식은 단순하지만 CI에 클러스터를 바꿀 수 있는 자격 증명을 둬야 하고, 누가 언제 무엇을 적용했는지가 CI 로그에 흩어집니다. pull 방식은 자격 증명이 클러스터 밖으로 나가지 않고, git이 곧 배포 기록이 됩니다. 이 방식을 <strong>GitOps</strong>라고 부릅니다.</p>
<h3 id="argo-cd가-하는-일">Argo CD가 하는 일<a class="anchor after" aria-hidden="true" tabindex="-1" href="#argo-cd가-하는-일"><span class="anchor-icon">#</span></a></h3>
<p>Argo CD는 클러스터 안에 설치되는 컨트롤러입니다. 다른 컨트롤러와 다른 점은 클러스터 객체에 더해 git 저장소까지 지켜본다는 것입니다.</p>
<p><img src="/assets/img/posts/etc/k8s_addons.svg" alt="EKS 클러스터 안에서 Argo CD 와 배포하는 서버가 각자의 네임스페이스에 Deployment 로 떠 있는 구조" loading="lazy" decoding="async" width="760" height="520"></p>
<p>공식 설치 매니페스트나 Helm chart(argo-helm)를 설치하면 Argo CD 구성 요소가 <code>argocd</code> 네임스페이스에 Pod로 만들어집니다. 별도 서비스가 아니라 클러스터 안에서 돌고, <code>web</code>과 마찬가지로 컨트롤러가 Pod 수를 유지합니다. Argo CD가 하는 일은 순서대로 다음과 같습니다.</p>
<ol>
<li>git 저장소의 지정한 경로를 주기적으로(기본 2~3분, 120초에 최대 60초의 무작위 지연을 더한 값) 읽습니다. 웹훅을 걸면 push 즉시 읽습니다.</li>
<li>그 경로가 Helm chart면 <code>helm template</code>으로, 평범한 YAML이면 그대로 렌더링해 <strong>git이 원하는 상태</strong>를 만듭니다.</li>
<li>클러스터에서 같은 객체들을 읽어 <strong>현재 상태</strong>와 비교합니다. 둘이 다르면 OutOfSync(git과 클러스터가 어긋난 상태)로 표시합니다.</li>
<li>자동 동기화가 켜져 있으면 렌더링한 객체를 API 서버에 <code>apply</code>합니다. 그 뒤는 <code>kubectl apply</code>를 했을 때와 똑같이 컨트롤러와 kubelet의 몫입니다.</li>
</ol>
<p>Argo CD는 Helm의 <code>install</code>을 쓰지 않고 <code>template</code>으로 YAML만 뽑아 직접 적용합니다. 그래서 <code>helm list</code>에는 아무것도 나오지 않고, <code>helm rollback</code>도 쓸 수 없습니다. Argo CD 화면에는 이전 커밋으로 되돌리는 롤백 메뉴가 있습니다. 하지만 자동 동기화가 켜져 있으면 되돌려도 곧바로 최신 커밋으로 다시 맞춰지므로, Argo CD는 자동 동기화를 끄기 전에는 롤백을 받아 주지 않습니다. 롤백은 git에서 커밋을 되돌려서 합니다.</p>

<h3 id="synced와-healthy">Synced와 Healthy<a class="anchor after" aria-hidden="true" tabindex="-1" href="#synced와-healthy"><span class="anchor-icon">#</span></a></h3>
<p>Argo CD 화면은 Application마다 Sync와 Health 두 가지 상태를 보여 줍니다.</p>




















<div class="table-scroll"><table><thead><tr><th>상태</th><th>묻는 것</th><th>값</th></tr></thead><tbody><tr><td>Sync</td><td>git과 클러스터의 <strong>선언</strong>이 같은가</td><td>Synced, OutOfSync, Unknown</td></tr><tr><td>Health</td><td>선언대로 <strong>실제로 돌고</strong> 있는가</td><td>Healthy, Progressing, Degraded, Suspended, Missing, Unknown</td></tr></tbody></table></div>
<ul>
<li>Sync: git에 적힌 필드(라벨과 어노테이션 포함)를 클러스터 객체의 같은 필드와 비교한 결과입니다. <code>status</code>나 클러스터가 채운 기본값은 비교하지 않습니다.</li>
<li>Health: 객체의 <code>status</code>를 읽은 결과입니다. Deployment라면 <code>kubectl rollout status</code>와 같은 기준으로 판정합니다.
<ul>
<li>Progressing: Pod 교체가 진행 중입니다. 배포 직후에는 git이 반영된 상태라 Synced이면서 Progressing입니다.</li>
<li>Healthy: 새 Pod가 readiness 프로브를 통과하고(<code>minReadySeconds</code>가 있으면 그만큼 더 지나) 이전 Pod가 모두 내려간 상태입니다. Health 판정도 결국 readiness 프로브가 기준입니다.</li>
<li>Degraded: 새 Pod가 계속 <code>CrashLoopBackOff</code>여서 Deployment의 <code>progressDeadlineSeconds</code>(기본 600초) 안에 교체를 끝내지 못한 상태입니다.</li>
</ul>
</li>
</ul>
<h2 id="git-chart-argo-cd의-관계">git, chart, Argo CD의 관계<a class="anchor after" aria-hidden="true" tabindex="-1" href="#git-chart-argo-cd의-관계"><span class="anchor-icon">#</span></a></h2>
<p>세 가지가 어떻게 이어지는지를 저장소 구조에서 시작해 살펴보겠습니다.</p>
<h3 id="저장소-두-개">저장소 두 개<a class="anchor after" aria-hidden="true" tabindex="-1" href="#저장소-두-개"><span class="anchor-icon">#</span></a></h3>

<span class="line"><span>  argocd/</span></span>
<span class="line"><span>    web-dev.yaml                # Application. apps/web 을 values-dev.yaml 로 dev 네임스페이스에</span></span>
<span class="line"><span>    web-prod.yaml               # Application. apps/web 을 values-prod.yaml 로 web 네임스페이스에</span></span></code></pre>
<p>앱 코드와 매니페스트를 다른 저장소에 두는 이유는 두 가지입니다.</p>
<ul>
<li>코드가 머지됐다고 바로 배포되면 안 되는 경우가 있습니다. 머지는 오늘 하고 배포는 내일 하는 식입니다.</li>
<li>매니페스트 저장소의 커밋 기록이 곧 배포 기록이 됩니다. 코드 커밋이 섞여 있으면 어느 커밋이 배포였는지 가려내야 합니다.</li>
</ul>
<h3 id="배포는-커밋-한-줄">배포는 커밋 한 줄<a class="anchor after" aria-hidden="true" tabindex="-1" href="#배포는-커밋-한-줄"><span class="anchor-icon">#</span></a></h3>
<p>앱 코드와 매니페스트를 나눈 구조에서 <strong>배포는 git 커밋</strong>입니다. 코드가 머지되면 CI는 이미지를 빌드해 올려 두기만 합니다. 배포할 때는 <code>values-prod.yaml</code>의 <code>image.tag</code>를 그 이미지 태그로 바꿔 커밋합니다. 이 커밋은 배포 워크플로를 실행한 CI가 만들어도 되고 사람이 직접 만들어도 됩니다. 커밋이 머지되면 Argo CD가 읽어 Deployment를 갱신하고 롤링 업데이트가 시작됩니다. 이미지를 올리고 git에 커밋하는 것까지가 클러스터 밖의 일이고, 클러스터에 넣는 것은 Argo CD의 일입니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="text"><code><span class="line"><span> # values-prod.yaml</span></span>
<span class="line"><span> image:</span></span>
<span class="line"><span>-  tag: "1.2.3"</span></span>
<span class="line"><span>+  tag: "1.2.4"</span></span></code></pre>
<p>CI가 커밋을 만드는 구성이라면 사람이 하는 일은 그 커밋을 리뷰하고 머지하는 것뿐입니다. 되돌리고 싶으면 커밋을 revert합니다. revert 커밋이 머지되면 Argo CD가 이전 태그로 렌더링해 적용하고, 롤링 업데이트가 한 번 더 일어나 이전 이미지로 돌아갑니다. <code>kubectl</code>로 클러스터만 이전 상태로 되돌려도 <code>selfHeal</code>이 켜져 있으면 수 초 안에 git 상태로 되돌아갑니다.</p>
<h3 id="무엇을-바꾸려면-어디를-고치나">무엇을 바꾸려면 어디를 고치나<a class="anchor after" aria-hidden="true" tabindex="-1" href="#무엇을-바꾸려면-어디를-고치나"><span class="anchor-icon">#</span></a></h3>
<p>저장소의 각 위치가 무엇을 책임지는지를 표로 정리하면 다음과 같습니다.</p>

























<div class="table-scroll"><table><thead><tr><th>바꾸고 싶은 것</th><th>고치는 곳</th></tr></thead><tbody><tr><td>코드</td><td>앱 저장소. 배포를 시작하면 CI가 <code>values-&#x3C;env>.yaml</code>의 <code>image.tag</code>를 커밋</td></tr><tr><td>메모리 limit, Pod 수, 도메인, 환경 변수</td><td><code>values-&#x3C;env>.yaml</code></td></tr><tr><td>프로브 시간, <code>preStop</code>, 어노테이션 구조</td><td><code>templates/</code></td></tr><tr><td>어느 브랜치의 어느 경로를 어느 클러스터에</td><td><code>argocd/*.yaml</code></td></tr></tbody></table></div>
<p>템플릿을 고치는 커밋은 모든 환경에 동시에 적용되므로, 구조를 바꿀 때는 values로 빼서 dev에서 먼저 켜 보는 쪽이 안전합니다.</p>
<h2 id="부록-yaml-읽는-법">부록: YAML 읽는 법<a class="anchor after" aria-hidden="true" tabindex="-1" href="#부록-yaml-읽는-법"><span class="anchor-icon">#</span></a></h2>
<p>본문의 템플릿에 나온 쿠버네티스 YAML 필드를 정리한 부록입니다. 필드가 낯설 때 참고하면 됩니다.</p>
<h3 id="네-필드">네 필드<a class="anchor after" aria-hidden="true" tabindex="-1" href="#네-필드"><span class="anchor-icon">#</span></a></h3>
<p>쿠버네티스 YAML은 종류가 무엇이든 <code>apiVersion</code>, <code>kind</code>, <code>metadata</code>로 시작하고, 그 아래에 <code>spec</code>이 옵니다. <code>spec</code>은 Deployment, Service처럼 원하는 상태를 적는 종류에만 있고, ConfigMap, Secret처럼 값만 담는 종류는 <code>spec</code> 자리에 <code>data</code>가 옵니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="yaml"><code><span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">apiVersion</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#032563;--shiki-dark:#ADDCFF">apps/v1</span><span style="color:#66707B;--shiki-dark:#BDC4CC">       # 이 리소스가 속한 API 그룹과 버전</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">kind</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#032563;--shiki-dark:#ADDCFF">Deployment</span><span style="color:#66707B;--shiki-dark:#BDC4CC">          # 리소스 종류</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">metadata</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">:                 </span><span style="color:#66707B;--shiki-dark:#BDC4CC"># 이름, 네임스페이스, 라벨 같은 식별 정보</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">  name</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#032563;--shiki-dark:#ADDCFF">web</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">  namespace</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#032563;--shiki-dark:#ADDCFF">web</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">  labels</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">:</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">    app</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#032563;--shiki-dark:#ADDCFF">web</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">spec</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">:                     </span><span style="color:#66707B;--shiki-dark:#BDC4CC"># 원하는 상태. 내용은 kind 마다 다름</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">  replicas</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#023B95;--shiki-dark:#91CBFF">3</span></span></code></pre>
<p><code>apiVersion</code>은 "API 그룹/버전" 형식입니다. 쿠버네티스 API는 객체 종류를 주제별 그룹에 나눠 담습니다. 그래서 Deployment는 <code>apps/v1</code>, Ingress는 <code>networking.k8s.io/v1</code>, HorizontalPodAutoscaler는 <code>autoscaling/v2</code>처럼 그룹 이름이 앞에 붙습니다. Pod, Service, ConfigMap처럼 처음부터 있던 종류는 이름 없는 핵심 그룹에 있어 <code>v1</code>만 적습니다. 어떤 종류가 어느 그룹에 있는지는 외우기보다 <code>kubectl api-resources</code>로 찾는 편이 빠릅니다.</p>
<p><code>metadata.name</code>은 같은 네임스페이스의 같은 종류 안에서 유일해야 합니다.</p>
<p><code>spec</code> 아래에 어떤 필드가 들어가는지는 <code>kind</code>마다 다릅니다. 문서를 뒤지는 대신 <code>kubectl explain</code>으로 바로 볼 수 있습니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="bash"><code><span class="line"><span style="color:#702C00;--shiki-dark:#FFB757">kubectl</span><span style="color:#032563;--shiki-dark:#ADDCFF"> explain</span><span style="color:#032563;--shiki-dark:#ADDCFF"> deployment.spec</span></span>
<span class="line"><span style="color:#702C00;--shiki-dark:#FFB757">kubectl</span><span style="color:#032563;--shiki-dark:#ADDCFF"> explain</span><span style="color:#032563;--shiki-dark:#ADDCFF"> deployment.spec.strategy.rollingUpdate</span></span></code></pre>
<p><code>status</code>는 YAML에 쓰지 않습니다. 컨트롤러와 kubelet이 현재 상태를 적는 자리라서, <code>kubectl get deployment web -o yaml</code>로 꺼내 보면 직접 쓴 적 없는 <code>status.readyReplicas</code> 같은 값이 들어 있습니다. 이 출력을 그대로 저장해 다시 <code>apply</code>하면 <code>resourceVersion</code> 같은 자동 생성 필드 때문에 충돌 에러가 날 수 있습니다. 저장소에는 직접 쓴 <code>spec</code>까지만 둡니다.</p>
<h3 id="이름과-라벨로-이어지는-고리">이름과 라벨로 이어지는 고리<a class="anchor after" aria-hidden="true" tabindex="-1" href="#이름과-라벨로-이어지는-고리"><span class="anchor-icon">#</span></a></h3>
<p>객체가 다른 객체를 가리키는 방식은 이름과 라벨 두 가지입니다. 이 chart에서는 <code>metadata.name</code>과 <code>metadata.labels.app</code>이 둘 다 <code>web</code>으로 렌더링되지만 성격이 다릅니다. 이름은 객체 하나를 가리키는 주소이고, 라벨은 여러 객체를 묶는 분류 꼬리표입니다.</p>
<p>HTML에 비유하면 이름은 <code>id</code>, 라벨은 <code>data-*</code> 속성입니다. <code>getElementById</code>로 하나를 집듯 이름으로는 객체 하나를 가리키고, <code>querySelectorAll('[data-app="web"]')</code>로 여러 개를 모으듯 라벨로는 조건에 맞는 객체를 모두 고릅니다.</p>



































<div class="table-scroll"><table><thead><tr><th></th><th><code>metadata.name</code></th><th><code>metadata.labels.app</code></th></tr></thead><tbody><tr><td>필수 여부</td><td>필수</td><td>선택</td></tr><tr><td>유일성</td><td>같은 네임스페이스의 같은 종류 안에서 유일</td><td>같은 값을 여러 객체가 가질 수 있음</td></tr><tr><td>변경</td><td>만든 뒤 바꿀 수 없음</td><td>언제든 추가, 수정, 삭제 가능</td></tr><tr><td>쓰는 쪽</td><td>특정 객체 하나를 가리킬 때</td><td>조건에 맞는 객체 여러 개를 고를 때</td></tr><tr><td>예</td><td><code>kubectl get deployment web</code></td><td><code>kubectl get all -l app=web</code></td></tr></tbody></table></div>
<p>상대가 하나로 정해져 있으면 이름으로 가리킵니다. Ingress가 트래픽을 보낼 Service, Deployment가 읽을 ConfigMap이 그렇습니다. 상대가 여러 개이거나 개수가 변하면 라벨로 고릅니다. Pod는 Deployment가 <code>web-7d4f9-abc12</code>처럼 임의 이름으로 만들고, 그 이름도 수시로 바뀝니다. 그래서 이름으로 가리킬 수 없고, Service와 Deployment는 <code>selector</code>로 <code>app: web</code> 라벨이 붙은 Pod를 모두 고릅니다.</p>
<p>라벨로 고르는 자리가 여럿이라 Deployment 템플릿 안에는 <code>app: web</code>이 세 번 나옵니다.</p>
<ul>
<li><code>metadata.labels</code>: Deployment 객체 자신의 라벨입니다. 분류에만 쓰이므로 지워도 동작에 영향이 없습니다.</li>
<li><code>spec.selector.matchLabels</code>: 이 Deployment가 관리할 Pod를 고르는 조건입니다.</li>
<li><code>spec.template.metadata.labels</code>: 만들어질 Pod에 붙는 라벨입니다.</li>
</ul>
<p>뒤의 둘은 Pod를 찾는 고리라서 어긋나면 바로 문제가 납니다.</p>
<p>트래픽이 Ingress에서 Pod까지 가려면 Ingress, Service, Deployment가 이 두 방식으로 이어져 있어야 합니다.</p>
<p><img src="/assets/img/posts/etc/k8s_label_links.svg" alt="Ingress, Service, Deployment, Pod 가 이름과 라벨로 이어지는 고리" loading="lazy" decoding="async" width="1080" height="330"></p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="yaml"><code><span class="line"><span style="color:#66707B;--shiki-dark:#BDC4CC"># Ingress → Service: 이름으로</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">backend</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">:</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">  service</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: { </span><span style="color:#024C1A;--shiki-dark:#72F088">name</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#032563;--shiki-dark:#ADDCFF">web</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">, </span><span style="color:#024C1A;--shiki-dark:#72F088">port</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: { </span><span style="color:#024C1A;--shiki-dark:#72F088">number</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#023B95;--shiki-dark:#91CBFF">80</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> } }</span></span>
<span class="line"><span style="color:#023B95;--shiki-dark:#91CBFF">---</span></span>
<span class="line"><span style="color:#66707B;--shiki-dark:#BDC4CC"># Service → Pod: 라벨로</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">kind</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#032563;--shiki-dark:#ADDCFF">Service</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">spec</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">:</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">  selector</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: { </span><span style="color:#024C1A;--shiki-dark:#72F088">app</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#032563;--shiki-dark:#ADDCFF">web</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> }</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">  ports</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">:</span></span>
<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">    - </span><span style="color:#024C1A;--shiki-dark:#72F088">port</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#023B95;--shiki-dark:#91CBFF">80</span><span style="color:#66707B;--shiki-dark:#BDC4CC">            # Service 의 포트</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">      targetPort</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#032563;--shiki-dark:#ADDCFF">http</span><span style="color:#66707B;--shiki-dark:#BDC4CC">    # 컨테이너 포트. containerPort 의 이름 또는 번호</span></span>
<span class="line"><span style="color:#023B95;--shiki-dark:#91CBFF">---</span></span>
<span class="line"><span style="color:#66707B;--shiki-dark:#BDC4CC"># Deployment → Pod: 라벨로</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">kind</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#032563;--shiki-dark:#ADDCFF">Deployment</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">spec</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">:</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">  selector</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">:</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">    matchLabels</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: { </span><span style="color:#024C1A;--shiki-dark:#72F088">app</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#032563;--shiki-dark:#ADDCFF">web</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> }</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">  template</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">:</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">    metadata</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">:</span></span>
<span class="line"><span style="color:#024C1A;--shiki-dark:#72F088">      labels</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: { </span><span style="color:#024C1A;--shiki-dark:#72F088">app</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">: </span><span style="color:#032563;--shiki-dark:#ADDCFF">web</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> }</span></span></code></pre>
<p>Ingress는 Service를 <strong>이름</strong>으로 가리킵니다. 같은 네임스페이스에 그 이름의 Service가 있어야 합니다. Service는 Pod를 <strong>라벨</strong>로 고릅니다. <code>selector</code>에 적은 라벨을 모두 가진 Pod가 EndpointSlice에 들어갑니다. Deployment도 Pod를 라벨로 고릅니다. Pod는 <code>template.metadata.labels</code>에 적힌 라벨을 달고 만들어집니다. 그래서 <code>template.metadata.labels</code>에는 <code>selector.matchLabels</code>의 라벨이 모두 들어 있어야 하고, 빠지면 API 서버가 Deployment 생성을 거부합니다. Deployment의 <code>selector</code>는 한 번 만들면 바꿀 수 없으므로 처음부터 바뀌지 않을 라벨로 정합니다.</p>
<p>이 고리에서 가장 흔한 사고는 Service의 <code>selector</code>와 Pod 라벨이 어긋나는 것입니다. 이때는 아무 에러도 나지 않습니다. Deployment도 Pod도 멀쩡하고 Service도 만들어지는데, EndpointSlice에 Pod IP가 하나도 없어 트래픽만 가지 않습니다. 본문의 chart 템플릿이 이름과 라벨을 모두 <code>.Release.Name</code> 하나에서 렌더링하는 이유가 이것입니다. 값이 같아야 해서가 아니라, 한 곳에서 나오게 해 서로 어긋날 일을 없애기 위해서입니다.</p>
<h3 id="종류별-주요-필드">종류별 주요 필드<a class="anchor after" aria-hidden="true" tabindex="-1" href="#종류별-주요-필드"><span class="anchor-icon">#</span></a></h3>
<p>이 chart의 템플릿에 나오는 필드만 종류별로 모았습니다. 모든 종류에 공통인 <code>apiVersion</code>, <code>kind</code>, <code>metadata</code>는 뺐고, 본문에서 길게 다룬 필드는 짧게 적고 해당 절로 링크했습니다.</p>
<p><strong>Deployment</strong> (<a href="#deployment-%ED%94%84%EB%A1%9C%EB%B8%8C-%EB%A6%AC%EC%86%8C%EC%8A%A4-%EC%A2%85%EB%A3%8C">본문</a>)</p>





























































<div class="table-scroll"><table><thead><tr><th>필드</th><th>역할</th></tr></thead><tbody><tr><td><code>spec.replicas</code></td><td>유지할 Pod 수. HPA를 쓰면 적지 않음</td></tr><tr><td><code>spec.selector.matchLabels</code></td><td>이 Deployment가 관리할 Pod를 고르는 라벨. 만든 뒤 변경 불가</td></tr><tr><td><code>spec.minReadySeconds</code></td><td>새 Pod가 Ready가 된 뒤 이 시간을 버텨야 가용으로 봄</td></tr><tr><td><code>spec.strategy.rollingUpdate</code></td><td><code>maxSurge</code>는 정원 초과 허용 수, <code>maxUnavailable</code>은 정원 미달 허용 수</td></tr><tr><td><code>spec.template.metadata.labels</code></td><td>만들어질 Pod에 붙는 라벨. <code>selector</code>와 일치해야 함</td></tr><tr><td><code>spec.template.metadata.annotations</code></td><td>Pod 어노테이션. <code>checksum/config</code>로 ConfigMap이 바뀌면 Pod 교체</td></tr><tr><td><code>spec.template.spec.terminationGracePeriodSeconds</code></td><td>종료가 시작된 뒤 강제 종료까지 기다리는 시간. <code>preStop</code> 실행 시간도 이 안에 포함</td></tr><tr><td><code>spec.template.spec.containers[].image</code></td><td>컨테이너 이미지. <code>저장소:태그</code></td></tr><tr><td><code>….containers[].ports</code></td><td>컨테이너가 여는 포트. 이름을 붙이면 Service와 프로브가 이름으로 참조</td></tr><tr><td><code>….containers[].env</code>, <code>envFrom</code></td><td>환경 변수. <code>env</code>는 개별 값, <code>envFrom</code>은 ConfigMap이나 Secret 통째로</td></tr><tr><td><code>….containers[].resources</code></td><td>CPU와 메모리의 <code>requests</code>(보장)와 <code>limits</code>(상한)</td></tr><tr><td><code>….containers[].startupProbe</code>, <code>livenessProbe</code>, <code>readinessProbe</code></td><td>기동 완료, 생존, 트래픽 수신 가능 판정</td></tr><tr><td><code>….containers[].lifecycle.preStop</code></td><td>종료 신호를 보내기 전에 실행할 동작</td></tr></tbody></table></div>
<p><strong>Service</strong></p>

























<div class="table-scroll"><table><thead><tr><th>필드</th><th>역할</th></tr></thead><tbody><tr><td><code>spec.type</code></td><td>노출 범위. <code>ClusterIP</code>는 클러스터 안에서만 접근 가능</td></tr><tr><td><code>spec.selector</code></td><td>트래픽을 보낼 Pod를 고르는 라벨</td></tr><tr><td><code>spec.ports[].port</code></td><td>Service가 받는 포트</td></tr><tr><td><code>spec.ports[].targetPort</code></td><td>트래픽을 넘길 컨테이너 포트. 번호 또는 <code>containerPort</code>의 이름</td></tr></tbody></table></div>
<p><strong>Ingress</strong> (<a href="#ingress%EC%99%80-alb-%EC%96%B4%EB%85%B8%ED%85%8C%EC%9D%B4%EC%85%98">본문</a>)</p>

<div class="table-scroll"><table><thead><tr><th>필드</th><th>역할</th></tr></thead><tbody><tr><td><code>spec.scaleTargetRef</code></td><td>Pod 수를 조절할 대상. 보통 Deployment</td></tr><tr><td><code>spec.minReplicas</code>, <code>maxReplicas</code></td><td>Pod 수의 하한과 상한</td></tr><tr><td><code>spec.metrics[]</code></td><td>판단 기준. <code>Resource</code> 타입은 평균 CPU 사용률이 목표치를 넘으면 늘림</td></tr></tbody></table></div>
