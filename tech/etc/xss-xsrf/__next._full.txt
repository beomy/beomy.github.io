<h2 id="xsscross-site-scripting">XSS(Cross-Site Scripting)<a class="anchor after" aria-hidden="true" tabindex="-1" href="#xsscross-site-scripting"><span class="anchor-icon">#</span></a></h2>
<p>사이트 간 스크립팅(XSS)는 웹 애플리케이션에서 많이 나타나는 웹 취약점 공격 중 하나입니다. 웹 사이트 관리자가 아닌 다른 사람이 웹 페이지에 악성 스크립트를 삽입할 수 있는 점을 노린 공격입니다. 주로 게시판에 악성 스크립트가 담긴 글을 올리는 형태로 이루어집니다.</p>
<p>XSS의 공격 유형은 표준으로 정해져 있지는 않지만, 비 지속적인 공격(Non-persistent XSS)과 지속적인 공격(persistent XSS)으로 구분할 수 있습니다.</p>
<h3 id="타겟이-되는-취약점">타겟이 되는 취약점<a class="anchor after" aria-hidden="true" tabindex="-1" href="#타겟이-되는-취약점"><span class="anchor-icon">#</span></a></h3>
<p>사이트 간 스크립팅은 사용자가 특정 웹 사이트를 신뢰한다는 점을 노린 공격입니다. 웹 사이트가 사용자의 입력 값을 제대로 검사하지 않고 사용할 경우를 XSS 공격에 노출됩니다. 공격자가 사용자의 정보(쿠키, 세션 등)를 탈취하거나 비정상적인 기능을 수행하게 할 수 있습니다.</p>
<h3 id="비-지속적non-persistent-공격-방법">비 지속적(Non-persistent) 공격 방법<a class="anchor after" aria-hidden="true" tabindex="-1" href="#비-지속적non-persistent-공격-방법"><span class="anchor-icon">#</span></a></h3>
<p>검색 엔진의 취약점을 노린 공격을 예로 들 수 있습니다. 포탈 사이트에서 문자열을 검색할 경우, 일반적으로 검색 결과 페이지에서 검색한 문자열을 그대로 다시 표시합니다. 검색한 문자열에 스크립트가 포함되어 그 스크립트가 실행 된다면 비 지속적 XSS 공격에 취약점을 가지고 있는 것입니다.</p>
<p>예를 들어 네이버 쇼핑에서 아래 그림과 같이 <code>&#x3C;script>alert('XSS')&#x3C;/script></code>를 검색해 보면 검색 결과 페이지에서 검색 문자열에 포함된 스크립트가 화면에 문자열로 나타나는 것을 볼 수 있습니다. 스크립트가 실행되지 않고 화면에 노출되기 때문에 네이버 쇼핑은 비 지속적 XSS 공격에 대응이 되어 있는 것으로 볼 수 있습니다.</p>
<p><img src="/assets/img/posts/etc/naver_non_persistent_xss.png" alt="네이버 XSS 취약점 확인" loading="lazy" decoding="async" width="1936" height="1104" srcset="/assets/img/posts/etc/nextImageExportOptimizer/naver_non_persistent_xss-opt-640.WEBP 640w, /assets/img/posts/etc/nextImageExportOptimizer/naver_non_persistent_xss-opt-1080.WEBP 1080w, /assets/img/posts/etc/nextImageExportOptimizer/naver_non_persistent_xss-opt-1920.WEBP 1920w" sizes="(max-width: 640px) 100vw, 1000px"></p>
<p>공격자는 웹 사이트에서 취약점을 찾아 낸 후, (네이버 쇼핑은 취약점이 없지만) 사용자에게 <code>https://search.shopping.naver.com/search/all?query=&#x3C;script>alert('XSS')&#x3C;/script></code>(이 링크는 <code>&#x3C;script>alert('XSS')&#x3C;/script></code> 검색 결과와 동일합니다.)와 같이 쿼리에 스크립트가 포함된 링크에 접속을 유도합니다. 사용자가 페이지에 접속하여 스크립트가 실행 된다면 비 지속적 XSS 공격이 성공하게 됩니다.</p>
<p>비 지속적 XSS는 검색 문자열을 그대로 화면에 다시 표시되는 점을 노린 공격이기 때문에 반사(Reflected) XSS라고도 불립니다.</p>
<h3 id="지속적persistent-공격-방법">지속적(Persistent) 공격 방법<a class="anchor after" aria-hidden="true" tabindex="-1" href="#지속적persistent-공격-방법"><span class="anchor-icon">#</span></a></h3>
<p>지속적 XSS 공격은 비 지속적 XSS 공격보다 더 치명적인 공격 방법입니다. 게시판을 예로 들면, 공격자가 게시판 글쓰기 통해서 스크립트를 포함한 게시 글을 작성한 후 서버에 저장 합니다. 다른 사용자가 그 게시 글을 읽을 때 게시 글에 포함된 스크립트가 실행되면서 XSS 공격이 성공하게 됩니다. 게시 글에 그 글을 읽는 사용자의 이름과 이메일 등의 개인 정보를 공격자에게 전송하는 스크립트가 포함되어 있다고 하면, 게시 글을 읽는 모든 사람의 개인 정보가 유출되게 됩니다.</p>

<p><code>&#x3C;script></code> 태그는 화면에 노출되지 않기 때문에 사용자는 자신의 개인 정보가 유출되는지 모른 체 피해를 입게 됩니다. 한 번 스크립트가 실행 되는 게시 글을 올릴 수 있다면, 그 게시 글이 삭제 될 때까지 지속적으로 사용자들에게 피해를 줄 수 있기 때문에 지속적 XSS 공격이라고 이야기 합니다.</p>
<h3 id="대응-방법">대응 방법<a class="anchor after" aria-hidden="true" tabindex="-1" href="#대응-방법"><span class="anchor-icon">#</span></a></h3>
<p>XSS 공격을 막기 위해서는 페이지에서 공격자가 입력한 스크립트를 실행하지 못하게 해야 합니다. 스크립트를 실행하지 못하게 하려면, 스크립트 입력을 막거나 브라우저가 스크립트를 실행하지 못하게 스크립트 값을 변경해야 합니다. XSS 공격은 보통 프론트엔드 측에서 대응해 줍니다.</p>
<h4 id="입력-값-제한">입력 값 제한<a class="anchor after" aria-hidden="true" tabindex="-1" href="#입력-값-제한"><span class="anchor-icon">#</span></a></h4>
<p>스크립트를 입력하지 못하게 하는 방법으로 XSS 공격을 막을 수 있습니다. 하지만 <code>&#x3C;script></code> 태그 뿐만 아니라 아래 코드와 같이 이벤트 핸들러를 사용하는 방법으로 스크립트를 실행 할 수 있습니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="html"><code><span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">&#x3C;</span><span style="color:#024C1A;--shiki-dark:#72F088">img</span><span style="color:#023B95;--shiki-dark:#91CBFF"> src</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">=</span><span style="color:#032563;--shiki-dark:#ADDCFF">"#"</span><span style="color:#023B95;--shiki-dark:#91CBFF"> onerror</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">=</span><span style="color:#032563;--shiki-dark:#ADDCFF">"</span><span style="color:#622CBC;--shiki-dark:#DBB7FF">alert</span><span style="color:#032563;--shiki-dark:#ADDCFF">('XSS')"</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">></span></span></code></pre>
<p>모든 케이스에 대응해서 입력 값을 제한하는 것은 쉽지 않기 때문에 입력 값 치환이 XSS 공격을 방어하는데 더 효과적입니다.</p>
<h4 id="입력-값-치환">입력 값 치환<a class="anchor after" aria-hidden="true" tabindex="-1" href="#입력-값-치환"><span class="anchor-icon">#</span></a></h4>
<p>XSS 공격은 HTML 태그를 사용하기 때문에 HTML 태그에 사용되는 <code>&#x3C;</code>와 <code>></code> 문자열을 인코딩한 <code>&#x26;lt</code>, <code>&#x26;gt</code>를 서버에 저장하거나 페이지를 그릴 때 인코딩한 값으로 화면에 그리는 방법입니다. 이렇게 인코딩이 되면 브라우저는 일반 문자열로 인식하여 페이지에 <code>&#x3C;script>&#x3C;/script></code>로 노출되어 스크립트가 실행되지 않습니다.</p>
<h2 id="xsrfcrose-site-request-forgery">XSRF(Crose-Site Request Forgery)<a class="anchor after" aria-hidden="true" tabindex="-1" href="#xsrfcrose-site-request-forgery"><span class="anchor-icon">#</span></a></h2>
<p>사이트 간 요청 위조(XSRF 또는 CSRF라고 합니다.)는 사용자가 자신의 의지와 무관하게 공격자가 의도한 행위(수정, 삭제, 등록 등)를 특정 웹사이트에 요청하게 하는 공격입니다.</p>
<h3 id="타겟이-되는-취약점-1">타겟이 되는 취약점<a class="anchor after" aria-hidden="true" tabindex="-1" href="#타겟이-되는-취약점-1"><span class="anchor-icon">#</span></a></h3>
<p>사이트 간 요청 위조는 특정 웹 사이트가 사용자의 웹 브라우저를 신뢰하는 상태를 노린 공격입니다. 사용자가 웹사이트에 로그인한 상태에서 사이트간 요청 위조 공격 코드가 삽입된 페이지를 열면, 공격 대상이 되는 웹사이트는 위조된 공격 명령이 믿을 수 있는 사용자로부터 발송된 것으로 판단하게 되어 공격에 노출됩니다.</p>
<h3 id="공격-방법">공격 방법<a class="anchor after" aria-hidden="true" tabindex="-1" href="#공격-방법"><span class="anchor-icon">#</span></a></h3>
<p>XSRF 공격 과정은 아래와 같습니다.</p>
<p><img src="/assets/img/posts/etc/xsrf_flow.png" alt="XSRF 공격 순서" loading="lazy" decoding="async" width="764" height="618" srcset="/assets/img/posts/etc/nextImageExportOptimizer/xsrf_flow-opt-640.WEBP 640w, /assets/img/posts/etc/nextImageExportOptimizer/xsrf_flow-opt-1080.WEBP 1080w" sizes="(max-width: 640px) 100vw, 1000px"></p>
<ol>
<li>이용자는 웹사이트에 로그인하여 정상적인 쿠키를 발급받는다.</li>
<li>공격자는 링크(예를 들어, <code>http://www.geocities.com/attacker</code>와 같은)를 이메일이나 게시판 등의 경로를 통해 이용자에게 전달한다.</li>
<li>위의 링크의 HTML 페이지는 <code>&#x3C;img src= "https://travel.service.com/travel_update?.src=Korea&#x26;.dst=Hell"></code> 같은 이미지 태그를 가집니다. 이 링크는 출발지와 도착지를 등록하기 위한 링크인데, 그 중 도착지 정보를 변조한 링크입니다.</li>
<li>이용자가 공격용 페이지를 열면, 브라우저는 이미지 파일을 받아오기 위해 공격용 URL을 실행합니다.</li>
<li>이용자의 승인이나 인지 없이 출발지와 도착지가 등록되어 공격이 완료됩니다.</li>
</ol>
<p>해당 서비스는 단순히 쿠키를 통해 본인확인이 이루어지기 때문에 XSRF 공격이 가능하게 됩니다.</p>

<p>프론트엔드 페이지는 로그인 페이지 입니다. ID와 Password를 입력 받아 <code>users/login</code> API를 호출합니다.  <code>users/login</code>에서는 쿠키에 <code>login-token</code>이라는 이름으로 토큰을 설정합니다. <code>user/change</code>에서는 <code>login-token</code>이 <code>test</code>일 경우 회원의 비밀 번호를 변경합니다.</p>
<p>아래 코드는 로그인 후 공격자가 사용자에게 접근을 유도하여, 사용자가 접근하게 되는 페이지입니다.</p>

<p><code>&#x3C;img></code> 태그는 Get 방식으로 src로 선언된 주소를 호출하기 때문에 서버의 <code>user/change</code> API가 호출됩니다. 쿠키를 통해서만 인증이 이루어지기 때문에 아래 그림과 같이 XSRF 공격이 성공하게 됩니다.</p>
<p><img src="/assets/img/posts/etc/xsrf_phising.gif" alt="XSRF 공격 시도" loading="lazy" decoding="async" width="1186" height="544" srcset="/assets/img/posts/etc/nextImageExportOptimizer/xsrf_phising-opt-640.WEBP 640w, /assets/img/posts/etc/nextImageExportOptimizer/xsrf_phising-opt-1080.WEBP 1080w, /assets/img/posts/etc/nextImageExportOptimizer/xsrf_phising-opt-1920.WEBP 1920w" sizes="(max-width: 640px) 100vw, 1000px"></p>
<h3 id="대응-방법-1">대응 방법<a class="anchor after" aria-hidden="true" tabindex="-1" href="#대응-방법-1"><span class="anchor-icon">#</span></a></h3>
<p>XSRF 공격을 막기 위해서는 피싱 페이지에서 호출한 백엔드 API가 실패 되도록 해야 합니다. 백엔드 API가 정상적으로 응답해야 하는지 판단해야 하기 때문에 XSRF 공격은 XSS와는 다르게 보통 백엔드 측에서 대응해 줘야 합니다.</p>
<h4 id="쿠키의-samesite-사용">쿠키의 SameSite 사용<a class="anchor after" aria-hidden="true" tabindex="-1" href="#쿠키의-samesite-사용"><span class="anchor-icon">#</span></a></h4>
<p>HTTP 응답 헤더의 Set-Cookie에 SameSite 속성으로 <code>None</code>, <code>Lax</code>, <code>Strict</code> 3종류가 올 수 있습니다. SameSite 속성 값으로 <code>Lax</code>, <code>Strict</code>를 사용하면 쿠키를 동일한 사이트에서만 전달 할 수 있게 할 수 있습니다.</p>
<p>SameSite 속성은 아래 그림과 같이 <a href="https://caniuse.com/?search=samesite">Can I Use</a>에서 확인해 보면, IE10와 같은 구형 브라우저에서는 SameSite 속성을 지원하지 않기 때문에 SameSite 속성만을 사용하여 XSRF 공격을 막는 것에는 한계가 있습니다.</p>
<p><img src="/assets/img/posts/etc/can_i_use_samesite.png" alt="SameSite 사용 가능 브라우저" loading="lazy" decoding="async" width="2724" height="998" srcset="/assets/img/posts/etc/nextImageExportOptimizer/can_i_use_samesite-opt-640.WEBP 640w, /assets/img/posts/etc/nextImageExportOptimizer/can_i_use_samesite-opt-1080.WEBP 1080w, /assets/img/posts/etc/nextImageExportOptimizer/can_i_use_samesite-opt-1920.WEBP 1920w" sizes="(max-width: 640px) 100vw, 1000px"></p>
<h4 id="referer-체크">Referer 체크<a class="anchor after" aria-hidden="true" tabindex="-1" href="#referer-체크"><span class="anchor-icon">#</span></a></h4>
<p>Request 헤더의 Referer를 확인하여 유효한 사이트에서 API를 호출하는지 확인하는 방법입니다.</p>
<p><a href="https://beomy.github.io/tech/browser/cors/#simple-request">Same-Origin Policy(SOP)</a>를 지키면 XSRF 공격을 방어할 수 있습니다. 하지만 다른 출처의 자원을 사용해야 하는 경우가 있기 때문에 <a href="https://beomy.github.io/tech/browser/cors/">CORS</a>를 허용해 주는 경우가 많습니다. CORS를 위해 <code>Access-Control-Allow-Origin: *</code>를 사용하여 모든 출처를 허용하게 되면 XSRF 공격에 취약 해지기 때문에 <code>Access-Controll-Allow-Origin: *</code> 사용을 피하고 유효한 출처만 허용하는 것이 좋습니다.</p>
<h4 id="security-token-사용">Security Token 사용<a class="anchor after" aria-hidden="true" tabindex="-1" href="#security-token-사용"><span class="anchor-icon">#</span></a></h4>
<p>Security Token을 사용 한다는 것은 사용자 인증 절차를 좀 더 복잡하게 만들어서 XSRF 공격을 막겠다는 의미입니다.</p>
<p>임의의 토큰을 발급하여 서버의 세션에 토큰을 저장하고, 그 토큰을 프론트엔드로 전달합니다. 프론트엔드에서는 API를 호출할 때 전달 받은 토큰을 함께 전달하고, 서버에서 세션에 저장된 토큰과 프론트엔트에서 전달 받은 토큰을 비교하여 동일할 경우 API를 실행하는 방식입니다. 피싱 사이트에서 API를 호출한 경우, 피싱 사이트에는 토큰이 존재하지 않기 때문에 API 호출이 실패하게 됩니다.</p>
<h2 id="부록">부록<a class="anchor after" aria-hidden="true" tabindex="-1" href="#부록"><span class="anchor-icon">#</span></a></h2>
<h3 id="samesite-cookie">SameSite Cookie<a class="anchor after" aria-hidden="true" tabindex="-1" href="#samesite-cookie"><span class="anchor-icon">#</span></a></h3>
<p>HTTP 응답 헤더의 Set-Cookie에 SameSite 속성을 사용하면 동일한 사이트에서만 쿠키를 전달 할 수 있게 할 수 있습니다. SameSite 속성에 설정할 수 있는 값은 아래 목록과 같은 <code>None</code>, <code>Lax</code>, <code>Strict</code> 3종류입니다.</p>
<ul>
<li><code>SameSite=None</code>: SameSite 속성이 등장 하기 전에 동작하던 쿠키 방식입니다. <code>None</code>으로 설정된 쿠키는 크로스 사이트 요청에서도 쿠키가 전송됩니다.</li>
<li><code>SameSite=Lax</code>: 원래의 사이트에서 링크 이동을 통해 이동 된 경우에만 쿠키를 전달합니다. 즉 <code>&#x3C;a></code> 태그를 통한 링크 이동시에 이동한 사이트로 쿠키가 전송됩니다. <code>&#x3C;a href></code>, <code>&#x3C;link href></code>, <code>&#x3C;form method=get></code> 사용시 쿠키가 전달됩니다.</li>
<li><code>SameSite=Strict</code>: <code>Lax</code>에서 허용하는 예외 상황에서도 쿠키를 전송하지 않는 가장 엄격한 형태입니다.</li>
</ul>
<p>아래 그림과 같이 <a href="https://caniuse.com/mdn-http_headers_set-cookie_samesite_lax_default">Can I Use</a>를 확인하면, 크롬 80버전부터 새로운 쿠키 정책이 적용되어 Cookie의 SameSite 속성의 기본값이 Lax로 변경 되었습니다. SameSite 속성이 정의 되어 있지 않더라도 <code>Lax</code>로 설정 된 것으로 인식하고 동작합니다.</p>
<p><img src="/assets/img/posts/etc/can_i_use_samesite_default.png" alt="SameSite 기본 값 허용 브라우저" loading="lazy" decoding="async" width="2730" height="782" srcset="/assets/img/posts/etc/nextImageExportOptimizer/can_i_use_samesite_default-opt-640.WEBP 640w, /assets/img/posts/etc/nextImageExportOptimizer/can_i_use_samesite_default-opt-1080.WEBP 1080w, /assets/img/posts/etc/nextImageExportOptimizer/can_i_use_samesite_default-opt-1920.WEBP 1920w" sizes="(max-width: 640px) 100vw, 1000px"></p>
<p>크롬에서 <code>SameSite=None</code>을 사용하려면 아래 코드와 같이 Secure과 함께 사용되어야 합니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="text"><code><span class="line"><span>Set-Cookie: login-token=test; SameSite=None; Secure</span></span></code></pre>
<p><code>Secure</code>를 사용하면 HTTPS 프로토콜을 사용할 때만 쿠키를 전달하게 됩니다. HTTP 프로토콜을 사용 할 때는 쿠키를 전달하지 않습니다.</p>
