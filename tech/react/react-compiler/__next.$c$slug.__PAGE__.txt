<p><strong>TL;DR</strong></p>
<ul>
<li>React Compiler는 Babel 플러그인 형태의 빌드 도구입니다. 컴포넌트와 훅 안의 값, 함수, JSX를 분석해 <code>useMemo</code>, <code>useCallback</code>, <code>memo</code>와 같은 효과를 내는 캐시 코드를 자동으로 끼워 넣습니다.</li>
<li>코드를 고칠 필요는 없지만, <a href="https://react.dev/reference/rules">React 규칙</a>을 지키는 코드여야 합니다. 규칙을 어긴 컴포넌트는 에러를 내지 않고 조용히 컴파일을 건너뜁니다.</li>
<li>메모이제이션의 단위는 컴포넌트가 아니라 컴포넌트 안의 값입니다. <code>count</code>가 바뀌어도 <code>count</code>와 무관한 JSX는 이전 엘리먼트를 그대로 재사용하기 때문에, 자식 컴포넌트를 <code>memo</code>로 감싸지 않아도 리렌더링이 건너뛰어집니다.</li>
<li>효과는 첫 화면을 그릴 때가 아니라 클릭이나 입력으로 화면이 갱신될 때 나타납니다. 부모의 상태가 바뀔 때 무관한 자식까지 함께 리렌더링되던 앱일수록 효과가 크고, 외부 라이브러리가 렌더링마다 새 객체를 넘기는 곳은 컴파일러도 잡지 못합니다.</li>
<li>2025년 10월 1.0 정식 버전이 나왔고, React 17 이상에서 쓸 수 있습니다. Next.js는 <code>reactCompiler: true</code> 한 줄로 켤 수 있습니다.</li>
<li><code>"use no memo"</code> 지시어로 컴포넌트 하나를 빼거나, <code>compilationMode: 'annotation'</code>으로 <code>"use memo"</code>를 붙인 컴포넌트만 컴파일하는 식으로 점진적으로 도입할 수 있습니다.</li>
</ul>
</blockquote>
<p>React는 상태가 바뀌면 그 컴포넌트와 하위 컴포넌트 전체를 다시 실행합니다. 이 단순한 모델이 React를 배우기 쉽게 만들었지만, 앱이 커지면 바뀐 것이 없는 자식까지 매번 실행되는 비용이 문제가 됩니다. 그래서 <code>useMemo</code>, <code>useCallback</code>, <code>memo</code>로 "이 값은 저 값이 바뀔 때만 다시 계산해"라고 React에 알려 주는 수동 메모이제이션을 해 왔습니다.</p>
<p>React Compiler(개발 당시 이름은 React Forget)는 이 작업을 사람 대신 빌드 도구가 하도록 만든 것입니다. 2024년 React Conf에서 오픈 소스로 공개되고, 2025년 10월 7일 1.0 정식 버전이 나왔습니다. 이번 포스트에서는 컴파일러가 코드를 어떻게 바꾸는지, 어떤 코드에서 컴파일을 포기하는지, 그리고 프로젝트에 어떻게 적용하는지 살펴보도록 하겠습니다.</p>

<p>이 코드에는 세 가지 문제가 있습니다.</p>
<ol>
<li><strong>번거롭고 읽기 어렵습니다.</strong><br>
핵심 로직은 <code>friends.filter(...)</code> 한 줄인데, 메모이제이션을 위해 <code>useMemo</code>와 의존성 배열이 둘러싸고 있습니다. 코드의 절반이 React를 위한 힌트입니다.</li>
<li><strong>실수하기 쉽습니다.</strong><br>
의존성 배열에서 값을 빠뜨리면 오래된 값을 보여 주는 버그가 생기고, 불필요한 값을 넣으면 메모이제이션이 무의미해집니다. ESLint의 <code>exhaustive-deps</code> 규칙이 도와주지만, 객체와 함수 참조가 얽히면 규칙만으로는 부족합니다.</li>
<li><strong>한 곳만 빠져도 전체가 무너집니다.</strong><br>
<code>MessageButton</code>은 props가 없는데도 <code>FriendList</code>가 리렌더링될 때마다 같이 실행됩니다. <code>memo</code>로 감싸야 건너뛸 수 있습니다. 그리고 <code>memo</code>로 감싼 컴포넌트에 <code>onClick={() => handleClick(item)}</code>처럼 인라인 함수를 넘기면 매번 새 함수라 <code>memo</code>가 무력화됩니다. 메모이제이션은 부모부터 자식까지 빈틈없이 이어져야 효과가 있는데, 이를 사람이 유지보수하기는 쉽지 않습니다.</li>
</ol>
<p>컴파일러를 사용하면 이 세 가지를 모두 해결할 수 있습니다. 컴파일러가 빠짐없이 정확한 메모이제이션을 넣기 때문에 사람은 더 이상 메모이제이션을 신경 쓰지 않아도 됩니다.</p>

<h3 id="캐시-배열-만들기">캐시 배열($) 만들기<a class="anchor after" aria-hidden="true" tabindex="-1" href="#캐시-배열-만들기"><span class="anchor-icon">#</span></a></h3>
<p><code>_c(13)</code>은 <code>react/compiler-runtime</code>이 제공하는 함수로, 칸이 13개인 캐시 배열을 만듭니다. 컴파일된 코드 첫 줄의 <code>const $ = _c(13)</code>에서 보듯 이 배열은 <code>$</code>라는 변수에 담기고, 이후 <code>$[0]</code>, <code>$[1]</code>처럼 칸 번호로 접근합니다. 컴파일러가 이 컴포넌트에서 기억해 둘 값의 개수를 세어 13이라는 숫자를 정합니다. 이 배열은 <code>useState</code>의 상태처럼 컴포넌트 인스턴스마다 하나씩 생기고, 다시 렌더링될 때 같은 배열을 그대로 돌려받습니다(실제로 훅으로 구현되어 있습니다). 처음에는 모든 칸이 <code>Symbol.for('react.memo_cache_sentinel')</code>이라는 "아직 계산하지 않았음" 표시로 채워져 있어서, 컴파일된 코드는 이 표시를 보고 첫 렌더링인지 판단합니다.</p>
<h3 id="reactive-scope로-묶기">Reactive Scope로 묶기<a class="anchor after" aria-hidden="true" tabindex="-1" href="#reactive-scope로-묶기"><span class="anchor-icon">#</span></a></h3>
<p><code>if ($[0] !== items) { ... } else { ... }</code> 블록 하나가 메모이제이션의 단위입니다. 컴파일러는 이것을 Reactive Scope라고 부릅니다. 각 블록은 다음 구조로 되어 있습니다.</p>
<ul>
<li><strong>의존성 칸</strong>: <code>$[0]</code>에 지난번 렌더링 때의 <code>items</code>를 저장합니다.</li>
<li><strong>출력 칸</strong>: <code>$[1]</code>에 <code>sum(items)</code>의 결과를 저장합니다.</li>
<li><strong>비교</strong>: 이번 렌더링의 <code>items</code>가 <code>$[0]</code>과 다르면(<code>!==</code>) 다시 계산하고 두 칸을 갱신합니다. 같으면 <code>$[1]</code>을 꺼내 씁니다.</li>
</ul>
<p><code>useMemo(() => sum(items), [items])</code>를 손으로 풀어 쓴 것과 같습니다. 차이는 사람이 의존성 배열을 적는 대신 컴파일러가 코드를 분석해 <code>items</code>를 찾아냈다는 점입니다.</p>
<p><img src="/assets/img/posts/react/react_compiler_memo_cache.svg" alt="Reactive Scope와 캐시 배열의 대응" loading="lazy" decoding="async" width="960" height="400"></p>
<p><code>onClick</code>도 같은 방식으로 <code>count</code>에 의존하는 Reactive Scope가 됩니다. <code>useCallback(() => setCount(count + 1), [count])</code>와 같습니다. <code>&#x3C;Child /></code>는 아무 값에도 의존하지 않아 비교할 의존성 칸이 없습니다. 캐시 칸에 "아직 계산하지 않았음" 표시(sentinel)가 남아 있는지만 확인해서, 첫 렌더링에 한 번 만든 뒤로는 계속 재사용합니다.</p>
<h4 id="jsx-엘리먼트도-묶기">JSX 엘리먼트도 묶기<a class="anchor after" aria-hidden="true" tabindex="-1" href="#jsx-엘리먼트도-묶기"><span class="anchor-icon">#</span></a></h4>

<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">  t6 </span><span style="color:#A0111F;--shiki-dark:#FF9492">=</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> $[</span><span style="color:#023B95;--shiki-dark:#91CBFF">12</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">]</span></span>

<p><code>&#x3C;div></code>의 자식은 <code>t3</code>, <code>t4</code>, <code>t5</code> 세 엘리먼트입니다. 이 셋은 이미 각각 메모이제이션되어 있어서 입력이 바뀌지 않으면 이전과 같은 객체입니다. 그래서 <code>&#x3C;div></code>를 새로 만들지 말지는 <code>total</code>이나 <code>count</code> 같은 원래 값을 다시 볼 필요 없이, 자식 엘리먼트 <code>t3</code>, <code>t4</code>가 이전과 같은 객체인지만 보면 됩니다. <code>t5</code>는 절대 바뀌지 않아 비교 조건에서 아예 빠져 있습니다.</p>
<p>결과적으로 의존 관계가 사슬처럼 이어집니다.</p>
<ul>
<li><code>count</code>가 바뀌면 <code>onClick</code>과 <code>t4</code>가 새로 만들어지고, <code>t4</code>가 바뀌었으니 <code>&#x3C;div></code>도 새로 만들어집니다. 하지만 그 안의 <code>t3</code>, <code>t5</code>는 이전 객체 그대로입니다.</li>
<li><code>items</code>가 바뀌면 <code>total</code>과 <code>t3</code>가 새로 만들어지고, <code>&#x3C;div></code>도 새로 만들어집니다. <code>t4</code>, <code>t5</code>는 그대로입니다.</li>
<li>둘 다 바뀌지 않았으면 <code>t3</code>, <code>t4</code>가 그대로라 <code>&#x3C;div></code>도 캐시에서 꺼냅니다. 컴포넌트가 지난번과 완전히 같은 엘리먼트 트리를 반환하는 것입니다.</li>
</ul>
<p>컴파일러는 이렇게 메모이제이션을 바깥 엘리먼트까지 겹겹이 쌓아서, 바뀐 가지만 새로 만들고 나머지 가지는 이전 객체를 그대로 끼워 넣습니다.</p>
<p>React는 컴포넌트가 돌려준 자식 엘리먼트가 이전 렌더링과 같은 객체이면, 그 자식 컴포넌트를 다시 실행하지 않고 지난 결과를 그대로 씁니다. 위 사슬에서 <code>t5</code>(<code>&#x3C;Child /></code>)는 한 번 만들어진 뒤 항상 같은 객체라, <code>Child</code>는 <code>memo</code>로 감싸지 않아도 다시 실행되지 않습니다. <code>memo</code>가 하던 일을 컴파일러가 부모 쪽에서 대신해 주는 셈입니다.</p>
<p><img src="/assets/img/posts/react/react_compiler_rerender.svg" alt="컴파일 전후의 리렌더링 범위" loading="lazy" decoding="async" width="960" height="380"></p>
<h4 id="수동-메모이제이션보다-촘촘하게">수동 메모이제이션보다 촘촘하게<a class="anchor after" aria-hidden="true" tabindex="-1" href="#수동-메모이제이션보다-촘촘하게"><span class="anchor-icon">#</span></a></h4>
<p>수동 메모이제이션은 사람이 고른 지점에서만 동작합니다. <code>useMemo</code>와 <code>useCallback</code>은 감싼 값 하나를, <code>memo</code>는 감싼 컴포넌트의 리렌더링 여부를 메모이제이션하고, 감싸지 않은 나머지는 매번 다시 계산됩니다. 컴파일러는 컴포넌트 안의 모든 값과 모든 JSX 엘리먼트에 대해 각각 "다시 계산하느냐 마느냐"를 결정합니다. React 팀은 이것을 세밀한 반응성(Fine-grained Reactivity)이라고 부릅니다.</p>
<p>앞에서 본 인라인 함수 문제가 어떻게 해결되는지 아래 코드로 살펴보겠습니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="tsx"><code><span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">const</span><span style="color:#622CBC;--shiki-dark:#DBB7FF"> List</span><span style="color:#A0111F;--shiki-dark:#FF9492"> =</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> ({ </span><span style="color:#702C00;--shiki-dark:#FFB757">items</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">, </span><span style="color:#702C00;--shiki-dark:#FFB757">onSelect</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> }) </span><span style="color:#A0111F;--shiki-dark:#FF9492">=></span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> (</span></span>

<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">)</span></span></code></pre>
<p>컴파일 전에는 <code>List</code>가 리렌더링될 때마다 <code>items.map(...)</code>이 다시 실행되고, 행마다 <code>() => onSelect(item)</code> 화살표 함수가 새로 만들어집니다. <code>Item</code>을 <code>memo</code>로 감싸 두어도 <code>memo</code>는 props를 <code>Object.is</code>로 비교하기 때문에, 매번 다른 <code>onClick</code> 함수를 보고 props가 바뀌었다고 판단해 <code>Item</code>을 전부 다시 렌더링합니다. 이를 막으려면 행마다 <code>onClick</code> 함수가 렌더링 사이에 같은 참조를 유지하도록 해야 하는데, 반복문 안에서는 <code>useCallback</code>을 쓸 수 없어 컴포넌트 구조를 바꿔야 했습니다.</p>
<p>컴파일러를 쓰면 구조를 바꾸지 않아도 됩니다. 컴파일 후 <code>items.map(...)</code> 부분은 아래처럼 바뀝니다.</p>

<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">}</span></span></code></pre>
<p><code>map</code>의 결과 전체가 <code>items</code>와 <code>onSelect</code>에만 의존하는 Reactive Scope로 묶였습니다. 부모의 무관한 상태 변경으로 <code>List</code>가 리렌더링되더라도 <code>items</code>와 <code>onSelect</code>가 그대로면 <code>map</code>을 실행하지 않고 지난번에 만든 <code>&#x3C;Item></code> 엘리먼트 배열을 캐시에서 꺼냅니다. <code>&#x3C;Item></code> 엘리먼트가 이전 렌더링과 같은 객체라 React는 <code>Item</code>을 다시 실행하지 않습니다. <code>Item</code>을 <code>memo</code>로 감싸거나 <code>onClick</code>을 <code>useCallback</code>으로 고정하지 않아도 같은 결과가 됩니다.</p>
<p>다만 <code>items</code>가 바뀌면 <code>map</code>이 다시 실행되고 화살표 함수도 전부 새로 만들어져 모든 <code>Item</code>이 리렌더링됩니다. 컴파일러가 하는 일은 행마다 <code>onClick</code> 참조를 유지하는 것이 아니라, <code>items</code>와 <code>onSelect</code>가 그대로일 때 리스트 전체를 통째로 건너뛰는 것입니다. 한 행만 바뀌었을 때 그 행만 리렌더링하고 싶다면 컴파일러만으로는 부족하고, 데이터 구조나 컴포넌트 분리를 직접 신경 써야 합니다.</p>
<h3 id="컴포넌트-밖으로-끌어올리기">컴포넌트 밖으로 끌어올리기<a class="anchor after" aria-hidden="true" tabindex="-1" href="#컴포넌트-밖으로-끌어올리기"><span class="anchor-icon">#</span></a></h3>
<p>앞의 <code>FriendList</code>를 컴파일하면 <code>visible.map((f) => &#x3C;li key={f.id}>{f.name}&#x3C;/li>)</code>의 콜백이 컴포넌트 밖으로 빠져나갑니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="tsx"><code><span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">t4 </span><span style="color:#A0111F;--shiki-dark:#FF9492">=</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> visible.</span><span style="color:#622CBC;--shiki-dark:#DBB7FF">map</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">(_temp)</span></span>

<span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">  return</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> &#x3C;</span><span style="color:#024C1A;--shiki-dark:#72F088">li</span><span style="color:#023B95;--shiki-dark:#91CBFF"> key</span><span style="color:#A0111F;--shiki-dark:#FF9492">={</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">f_0.id</span><span style="color:#A0111F;--shiki-dark:#FF9492">}</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">></span><span style="color:#A0111F;--shiki-dark:#FF9492">{</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">f_0.name</span><span style="color:#A0111F;--shiki-dark:#FF9492">}</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">&#x3C;/</span><span style="color:#024C1A;--shiki-dark:#72F088">li</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">></span></span>
<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">}</span></span></code></pre>
<p>콜백이 컴포넌트의 어떤 값도 참조하지 않는다면 매 렌더링마다 새로 만들 이유가 없습니다. 컴파일러는 이런 함수를 모듈 수준으로 끌어올려 아예 한 번만 만듭니다.</p>
<h2 id="컴파일-과정">컴파일 과정<a class="anchor after" aria-hidden="true" tabindex="-1" href="#컴파일-과정"><span class="anchor-icon">#</span></a></h2>
<p>컴파일러는 Babel 플러그인이지만, 핵심 로직은 Babel과 분리된 별도의 컴파일러입니다. Babel은 소스를 AST로 파싱해 넘겨 주는 입구이고, 컴파일러는 AST를 자체 중간 표현인 HIR(High-level Intermediate Representation)로 바꿔 분석합니다.</p>
<blockquote>
<ul>
<li><strong>AST(Abstract Syntax Tree)</strong>: 소스 코드를 트리 구조로 표현한 것입니다. <code>a + b</code>라면 <code>+</code> 노드 아래에 <code>a</code>와 <code>b</code>가 자식으로 달리는 식입니다. Babel, ESLint, Prettier가 모두 이 형태로 코드를 다룹니다.</li>
<li><strong>중간 표현(IR, Intermediate Representation)</strong>: 컴파일러가 분석하기 쉽도록 소스를 바꿔 놓은 내부 형식입니다. AST는 사람이 쓴 문법 그대로라 "이 값이 어디서 바뀌는가" 같은 질문에 답하기 불편해서, 대부분의 컴파일러는 자기만의 IR을 따로 둡니다.</li>
<li><strong>HIR(High-level Intermediate Representation)</strong>: React Compiler의 IR입니다. 함수 본문을 분기가 없는 코드 블록 단위로 쪼개고, 각 값에 한 번만 이름을 붙여서 값의 생성, 변경, 의존 관계를 추적하기 쉽게 만든 형태입니다.</li>
</ul>
</blockquote>
<p><img src="/assets/img/posts/react/react_compiler_pipeline.svg" alt="컴파일 과정" loading="lazy" decoding="async" width="960" height="410"></p>
<ol>
<li>
<p><strong>컴포넌트와 훅 찾기</strong>: 기본 설정(<code>compilationMode: 'infer'</code>)에서는 대문자로 시작하는 이름의 함수를 컴포넌트로, <code>use</code>로 시작하는 이름의 함수를 훅으로 보되, 그중 JSX를 만들거나 다른 훅을 호출하는 함수만 컴파일합니다.</p>
</li>
<li>
<p><strong>분석</strong>: HIR 위에서 각 값이 어디서 만들어지고(①) 어디서 변경되는지(②), 그리고 <code>const b = a</code>처럼 두 이름이 같은 객체를 가리키는 별칭 관계(③)를 추적합니다. 이 분석 결과로 "이 값은 저 값에 의존한다"는 그래프가 만들어집니다.</p>
<p>이 분석이 왜 필요한지 예로 보겠습니다. <code>alias</code>는 <code>list</code>와 같은 배열을 가리키기 때문에, <code>alias.push</code>도 <code>list</code>를 바꾸는 코드입니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="tsx"><code><span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">const</span><span style="color:#622CBC;--shiki-dark:#DBB7FF"> Tags</span><span style="color:#A0111F;--shiki-dark:#FF9492"> =</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> ({ </span><span style="color:#702C00;--shiki-dark:#FFB757">items</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">, </span><span style="color:#702C00;--shiki-dark:#FFB757">label</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> }) </span><span style="color:#A0111F;--shiki-dark:#FF9492">=></span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> {</span></span>

</li>
<li>
<p><strong>규칙 검사</strong>: 분석 중에 React 규칙 위반이 발견되면 그 함수는 컴파일하지 않고 원본 그대로 출력합니다. 컴파일은 함수 단위로 독립적이라, 파일에 컴포넌트가 다섯 개 있고 하나가 규칙을 어겼다면 나머지 넷만 컴파일됩니다. <a href="#react-%EA%B7%9C%EC%B9%99%EA%B3%BC-%EC%BB%B4%ED%8C%8C%EC%9D%BC-%EA%B1%B4%EB%84%88%EB%9B%B0%EA%B8%B0">React 규칙과 컴파일 건너뛰기</a> 절에서 자세히 봅니다.</p>
</li>
<li>
<p><strong>Reactive Scope 결정과 코드 생성</strong>: 의존성이 같은 값들을 하나의 Reactive Scope로 묶고, 캐시 배열의 칸을 할당한 뒤 <code>if/else</code> 코드로 다시 출력합니다. 2번에서 분석한 <code>Tags</code>의 <code>list</code>는 생성부터 마지막 변경까지가 하나의 스코프가 되고, 의존성도 <code>items</code> 전체가 아니라 실제로 읽은 <code>items[0]</code>과 <code>items[1]</code>로 잡힙니다.</p>

<p><code>list</code>와 무관한 <code>title</code>은 <code>label</code>에만 의존하는 별도 스코프가 됩니다.</p>
</li>
</ol>
<h2 id="react-규칙과-컴파일-건너뛰기">React 규칙과 컴파일 건너뛰기<a class="anchor after" aria-hidden="true" tabindex="-1" href="#react-규칙과-컴파일-건너뛰기"><span class="anchor-icon">#</span></a></h2>
<p>컴파일러가 안전하게 메모이제이션하려면 두 가지 전제가 필요합니다. 같은 입력에 항상 같은 출력이 나와야 캐시한 값을 그대로 돌려줄 수 있고, 렌더링 중에 바깥 상태를 바꾸지 않아야 계산을 건너뛰어도 빠지는 일이 없습니다. 이 두 전제는 React가 오래전부터 문서화해 온 <a href="https://react.dev/reference/rules">React 규칙</a>과 같습니다.</p>
<h3 id="react-규칙">React 규칙<a class="anchor after" aria-hidden="true" tabindex="-1" href="#react-규칙"><span class="anchor-icon">#</span></a></h3>
<p>컴파일러가 검사하는 규칙은 아래 네 가지입니다.</p>
<ul>
<li>
<p><strong>컴포넌트와 훅은 순수해야 합니다.</strong> 렌더링 중에 props, state, 외부 변수를 변경하지 않습니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="tsx"><code><span class="line"><span style="color:#66707B;--shiki-dark:#BDC4CC">// This value cannot be modified</span></span>
<span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">const</span><span style="color:#622CBC;--shiki-dark:#DBB7FF"> A</span><span style="color:#A0111F;--shiki-dark:#FF9492"> =</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> ({ </span><span style="color:#702C00;--shiki-dark:#FFB757">user</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> }) </span><span style="color:#A0111F;--shiki-dark:#FF9492">=></span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> {</span></span>
<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">  user.name </span><span style="color:#A0111F;--shiki-dark:#FF9492">=</span><span style="color:#032563;--shiki-dark:#ADDCFF"> 'x'</span><span style="color:#66707B;--shiki-dark:#BDC4CC"> // props 변경</span></span>
<span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">  return</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> &#x3C;</span><span style="color:#024C1A;--shiki-dark:#72F088">div</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">></span><span style="color:#A0111F;--shiki-dark:#FF9492">{</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">user.name</span><span style="color:#A0111F;--shiki-dark:#FF9492">}</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">&#x3C;/</span><span style="color:#024C1A;--shiki-dark:#72F088">div</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">></span></span>
<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">}</span></span></code></pre>
</li>
<li>
<p><strong>훅은 최상위에서, 매번 같은 순서로 호출합니다.</strong></p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="tsx"><code><span class="line"><span style="color:#66707B;--shiki-dark:#BDC4CC">// Hooks must always be called in a consistent order, and may not be called conditionally</span></span>
<span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">const</span><span style="color:#622CBC;--shiki-dark:#DBB7FF"> B</span><span style="color:#A0111F;--shiki-dark:#FF9492"> =</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> ({ </span><span style="color:#702C00;--shiki-dark:#FFB757">on</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> }) </span><span style="color:#A0111F;--shiki-dark:#FF9492">=></span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> {</span></span>
<span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">  if</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> (on) {</span></span>
<span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">    const</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> [</span><span style="color:#023B95;--shiki-dark:#91CBFF">s</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">] </span><span style="color:#A0111F;--shiki-dark:#FF9492">=</span><span style="color:#622CBC;--shiki-dark:#DBB7FF"> useState</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">(</span><span style="color:#023B95;--shiki-dark:#91CBFF">0</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">) </span><span style="color:#66707B;--shiki-dark:#BDC4CC">// 조건부 훅</span></span>
<span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">    return</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> &#x3C;</span><span style="color:#024C1A;--shiki-dark:#72F088">div</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">></span><span style="color:#A0111F;--shiki-dark:#FF9492">{</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">s</span><span style="color:#A0111F;--shiki-dark:#FF9492">}</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">&#x3C;/</span><span style="color:#024C1A;--shiki-dark:#72F088">div</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">></span></span>
<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">  }</span></span>
<span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">  return</span><span style="color:#023B95;--shiki-dark:#91CBFF"> null</span></span>
<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">}</span></span></code></pre>
</li>
<li>
<p><strong><code>ref.current</code>는 렌더링 중에 읽거나 쓰지 않습니다.</strong> ref는 바뀌어도 리렌더링을 일으키지 않아 렌더링 중에 읽은 값이 화면과 어긋날 수 있기 때문에, 컴파일러가 규칙 위반으로 판단합니다. 화면에 렌더링되어야 하는 값이면 state를 사용하고, 첫 렌더링에 한 번만 초기화하는 <code>if (ref.current === null) ref.current = ...</code> 형태는 허용됩니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="tsx"><code><span class="line"><span style="color:#66707B;--shiki-dark:#BDC4CC">// Cannot access refs during render</span></span>

<span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">  const</span><span style="color:#023B95;--shiki-dark:#91CBFF"> ref</span><span style="color:#A0111F;--shiki-dark:#FF9492"> =</span><span style="color:#622CBC;--shiki-dark:#DBB7FF"> useRef</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">(</span><span style="color:#023B95;--shiki-dark:#91CBFF">0</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">)</span></span>
<span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">  return</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> &#x3C;</span><span style="color:#024C1A;--shiki-dark:#72F088">div</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">></span><span style="color:#A0111F;--shiki-dark:#FF9492">{</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">ref.current</span><span style="color:#A0111F;--shiki-dark:#FF9492">}</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">&#x3C;/</span><span style="color:#024C1A;--shiki-dark:#72F088">div</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">> </span><span style="color:#66707B;--shiki-dark:#BDC4CC">// 렌더링 중 ref 읽기</span></span>
<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">}</span></span></code></pre>
</li>
<li>
<p><strong>렌더링 중에 <code>setState</code>를 무조건 호출하지 않습니다.</strong> <code>if (prev !== count)</code>처럼 조건을 걸어 이전 렌더링의 값과 비교하는 패턴은 조건이 거짓이 되면 멈추기 때문에 허용되며, 컴파일러와 lint 모두 통과시킵니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="tsx"><code><span class="line"><span style="color:#66707B;--shiki-dark:#BDC4CC">// Calling setState during render may trigger an infinite loop</span></span>

<h4 id="eslint로-미리-찾기">ESLint로 미리 찾기<a class="anchor after" aria-hidden="true" tabindex="-1" href="#eslint로-미리-찾기"><span class="anchor-icon">#</span></a></h4>
<p><code>eslint-plugin-react-hooks</code>를 사용하면 규칙 위반을 미리 찾을 수 있습니다. 컴파일러 1.0과 함께 나온 <code>eslint-plugin-react-hooks</code> 7.0부터는 컴파일러의 분석 엔진으로 동작하는 규칙이 기본 <code>recommended</code> 프리셋에 포함되어, 컴파일러와 같은 기준으로 규칙 위반을 lint 에러로 볼 수 있습니다. 컴파일러를 설치하지 않아도 lint만 따로 쓸 수 있습니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="js"><code><span class="line"><span style="color:#66707B;--shiki-dark:#BDC4CC">// eslint.config.js</span></span>

<span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">import</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> { defineConfig } </span><span style="color:#A0111F;--shiki-dark:#FF9492">from</span><span style="color:#032563;--shiki-dark:#ADDCFF"> 'eslint/config'</span></span>
<span class="line"></span>
<span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">export</span><span style="color:#A0111F;--shiki-dark:#FF9492"> default</span><span style="color:#622CBC;--shiki-dark:#DBB7FF"> defineConfig</span><span style="color:#702C00;--shiki-dark:#FFB757">([</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">reactHooks</span><span style="color:#702C00;--shiki-dark:#FFB757">.</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">configs</span><span style="color:#702C00;--shiki-dark:#FFB757">.</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">flat</span><span style="color:#702C00;--shiki-dark:#FFB757">.</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">recommended</span><span style="color:#702C00;--shiki-dark:#FFB757">])</span></span></code></pre>
<p><code>recommended</code> 프리셋에 <code>set-state-in-render</code>, <code>set-state-in-effect</code>, <code>refs</code>, <code>immutability</code> 같은 규칙이 포함되어 있습니다. 별도 패키지였던 <code>eslint-plugin-react-compiler</code>는 이 플러그인으로 통합되었기 때문에, 설치되어 있다면 제거하면 됩니다.</p>
<h3 id="컴파일-건너뛰기">컴파일 건너뛰기<a class="anchor after" aria-hidden="true" tabindex="-1" href="#컴파일-건너뛰기"><span class="anchor-icon">#</span></a></h3>
<p>컴파일러는 위에서 살펴본 네 가지 규칙을 지킨다고 가정하고 코드를 바꿉니다. 규칙을 어긴 코드가 발견되면 <strong>빌드를 실패시키는 대신 그 함수만 컴파일하지 않고 원본 그대로 둡니다.</strong></p>
<p>다만 기본 설정에서는 규칙을 위반해도 아무 알림 없이 조용히 건너뛸 뿐, 위 주석 같은 이유를 터미널이나 콘솔에 보여주지 않습니다. 건너뛴 컴포넌트는 컴파일 전과 똑같이 동작하기 때문에 어느 컴포넌트가 빠졌는지 모르고 지나치기 쉽습니다. 앞의 ESLint 플러그인이 컴파일러와 같은 기준으로 검사하기 때문에, lint를 통과시켜 두면 규칙 위반으로 건너뛰는 컴포넌트는 대부분 사라집니다. 또한 객체나 함수를 반환하는 <code>useMemo</code>, <code>useCallback</code>의 의존성 배열 누락처럼 <code>exhaustive-deps</code> 경고로만 나오는 경우도 컴파일러는 그 컴포넌트를 건너뛰기 때문에, 경고까지 없애 두는 것이 좋습니다.</p>
<h4 id="컴파일러가-잡지-못하는-위반">컴파일러가 잡지 못하는 위반<a class="anchor after" aria-hidden="true" tabindex="-1" href="#컴파일러가-잡지-못하는-위반"><span class="anchor-icon">#</span></a></h4>
<p>컴파일러의 분석은 정적 분석이라 한계가 있습니다. 아래 코드는 props로 받은 배열을 <code>sort()</code>로 정렬하는데, 컴파일러는 <code>Array.prototype.sort</code>가 배열을 변경한다는 것을 모델링하지 않아 그냥 컴파일합니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="tsx"><code><span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">const</span><span style="color:#622CBC;--shiki-dark:#DBB7FF"> E</span><span style="color:#A0111F;--shiki-dark:#FF9492"> =</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> ({ </span><span style="color:#702C00;--shiki-dark:#FFB757">list</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> }) </span><span style="color:#A0111F;--shiki-dark:#FF9492">=></span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> {</span></span>
<span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">  const</span><span style="color:#023B95;--shiki-dark:#91CBFF"> sorted</span><span style="color:#A0111F;--shiki-dark:#FF9492"> =</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> list.</span><span style="color:#622CBC;--shiki-dark:#DBB7FF">sort</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">() </span><span style="color:#66707B;--shiki-dark:#BDC4CC">// list 자체가 바뀜</span></span>
<span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">  return</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> &#x3C;</span><span style="color:#024C1A;--shiki-dark:#72F088">div</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">></span><span style="color:#A0111F;--shiki-dark:#FF9492">{</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">sorted.</span><span style="color:#023B95;--shiki-dark:#91CBFF">length</span><span style="color:#A0111F;--shiki-dark:#FF9492">}</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">&#x3C;/</span><span style="color:#024C1A;--shiki-dark:#72F088">div</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">></span></span>
<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">}</span></span></code></pre>
<p>이 코드는 컴파일 전에도 문제가 있습니다. <code>sort()</code>는 새 배열을 만들지 않고 원본 배열의 순서를 직접 바꾸기 때문에, 부모가 같은 배열을 다른 곳에서도 쓰고 있다면 그쪽 순서까지 바뀝니다. 컴파일 후에는 <code>list</code> 참조가 같을 때 <code>sort()</code>를 건너뛰고 캐시한 <code>sorted</code>를 돌려줍니다. 배열은 첫 렌더링 때 이미 정렬되어 있으니 화면은 그대로지만, 매 렌더링마다 실행되던 <code>sort()</code>가 한 번만 실행되도록 동작이 바뀌게 됩니다. 컴파일러는 규칙을 지킨 코드를 전제로 변환하기 때문에, 규칙 위반이 남아 있으면 이렇게 컴파일 전후의 동작이 미묘하게 달라질 수 있습니다.</p>

<h2 id="점진적-도입">점진적 도입<a class="anchor after" aria-hidden="true" tabindex="-1" href="#점진적-도입"><span class="anchor-icon">#</span></a></h2>
<p>처음부터 전체 프로젝트에 컴파일러를 적용하는 대신, 범위를 좁혀 시작할 수 있는 여러 방법이 있습니다.</p>
<h3 id="지시어-함수-단위">지시어: 함수 단위<a class="anchor after" aria-hidden="true" tabindex="-1" href="#지시어-함수-단위"><span class="anchor-icon">#</span></a></h3>
<p>컴포넌트나 훅의 첫 줄에 지시어를 쓰면 그 함수만 컴파일 대상에서 넣거나 뺄 수 있습니다. 소스 코드에 쓰는 것이라 도구와 무관합니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="tsx"><code><span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">const</span><span style="color:#622CBC;--shiki-dark:#DBB7FF"> Legacy</span><span style="color:#A0111F;--shiki-dark:#FF9492"> =</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> () </span><span style="color:#A0111F;--shiki-dark:#FF9492">=></span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> {</span></span>
<span class="line"><span style="color:#032563;--shiki-dark:#ADDCFF">  'use no memo'</span><span style="color:#66707B;--shiki-dark:#BDC4CC"> // 이 컴포넌트는 컴파일하지 않음</span></span>
<span class="line"><span style="color:#66707B;--shiki-dark:#BDC4CC">  // ...</span></span>
<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">}</span></span>
<span class="line"></span>
<span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">const</span><span style="color:#622CBC;--shiki-dark:#DBB7FF"> Modern</span><span style="color:#A0111F;--shiki-dark:#FF9492"> =</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> () </span><span style="color:#A0111F;--shiki-dark:#FF9492">=></span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> {</span></span>
<span class="line"><span style="color:#032563;--shiki-dark:#ADDCFF">  'use memo'</span><span style="color:#66707B;--shiki-dark:#BDC4CC"> // annotation 모드에서 이 컴포넌트만 컴파일</span></span>
<span class="line"><span style="color:#66707B;--shiki-dark:#BDC4CC">  // ...</span></span>
<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">}</span></span></code></pre>
<p>파일 최상단(import 보다 앞)에 쓰면 파일 전체에 적용됩니다. <code>"use no memo"</code>와 <code>"use memo"</code>가 겹치면 <code>"use no memo"</code>가 이깁니다. 파일에 <code>"use no memo"</code>를 두면 함수에 <code>"use memo"</code>를 써도 컴파일되지 않고, 파일에 <code>"use memo"</code>를 두고 한 함수에만 <code>"use no memo"</code>를 쓰면 그 함수만 빠집니다. <code>"use no memo"</code>는 문제를 격리하기 위한 임시 장치로, 왜 뺐는지 주석과 함께 남기고 원인을 고친 뒤 제거하는 것이 좋습니다. 철자가 틀리면 조용히 무시되니 주의해야 합니다.</p>
<h3 id="compilationmode-기본-범위">compilationMode: 기본 범위<a class="anchor after" aria-hidden="true" tabindex="-1" href="#compilationmode-기본-범위"><span class="anchor-icon">#</span></a></h3>
<p><code>compilationMode</code>는 어떤 함수를 컴파일할지 정합니다.</p>





















<table><thead><tr><th align="left">값</th><th align="left">동작</th></tr></thead><tbody><tr><td align="left"><code>'infer'</code> (기본값)</td><td align="left">이름과 내용으로 컴포넌트·훅을 추론해 컴파일합니다. 지시어가 있으면 지시어를 따릅니다.</td></tr><tr><td align="left"><code>'annotation'</code></td><td align="left"><code>"use memo"</code>가 있는 함수만 컴파일합니다. 하나씩 켜 가며 도입할 때 사용합니다.</td></tr><tr><td align="left"><code>'all'</code></td><td align="left">파일 가장 바깥에 선언된 모든 함수를 컴파일합니다.</td></tr></tbody></table>
<blockquote>
<p><strong><code>'all'</code>은 컴포넌트가 아닌 함수에도 훅 호출이 들어가기 때문에 권장하지 않습니다.</strong></p>
<ul>
<li>컴파일러가 넣는 <code>const $ = _c(n)</code>은 내부적으로 <code>useMemoCache</code>라는 훅입니다. 파일 가장 바깥의 유틸 함수에 이 코드가 들어가면, 렌더링 바깥에서 호출될 때 훅 호출 규칙 위반으로 실패합니다(개발 모드에서는 "Invalid hook call" 경고가 함께 출력됩니다).</li>
<li>인자로 받은 객체의 속성을 고치는(<code>obj.x = 1</code>) 평범한 함수도 React 규칙 위반으로 걸려 조용히 건너뛰어집니다. lint는 컴포넌트와 훅만 검사하기 때문에 알려 주지도 않습니다. 컴포넌트가 아닌 함수에 순수성 규칙을 강제할 이유가 없습니다.</li>
<li>메모이제이션이 의미 없는 함수에도 캐시 배열과 비교 코드가 붙어 번들만 커집니다.</li>
</ul>
<p>React 문서도 React와 무관한 함수까지 컴파일할 수 있고 유틸 함수를 컴파일하면 성능이 오히려 나빠질 수 있다며 권장하지 않습니다. 실무에서는 <code>'infer'</code>를 기본으로 쓰고, 더 좁히고 싶을 때 <code>'annotation'</code>을 쓰는 두 가지면 충분합니다.</p>
</blockquote>

<h3 id="디렉터리-단위">디렉터리 단위<a class="anchor after" aria-hidden="true" tabindex="-1" href="#디렉터리-단위"><span class="anchor-icon">#</span></a></h3>
<p>새로 작성하는 디렉터리부터 켜고 레거시는 나중에 옮기는 방식입니다. 이것은 <code>babel-plugin-react-compiler</code> 플러그인 옵션이 아니라 "어떤 파일에 플러그인을 돌릴지"의 문제라서 도구마다 방법이 다릅니다.</p>

<p><strong>Next.js</strong></p>
<p>Next.js는 디렉터리 단위로 지정할 수 없습니다. <code>reactCompiler</code> 옵션에 경로 옵션이 없고, <code>babel.config.js</code>의 <code>overrides</code>도 무시합니다. 디렉터리 단위로 가려면 <code>compilationMode: 'annotation'</code>을 켜고 원하는 컴포넌트와 훅의 함수 첫 줄에 <code>"use memo"</code>를 적습니다. annotation 모드는 함수 안의 지시어만 보기 때문에 파일 최상단에 적어서는 안 됩니다.</p>

<h3 id="게이팅-사용자-단위">게이팅: 사용자 단위<a class="anchor after" aria-hidden="true" tabindex="-1" href="#게이팅-사용자-단위"><span class="anchor-icon">#</span></a></h3>
<p>앞의 방법들이 어떤 컴포넌트를 컴파일할지 정한다면, <code>gating</code>은 <strong>어떤 사용자에게 컴파일된 코드를 줄지</strong> 정합니다. 옵션을 사용하면 컴파일러가 컴포넌트마다 컴파일된 버전과 원본 버전을 모두 번들에 포함하고, 지정한 함수를 호출해 런타임에 둘 중 하나를 고릅니다. A/B 테스트나 일부 사용자에게만 먼저 배포할 때 사용합니다.</p>
<p>설정에는 "고르는 함수"가 어느 모듈(<code>source</code>)의 어떤 이름(<code>importSpecifierName</code>)인지만 적습니다. <code>source</code>에 적은 문자열이 그대로 <code>import</code> 경로가 되기 때문에 상대 경로보다는 경로 별칭이나 패키지 이름을 씁니다. Next.js의 <code>reactCompiler</code> 옵션에는 <code>gating</code>이 없어 지원하지 않습니다.</p>

<p><code>isCompilerEnabled()</code>는 이 모듈이 처음 import 될 때 한 번만 호출되고, 그 결과가 모듈이 살아 있는 동안 유지됩니다. 브라우저에서는 번들이 로드될 때, SSR 서버에서는 프로세스가 모듈을 import 할 때입니다. 그래서 이 함수는 API 응답을 기다리는 비동기 함수일 수 없고, 호출 즉시 <code>true</code>나 <code>false</code>를 반환해야 합니다. 컴파일된 코드와 원본 코드가 번들에 모두 들어가 크기가 늘어나기 때문에, 전환이 끝나면 <code>gating</code> 옵션을 제거합니다.</p>
<h2 id="규칙-위반을-빌드-에러로">규칙 위반을 빌드 에러로<a class="anchor after" aria-hidden="true" tabindex="-1" href="#규칙-위반을-빌드-에러로"><span class="anchor-icon">#</span></a></h2>
<p>앞의 옵션들이 어디까지 컴파일할지를 정했다면, <code>panicThreshold</code>는 컴파일러가 규칙 위반을 만났을 때 조용히 건너뛸지, 빌드를 실패시킬지 정합니다.</p>





















<table><thead><tr><th align="left">값</th><th align="left">동작</th></tr></thead><tbody><tr><td align="left"><code>'none'</code> (기본값)</td><td align="left">코드를 분석하다 나온 에러는 어떤 것이든 빌드를 실패시키지 않고 해당 함수만 건너뜁니다. 다만 <code>compilationMode: 'bogus'</code>처럼 컴파일러 옵션 자체가 잘못된 경우는 <code>'none'</code>이어도 빌드가 실패합니다.</td></tr><tr><td align="left"><code>'critical_errors'</code></td><td align="left">React 규칙 위반이나 기존 <code>useMemo</code>, <code>useCallback</code>의 의존성 불일치처럼 코드 자체가 잘못된 경우만 빌드 에러로 만듭니다. 제너레이터 함수나 <code>try/finally</code>처럼 코드는 멀쩡하지만 컴파일러가 아직 지원하지 않는 문법 때문에 건너뛰는 경우는 에러로 만들지 않습니다.</td></tr><tr><td align="left"><code>'all_errors'</code></td><td align="left">컴파일러가 지원하지 않는 문법 등 모든 건너뛰기를 빌드 에러로 만듭니다. 코드가 틀리지 않아도 빌드가 깨질 수 있습니다.</td></tr></tbody></table>
<p>개발 중에는 <code>'critical_errors'</code>로 두어 위반을 넣는 순간 바로 알아차리게 하고, 운영 빌드에는 <code>'none'</code>을 두어 컴파일러 문제로 배포가 막히지 않게 하는 구성이 일반적입니다.</p>

<h2 id="성능은-얼마나-좋아지나">성능은 얼마나 좋아지나<a class="anchor after" aria-hidden="true" tabindex="-1" href="#성능은-얼마나-좋아지나"><span class="anchor-icon">#</span></a></h2>

<p><a href="/assets/example/react/react-compiler/compare.html">compare.html</a>에서 직접 눌러 볼 수 있습니다. 컴파일 전후 코드는 <code>babel-plugin-react-compiler</code> 1.0.0을 쓰는 <a href="/assets/example/react/react-compiler/compile.mjs">compile.mjs</a> 스크립트로 <a href="/assets/example/react/react-compiler/App.jsx">App.jsx</a>를 변환한 결과입니다. 컴파일 전은 브라우저가 읽을 수 있도록 JSX 변환만 거쳤고, 컴파일 후는 컴파일러 플러그인을 켠 뒤 같은 JSX 변환을 거쳤습니다. 컴파일 전(왼쪽)은 버튼을 누를 때마다 300개 행이 전부 반짝이고 클릭 한 번에 약 26~29ms가 걸립니다. 컴파일 후(오른쪽)는 행이 하나도 반짝이지 않고 0.2ms면 끝납니다. 컴파일러는 <code>Row</code>에 넘기는 <code>onRender</code>를 한 번만 만들고 재사용하기 때문에 <code>items</code>, <code>onSelect</code>, <code>onRender</code> 모두 변경되지 않아 리스트 JSX를 비교하지 않습니다. 첫 렌더링 때 만들어진 JSX를 계속 캐시에서 꺼내 쓰게 되어 300개 <code>Row</code>의 리렌더링이 발생하지 않습니다.</p>

<p>위 표는 같은 구조를 jsdom + React 19에서 반복 실행해 잰 것입니다. 앞의 브라우저 데모는 행마다 강제 리플로우가 포함된 수치라 한 번 클릭에 걸리는 시간이 이 표의 한 회분보다 큽니다.</p>
<p>행의 계산이 가벼워도 차이가 큰 이유는, 300개 컴포넌트를 다시 실행하고 비교(Reconciliation)하는 비용 자체가 사라지기 때문입니다. 세 번째 줄의 인라인 객체 <code>style={{ ... }}</code>는 컴파일 전에는 렌더링마다 새로운 객체가 되어 자식을 <code>memo</code>로 감싸도 매번 리렌더링됩니다. 컴파일러는 이런 객체 리터럴도 함께 캐시해 매번 같은 참조를 넘기기 때문에, 컴파일 후에는 인라인 객체가 있어도 문제가 되지 않습니다.</p>
<h2 id="주의할-점">주의할 점<a class="anchor after" aria-hidden="true" tabindex="-1" href="#주의할-점"><span class="anchor-icon">#</span></a></h2>
<p>컴파일러를 실제 프로젝트에 적용하면서 겪는 문제들입니다.</p>
<h3 id="기존-수동-메모이제이션은-그대로-둔다">기존 수동 메모이제이션은 그대로 둔다<a class="anchor after" aria-hidden="true" tabindex="-1" href="#기존-수동-메모이제이션은-그대로-둔다"><span class="anchor-icon">#</span></a></h3>
<p>컴파일러를 도입할 때 기존 코드의 <code>useMemo</code>, <code>useCallback</code>을 미리 걷어낼 필요는 없습니다. 컴파일러가 이 훅들을 분석해서 자신의 Reactive Scope로 바꿔 넣고, 그대로 보장할 수 없는 경우에는 그 컴포넌트만 건너뛰기 때문에, 걷어내는 작업은 컴파일러가 안정적으로 돌아간 뒤 해도 늦지 않습니다.</p>
<p>아래 표는 컴파일러가 사람이 작성한 <code>useMemo</code>를 어떻게 처리하는지 정리한 것입니다. <code>useCallback</code>은 결과가 항상 함수라 객체와 같은 첫 세 행에 해당합니다.</p>









































<table><thead><tr><th align="left">기존 코드</th><th align="left">컴파일 결과</th></tr></thead><tbody><tr><td align="left"><code>useMemo(() => ({ a, b }), [a, b])</code> (객체)</td><td align="left"><code>a</code>, <code>b</code>에 의존하는 Reactive Scope로 바꿔 넣음</td></tr><tr><td align="left"><code>useMemo(() => ({ a, b }), [a])</code> (객체, 의존성 누락)</td><td align="left">컴포넌트 전체를 건너뜀</td></tr><tr><td align="left"><code>useMemo(() => ({ a }), [a, b])</code> (객체, 쓰지 않는 의존성 포함)</td><td align="left"><code>a</code>에만 의존하는 Reactive Scope로 바꿔 넣음. 남는 의존성은 무시</td></tr><tr><td align="left"><code>useMemo(() => a + b, [a, b])</code> (연산으로 만든 원시 값)</td><td align="left"><code>useMemo</code>를 벗겨 내고 매 렌더링마다 계산</td></tr><tr><td align="left"><code>useMemo(() => a + b, [a])</code> (연산으로 만든 원시 값, 의존성 누락)</td><td align="left">건너뛰지 않고 똑같이 <code>useMemo</code>를 벗겨 냄. <code>b</code>가 바뀌면 다시 계산되어 동작이 달라짐</td></tr><tr><td align="left"><code>useMemo(() => heavy(a), [a])</code> (함수 호출로 얻은 원시 값)</td><td align="left"><code>a</code>에 의존하는 Reactive Scope로 바꿔 넣음</td></tr><tr><td align="left"><code>useMemo(() => heavy(a, b), [a])</code> (함수 호출로 얻은 원시 값, 의존성 누락)</td><td align="left">컴포넌트 전체를 건너뜀</td></tr><tr><td align="left"><code>useMemo(() => { /* 무거운 루프 */ }, [a])</code> (인라인 루프로 만든 원시 값)</td><td align="left"><code>useMemo</code>를 벗겨 내고 루프를 매 렌더링마다 실행</td></tr></tbody></table>
<p><strong><code>useMemo(() => ({ a, b }), [a, b])</code> (객체)</strong></p>
<p>사람이 작성한 의존성이 컴파일러의 분석과 일치하면, <code>useMemo</code> 없이 <code>{ a, b }</code>를 적은 코드를 컴파일한 것과 동일하게 <code>a</code>, <code>b</code>에 의존하는 Reactive Scope로 바꿔 넣습니다.</p>
<p><strong><code>useMemo(() => ({ a, b }), [a])</code> (객체, 의존성 누락)</strong></p>
<p>의존성이 다르면 그 컴포넌트 전체를 건너뜁니다. 아래처럼 의존성 배열에서 <code>b</code>를 빠뜨린 경우, 컴파일러의 분석으로는 <code>b</code>가 바뀌면 <code>v</code>도 바뀌어야 하기 때문에 기존 메모이제이션을 그대로 보장할 수 없습니다. 이때는 <code>Existing memoization could not be preserved</code>라는 이유로 그 컴포넌트의 컴파일을 건너뜁니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="tsx"><code><span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">const</span><span style="color:#622CBC;--shiki-dark:#DBB7FF"> Wrong</span><span style="color:#A0111F;--shiki-dark:#FF9492"> =</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> ({ </span><span style="color:#702C00;--shiki-dark:#FFB757">a</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">, </span><span style="color:#702C00;--shiki-dark:#FFB757">b</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> }) </span><span style="color:#A0111F;--shiki-dark:#FF9492">=></span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> {</span></span>
<span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">  const</span><span style="color:#023B95;--shiki-dark:#91CBFF"> v</span><span style="color:#A0111F;--shiki-dark:#FF9492"> =</span><span style="color:#622CBC;--shiki-dark:#DBB7FF"> useMemo</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">(() </span><span style="color:#A0111F;--shiki-dark:#FF9492">=></span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> ({ a, b }), [a]) </span><span style="color:#66707B;--shiki-dark:#BDC4CC">// b 누락 → 이 컴포넌트 전체를 건너뜀</span></span>
<span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">  return</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> &#x3C;</span><span style="color:#024C1A;--shiki-dark:#72F088">Child</span><span style="color:#023B95;--shiki-dark:#91CBFF"> v</span><span style="color:#A0111F;--shiki-dark:#FF9492">={</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">v</span><span style="color:#A0111F;--shiki-dark:#FF9492">}</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> /></span></span>
<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">}</span></span></code></pre>
<p><strong><code>useMemo(() => ({ a }), [a, b])</code> (객체, 쓰지 않는 의존성 포함)</strong></p>
<p>계산에 쓰지 않는 <code>b</code>가 의존성에 들어 있는 경우는 건너뛰지 않습니다. 값이 실제로 <code>b</code>에 의존하지 않아, <code>a</code>에만 의존하는 Reactive Scope를 만들고, 남는 <code>b</code>는 무시합니다.</p>
<p><strong><code>useMemo(() => a + b, [a, b])</code> (연산으로 만든 원시 값)</strong></p>
<p>결과가 숫자나 문자열 같은 원시 값이면 참조를 유지할 이유가 없기 때문에 Reactive Scope로 바꿔 넣는 대신 <code>useMemo</code> 자체를 벗겨 내어 <code>const v = a + b</code>로 바꿉니다.</p>
<blockquote>
<p><strong>참조를 유지해야 하는 이유</strong></p>
<p><code>useMemo</code>로 참조를 유지하는 이유는, 객체나 배열은 내용이 같아도 새로 만들면 <code>!==</code>라서, <code>memo</code>로 감싼 자식이나 <code>useEffect</code> 의존성 배열이 "값이 바뀌었다"고 판단하기 때문입니다. 반면 숫자나 문자열은 다시 계산해도 <code>3 === 3</code>처럼 같아서 자식이 리렌더링되거나 이펙트가 재실행되지 않습니다.</p>
</blockquote>
<p><strong><code>useMemo(() => a + b, [a])</code> (연산으로 만든 원시 값, 의존성 누락)</strong></p>
<p><code>b</code>가 바뀌어도 옛 값을 유지하려고 의존성을 일부러 뺀 경우 주의해야 합니다. 결과가 원시 값이면 컴파일러가 <code>useMemo</code>를 벗겨 내기 때문에 <code>b</code>가 바뀔 때마다 다시 계산되어 동작이 달라집니다. 이때는 건너뛰지도 않고 에러도 발생하지 않습니다. React에서는 의존성 배열에 계산에 쓰인 값을 빠짐없이 적는 것이 규칙이기 때문에, 값을 고정하려는 의도라면 <code>useState(() => a + b)</code>나 <code>useRef</code>처럼 의도가 드러나는 방법으로 바꿔야 합니다.</p>
<p><strong><code>useMemo(() => heavy(a), [a])</code> (함수 호출로 얻은 원시 값)</strong></p>
<p>함수를 호출해 얻는 값은 비용을 알 수 없기 때문에 원시 값이어도 <code>a</code>에 의존하는 Reactive Scope로 바꿔 넣어 캐시를 유지합니다.</p>
<p><strong><code>useMemo(() => heavy(a, b), [a])</code> (함수 호출로 얻은 원시 값, 의존성 누락)</strong></p>
<p>함수 호출 결과를 캐시하기 때문에 <code>b</code>가 빠지면 기존 메모이제이션을 보장할 수 없어 컴포넌트 전체를 건너뜁니다.</p>
<p><strong><code>useMemo(() => { /* 무거운 루프 */ }, [a])</code> (인라인 루프로 만든 원시 값)</strong></p>
<p>무거운 계산을 함수로 분리하지 않고 <code>useMemo</code> 안에 루프로 직접 적은 코드는 주의해야 합니다. 결과가 원시 값이면 컴파일러가 <code>useMemo</code>를 벗겨 내고 루프를 매 렌더링마다 실행하기 때문에 컴파일 전보다 느려집니다. 무거운 계산은 함수로 분리해 컴파일러가 그 호출 결과를 캐시하게 하는 것이 좋습니다.</p>
<p>새로 작성하는 코드에서는 성능을 위한 <code>useMemo</code>, <code>useCallback</code>은 쓰지 않고 컴파일러에 맡깁니다. 다만 아래 코드처럼 참조가 바뀌면 동작까지 달라지는 경우는 예외입니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="tsx"><code><span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">const</span><span style="color:#023B95;--shiki-dark:#91CBFF"> options</span><span style="color:#A0111F;--shiki-dark:#FF9492"> =</span><span style="color:#622CBC;--shiki-dark:#DBB7FF"> useMemo</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">(() </span><span style="color:#A0111F;--shiki-dark:#FF9492">=></span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> ({ id }), [id]) </span><span style="color:#66707B;--shiki-dark:#BDC4CC">// 컴파일러에 맡기지 않고 직접 고정</span></span>
<span class="line"><span style="color:#622CBC;--shiki-dark:#DBB7FF">useEffect</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">(() </span><span style="color:#A0111F;--shiki-dark:#FF9492">=></span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> {</span></span>
<span class="line"><span style="color:#622CBC;--shiki-dark:#DBB7FF">  connect</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">(options) </span><span style="color:#66707B;--shiki-dark:#BDC4CC">// options 참조가 바뀔 때마다 다시 연결됨</span></span>
<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">}, [options])</span></span></code></pre>
<p><code>useMemo</code> 없이 <code>const options = { id }</code>로 쓰고 컴파일러에 맡겼다면, 나중에 규칙 위반 코드가 추가되는 등의 이유로 컴파일러가 이 컴포넌트를 건너뛰는 순간 <code>options</code>가 렌더링마다 새 객체가 되어 이펙트가 매번 재실행됩니다. 이런 값은 위처럼 <code>useMemo</code>로 직접 만들어 참조를 고정해 둡니다. 기존 코드의 <code>useMemo</code>를 지우는 것도 같은 이유로 결과가 달라질 수 있기 때문에, 지운다면 테스트로 확인하는 것이 좋습니다.</p>
<p><code>memo</code>로 감싼 컴포넌트도 그대로 둘 수 있습니다. 컴파일러는 <code>memo(...)</code> 호출은 건드리지 않고 안쪽 함수 본문만 바꾸기 때문에, <code>memo</code>의 props 비교와 컴파일러의 캐시가 함께 동작하고 서로 방해하지 않습니다.</p>
<h3 id="동작이-바뀌는-코드">동작이 바뀌는 코드<a class="anchor after" aria-hidden="true" tabindex="-1" href="#동작이-바뀌는-코드"><span class="anchor-icon">#</span></a></h3>
<p>가장 흔한 문제는 어떤 값이 매 렌더링마다 새로 만들어지는 것을 예상했던 코드가, 컴파일 후 그 값이 캐시되면서 다르게 동작하는 경우입니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="tsx"><code><span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">const</span><span style="color:#622CBC;--shiki-dark:#DBB7FF"> Search</span><span style="color:#A0111F;--shiki-dark:#FF9492"> =</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> ({ </span><span style="color:#702C00;--shiki-dark:#FFB757">query</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> }) </span><span style="color:#A0111F;--shiki-dark:#FF9492">=></span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> {</span></span>
<span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">  const</span><span style="color:#023B95;--shiki-dark:#91CBFF"> options</span><span style="color:#A0111F;--shiki-dark:#FF9492"> =</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> { query, page: </span><span style="color:#023B95;--shiki-dark:#91CBFF">1</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> }</span></span>
<span class="line"></span>
<span class="line"><span style="color:#622CBC;--shiki-dark:#DBB7FF">  useEffect</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">(() </span><span style="color:#A0111F;--shiki-dark:#FF9492">=></span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> {</span></span>
<span class="line"><span style="color:#622CBC;--shiki-dark:#DBB7FF">    fetchResults</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">(options)</span></span>
<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">  }, [options])</span></span>
<span class="line"><span style="color:#66707B;--shiki-dark:#BDC4CC">  // ...</span></span>
<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">}</span></span></code></pre>
<p>컴파일 전에는 <code>options</code>가 매 렌더링마다 새 객체라 이펙트가 매번 실행되었습니다. 컴파일 후에는 <code>options</code>가 <code>query</code>에 의존하는 Reactive Scope가 되어 <code>query</code>가 같으면 같은 객체이고, 이펙트는 <code>query</code>가 바뀔 때만 실행됩니다. 이것이 의도한 동작이라면 버그가 고쳐진 것이고, 매번 실행되는 것에 기대고 있었다면 동작이 바뀐 것입니다.</p>
<p>캐시가 잘못 작동하는 문제도 있습니다. <a href="#react-%EA%B7%9C%EC%B9%99">순수성 규칙</a>을 어기고 props나 state에서 온 객체를 렌더링 중에 변경하면 참조는 그대로인 채 내용만 바뀌기 때문에 캐시 비교가 어긋나고, 이펙트가 예상보다 자주 실행되거나 무한 루프에 빠지기도 합니다. <code>user.name = 'x'</code>처럼 컴포넌트 안에서 눈에 보이게 변경하는 코드는 lint가 잡아 주지만, <code>sort()</code>처럼 컴파일러가 모델링하지 않은 메서드나 다른 함수 안에 숨은 변경은 lint도 놓칩니다.</p>
<p>이런 문제가 의심되는 컴포넌트에 <code>"use no memo"</code>를 붙여 컴파일에서 빼 봅니다. 그렇게 해서 증상이 사라진다면 컴파일러 버그라기보다 그 컴포넌트에 숨어 있던 React 규칙 위반이 드러난 것이니, 컴파일러를 끄는 대신 위반한 코드를 고쳐야 합니다.</p>
<h3 id="캐시는-인스턴스마다-따로">캐시는 인스턴스마다 따로<a class="anchor after" aria-hidden="true" tabindex="-1" href="#캐시는-인스턴스마다-따로"><span class="anchor-icon">#</span></a></h3>
<p>캐시 배열은 컴포넌트 인스턴스마다 따로 만들어지기 때문에, 다른 컴포넌트나 같은 컴포넌트의 다른 인스턴스와 공유되지 않습니다. 여러 컴포넌트가 같은 무거운 계산을 한다면 각자 계산하기 때문에, 이런 경우는 직접 캐시를 관리하는 것이 좋습니다.</p>
<h3 id="비교는-얕은-비교">비교는 얕은 비교<a class="anchor after" aria-hidden="true" tabindex="-1" href="#비교는-얕은-비교"><span class="anchor-icon">#</span></a></h3>
<p>Reactive Scope는 의존성을 <code>!==</code>로 비교합니다. <code>useMemo</code>의 의존성 비교와 마찬가지로 참조만 보는 얕은 비교라, 내용이 같아도 참조가 다르면 다시 계산합니다. 그래서 컴파일되지 않은 부모가 매 렌더링마다 새 객체를 props로 넘기면 컴파일된 자식도 매번 다시 계산합니다. 외부 라이브러리의 훅이 호출할 때마다 새 객체를 반환하는 경우도 마찬가지입니다. 부모까지 컴파일되면 그 객체도 캐시되어 참조가 유지되기 때문에, 프로젝트 전체에 적용할수록 효과가 커집니다.</p>
<h3 id="런타임-비용">런타임 비용<a class="anchor after" aria-hidden="true" tabindex="-1" href="#런타임-비용"><span class="anchor-icon">#</span></a></h3>
<p>컴파일된 코드는 원본보다 길고, 렌더링마다 캐시 칸을 비교하는 연산이 추가됩니다. 매우 단순한 컴포넌트에서는 비교 비용이 절약되는 비용보다 클 수도 있습니다.</p>
<h3 id="라이브러리-배포-시-react-19-요구">라이브러리 배포 시 React 19 요구<a class="anchor after" aria-hidden="true" tabindex="-1" href="#라이브러리-배포-시-react-19-요구"><span class="anchor-icon">#</span></a></h3>
<p>라이브러리를 컴파일해서 배포하면, 그 라이브러리를 쓰는 앱은 컴파일러를 설치하지 않아도 메모이제이션된 코드를 받습니다. 다만 컴파일된 코드는 React 19에 들어 있는 <code>react/compiler-runtime</code>을 import 하기 때문에, 라이브러리가 React 19 이상을 요구하게 됩니다. 17이나 18까지 지원하려면 <a href="#react-17-18-%EB%9F%B0%ED%83%80%EC%9E%84-%ED%8C%A8%ED%82%A4%EC%A7%80">React 17, 18 런타임 패키지</a> 절처럼 <code>target</code>을 낮추고 <code>react-compiler-runtime</code> 패키지를 라이브러리의 의존성에 추가해야 합니다.</p>
