1a:T1e1d1,<blockquote>
<p><strong>TL;DR</strong></p>
<ul>
<li>서버 컴포넌트(Server Component)는 서버에서만 실행되는 컴포넌트입니다. 클라이언트로 JavaScript가 전달되지 않고, 렌더링 결과만 RSC Payload라는 형태로 전달됩니다.</li>
<li>클라이언트 컴포넌트(Client Component)는 파일 최상단에 <code>'use client'</code>를 선언한 컴포넌트로, 기존에 작성하던 React 컴포넌트와 같습니다. 상태, 이펙트, 이벤트 핸들러는 클라이언트 컴포넌트에서만 사용할 수 있습니다.</li>
<li>서버 컴포넌트는 <code>async</code> 함수로 선언하고 <code>await</code>로 데이터를 직접 가져올 수 있습니다. 데이터베이스, 파일 시스템, 내부 API에 클라이언트를 거치지 않고 접근합니다.</li>
<li>서버 컴포넌트에서는 클라이언트 컴포넌트를 import 할 수 있습니다. 하지만 클라이언트 컴포넌트에서 서버 컴포넌트를 import 하면 그 서버 컴포넌트는 클라이언트 컴포넌트가 되어 버립니다. 클라이언트 컴포넌트 안에 서버 컴포넌트를 두고 싶다면 <code>children</code>과 같은 prop으로 전달합니다.</li>
<li>SSR(Server Side Rendering)과는 다른 개념입니다. SSR은 HTML을 서버에서 만드는 것이고, 서버 컴포넌트는 컴포넌트 자체를 서버에서 실행하는 것입니다. 둘은 함께 사용됩니다.</li>
</ul>
</blockquote>
<p>React Server Components(이하 RSC)는 2020년 말 처음 소개되어 React 18 시기에 실험 기능으로 다듬어지고, React 19에서 정식 기능이 된 컴포넌트 모델입니다. 지금까지의 React 컴포넌트는 모두 브라우저에서 실행된다는 전제가 있었습니다. 서버에서 HTML을 미리 만드는 SSR을 사용하더라도, 컴포넌트 코드는 결국 브라우저로 전달되어 다시 한번 실행(하이드레이션)되어야 했습니다. RSC는 이 전제를 깨고 <strong>서버에서만 실행되고 브라우저로는 전달되지 않는 컴포넌트</strong>를 만들 수 있게 해 줍니다.</p>
<p>이번 포스트에서는 서버 컴포넌트가 무엇을 해결하려는 것인지, 서버 컴포넌트와 클라이언트 컴포넌트를 어떻게 나누는지, 그리고 내부적으로 어떤 원리로 동작하는지 살펴보도록 하겠습니다.</p>
<h2 id="서버-컴포넌트가-해결하려는-문제">서버 컴포넌트가 해결하려는 문제<a class="anchor after" aria-hidden="true" tabindex="-1" href="#서버-컴포넌트가-해결하려는-문제"><span class="anchor-icon">#</span></a></h2>
<p>RSC는 크게 세 가지 문제를 해결하기 위해 등장했습니다.</p>
<h3 id="번들-크기">번들 크기<a class="anchor after" aria-hidden="true" tabindex="-1" href="#번들-크기"><span class="anchor-icon">#</span></a></h3>

<p>이 컴포넌트는 사용자와 상호작용하지 않습니다. 마크다운을 HTML로 바꿔 보여주기만 합니다. 그럼에도 <code>marked</code>와 <code>sanitize-html</code> 라이브러리가 브라우저로 전달되어야 합니다. 서버 컴포넌트로 만들면 이 라이브러리는 서버에서만 실행되고, 브라우저로는 변환이 끝난 HTML만 전달됩니다. 번들에서 두 라이브러리가 완전히 사라집니다.</p>
<h3 id="데이터-접근">데이터 접근<a class="anchor after" aria-hidden="true" tabindex="-1" href="#데이터-접근"><span class="anchor-icon">#</span></a></h3>
<p>클라이언트 컴포넌트에서 데이터를 가져오려면 API 서버를 거쳐야 합니다. 컴포넌트가 마운트된 후 <code>useEffect</code>나 TanStack Query 같은 라이브러리로 요청을 보내고, 응답을 기다렸다가 화면을 그립니다. 부모 컴포넌트가 데이터를 받은 뒤에야 자식 컴포넌트의 요청이 시작되는 Waterfall 문제도 자주 겪게 됩니다.</p>
<p>API 서버를 거치는 이유는 브라우저가 데이터베이스나 파일 시스템에 직접 접근할 수 없기 때문입니다. 서버 컴포넌트는 서버에서 실행되므로 이 중간 단계가 필요 없습니다. 컴포넌트 안에서 데이터베이스에 바로 쿼리를 보내고, 파일을 읽고, 내부 네트워크의 API를 호출할 수 있습니다. 브라우저와 서버 사이의 왕복(Round Trip)이 사라집니다. Waterfall이 생기더라도 서버 안에서 일어나는 일이라 네트워크 지연이 거의 없고, 비용도 훨씬 작습니다.</p>

</ol>

<p>위 코드처럼 <code>Note</code>가 서버 컴포넌트이고 <code>PhotoEditor</code>와 <code>VideoEditor</code>가 클라이언트 컴포넌트라면, 서버 컴포넌트가 <code>lazy</code>의 이 두 가지 역할을 대신합니다.</p>
<ol>
<li>서버 컴포넌트에게 클라이언트 컴포넌트는 지금 실행할 코드가 아니라 브라우저가 나중에 불러올 모듈입니다. 그래서 번들러는 서버 컴포넌트가 import 하는 클라이언트 컴포넌트를 각각 별도 파일로 나눌 수 있습니다.</li>
<li>무엇을 렌더링할지는 서버 컴포넌트가 결정하고, RSC Payload에는 선택된 컴포넌트의 참조만 담깁니다. 브라우저는 그 컴포넌트의 파일만 요청합니다.</li>
</ol>
<p>개발자가 <code>lazy</code>로 분리할 컴포넌트를 일일이 고르지 않아도 되므로 자동 코드 분할이라고 부릅니다.</p>
<blockquote>
<p><strong>Next.js와 <code>next/dynamic</code></strong></p>
<p>React가 제공하는 번들러 플러그인(<code>react-server-dom-webpack</code> 등)은 클라이언트 컴포넌트마다 파일을 나눕니다. 하지만 Next.js는 라우트 단위로 묶기 때문에, 같은 라우트에 있는 <code>PhotoEditor</code>와 <code>VideoEditor</code>는 보통 한 파일로 묶입니다. 그러면 사진 노트를 열어도 <code>VideoEditor</code>의 코드가 함께 내려옵니다. Next.js에서 확실히 나누려면 <code>next/dynamic</code>(Next.js가 제공하는 <code>React.lazy</code>)으로 분리할 컴포넌트를 직접 지정해야 합니다.</p>
</blockquote>
<h2 id="서버-컴포넌트와-클라이언트-컴포넌트">서버 컴포넌트와 클라이언트 컴포넌트<a class="anchor after" aria-hidden="true" tabindex="-1" href="#서버-컴포넌트와-클라이언트-컴포넌트"><span class="anchor-icon">#</span></a></h2>
<p>RSC 모델에서 컴포넌트는 서버 컴포넌트와 클라이언트 컴포넌트 둘 중 하나입니다. 두 컴포넌트를 구분하는 방법과 각각의 제약을 살펴보겠습니다.</p>
<h3 id="구분하는-방법">구분하는 방법<a class="anchor after" aria-hidden="true" tabindex="-1" href="#구분하는-방법"><span class="anchor-icon">#</span></a></h3>
<p>Next.js App Router 같은 RSC를 지원하는 프레임워크에서는 <strong>모든 컴포넌트가 기본적으로 서버 컴포넌트</strong>입니다. 클라이언트 컴포넌트로 만들고 싶은 파일의 최상단에 <code>'use client'</code> 지시어를 선언합니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="tsx"><code><span class="line"><span style="color:#032563;--shiki-dark:#ADDCFF">'use client'</span></span>

<p><code>'use client'</code>는 "이 파일부터는 클라이언트 영역"이라는 경계(Boundary)를 표시하는 지시어입니다. 이 파일이 import 하는 모든 모듈도 클라이언트 번들에 포함됩니다. 모든 클라이언트 컴포넌트 파일마다 <code>'use client'</code>를 선언할 필요는 없고, 서버 컴포넌트에서 클라이언트 컴포넌트로 넘어가는 경계가 되는 파일에만 선언하면 됩니다.</p>
<h3 id="서버-컴포넌트의-제약">서버 컴포넌트의 제약<a class="anchor after" aria-hidden="true" tabindex="-1" href="#서버-컴포넌트의-제약"><span class="anchor-icon">#</span></a></h3>
<p>서버 컴포넌트는 서버에서 한 번 실행되고 끝나기 때문에, 브라우저에서 계속 살아 있어야 하는 기능은 사용할 수 없습니다.</p>
<ul>
<li><code>useState</code>, <code>useReducer</code>, <code>useEffect</code> 같이 상태와 생명주기에 관련된 훅을 사용할 수 없습니다.</li>
<li><code>onClick</code>, <code>onChange</code> 같은 이벤트 핸들러를 사용할 수 없습니다. 이벤트 핸들러는 함수인데, 함수는 서버의 변수를 참조하고 있어 문자열로 바꿔 브라우저로 보낼 수 없기 때문입니다.</li>
<li><code>window</code>, <code>document</code> 같은 브라우저 API를 사용할 수 없습니다.</li>
<li>클라이언트 컴포넌트에 전달하는 props는 직렬화 가능해야 합니다. 문자열, 숫자, 배열, 객체, <code>Date</code>, <code>Promise</code>, JSX 등은 전달할 수 있지만 함수는 전달할 수 없습니다. 클래스 인스턴스는 에러가 나지는 않지만 메서드와 프로토타입이 사라진 일반 객체로 넘어가고, 개발 모드에서 경고가 출력됩니다.</li>
</ul>
<blockquote>
<p><strong>직렬화(Serialization)</strong></p>
<p>메모리에 있는 값을 네트워크로 보낼 수 있는 문자열로 바꾸는 것입니다. <code>JSON.stringify</code>가 대표적인 예입니다. 서버 컴포넌트의 렌더링 결과는 RSC Payload라는 문자열로 바뀌어 브라우저로 전달되는데, 클라이언트 컴포넌트에 넘긴 props도 이 문자열 안에 함께 담겨야 합니다. 문자열, 숫자, 배열, 객체는 그대로 문자열로 표현할 수 있지만, 함수는 코드가 참조하는 서버의 변수까지 한 묶음이라 문자열 하나로 옮길 수 없습니다. <code>JSON.stringify({ onClick: () => {} })</code>의 결과가 <code>{}</code>인 것과 같은 이유입니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="tsx"><code><span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">const</span><span style="color:#622CBC;--shiki-dark:#DBB7FF"> Page</span><span style="color:#A0111F;--shiki-dark:#FF9492"> =</span><span style="color:#A0111F;--shiki-dark:#FF9492"> async</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> () </span><span style="color:#A0111F;--shiki-dark:#FF9492">=></span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> {</span></span>

<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">}</span></span></code></pre>
</blockquote>
<p>대신 서버 컴포넌트에서만 할 수 있는 것들이 있습니다.</p>
<ul>
<li><code>async</code> 함수로 선언하고 <code>await</code>를 사용할 수 있습니다.</li>
<li>데이터베이스나 파일 시스템에 직접 접근할 수 있고, API 키 같은 비밀 환경 변수도 사용할 수 있습니다. 이 코드는 브라우저로 전달되지 않기 때문에 비밀 값이 노출되지 않습니다.</li>
<li>무거운 라이브러리를 번들 크기 걱정 없이 사용할 수 있습니다.</li>
</ul>
<h3 id="클라이언트-컴포넌트의-제약">클라이언트 컴포넌트의 제약<a class="anchor after" aria-hidden="true" tabindex="-1" href="#클라이언트-컴포넌트의-제약"><span class="anchor-icon">#</span></a></h3>
<p>클라이언트 컴포넌트는 기존 React 컴포넌트와 같습니다. 다만 한 가지 규칙이 추가됩니다. <strong>클라이언트 컴포넌트가 import 한 컴포넌트는 모두 클라이언트 컴포넌트가 됩니다.</strong> <code>'use client'</code> 파일이 import 하는 모듈은 전부 클라이언트 번들에 들어가기 때문입니다. 아래 코드처럼 클라이언트 컴포넌트에서 서버 컴포넌트를 import 하면 에러 없이 그냥 클라이언트 컴포넌트가 되어 버리고, 서버 컴포넌트의 의미가 사라집니다. <code>async</code> 함수였거나, 서버에서만 쓰겠다고 표시해 둔 모듈(뒤에서 설명할 <code>server-only</code>)을 사용했다면 그때는 에러가 발생합니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="tsx"><code><span class="line"><span style="color:#032563;--shiki-dark:#ADDCFF">'use client'</span></span>

<span class="line"></span>

<span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">  return</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> &#x3C;</span><span style="color:#024C1A;--shiki-dark:#72F088">ServerComponent</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> /></span></span>
<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">}</span></span></code></pre>
<p>클라이언트 컴포넌트 안에 서버 컴포넌트를 두고 싶다면 import 대신 <strong>props로 전달</strong>합니다. 서버 컴포넌트가 렌더링한 결과는 직렬화 가능한 JSX이기 때문에 <code>children</code>을 비롯한 어떤 prop으로든 전달할 수 있습니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="tsx"><code><span class="line"><span style="color:#66707B;--shiki-dark:#BDC4CC">// ClientComponent.tsx</span></span>

<span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">const</span><span style="color:#622CBC;--shiki-dark:#DBB7FF"> Page</span><span style="color:#A0111F;--shiki-dark:#FF9492"> =</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> () </span><span style="color:#A0111F;--shiki-dark:#FF9492">=></span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> {</span></span>

<p>이 패턴은 "클라이언트 컴포넌트에 구멍(Slot)을 뚫는다"고 표현하기도 합니다. 클라이언트 컴포넌트는 <code>children</code>이 무엇인지 알 필요 없이 자리만 내어 주고, 그 자리를 서버 컴포넌트가 채웁니다.</p>
<p><img src="/assets/img/posts/react/rsc_slot_pattern.svg" alt="import 와 children 의 차이" loading="lazy" decoding="async" width="960" height="420"></p>
<p>두 종류의 컴포넌트가 서로를 어떻게 사용할 수 있는지 정리하면 다음과 같습니다. 서버 컴포넌트는 서버 컴포넌트든 클라이언트 컴포넌트든 자유롭게 사용할 수 있습니다. 제약은 클라이언트 컴포넌트에서 서버 컴포넌트를 사용할 때만 있습니다.</p>

<h3 id="어떤-컴포넌트를-클라이언트-컴포넌트로-만들어야-할까">어떤 컴포넌트를 클라이언트 컴포넌트로 만들어야 할까<a class="anchor after" aria-hidden="true" tabindex="-1" href="#어떤-컴포넌트를-클라이언트-컴포넌트로-만들어야-할까"><span class="anchor-icon">#</span></a></h3>
<p>"상호작용이 필요한 가장 작은 단위"만 클라이언트 컴포넌트로 만드는 것이 원칙입니다. 페이지 전체에 <code>'use client'</code>를 선언하면 RSC의 이점을 전부 잃어버립니다. 예를 들어 상품 상세 페이지에서 상품 정보, 설명, 리뷰 목록은 서버 컴포넌트로 두고, 수량을 고르는 셀렉트 박스와 장바구니 버튼만 클라이언트 컴포넌트로 분리합니다.</p>
<p>아래 기준에 하나라도 해당하면 클라이언트 컴포넌트입니다.</p>
<ul>
<li>상태(<code>useState</code>)나 이펙트(<code>useEffect</code>)를 사용합니다.</li>
<li>이벤트 핸들러를 사용합니다.</li>
<li>브라우저 API를 사용합니다.</li>
<li>클라이언트 전용 라이브러리(상태 관리, 애니메이션 등)를 사용합니다.</li>
</ul>
<h2 id="동작-원리">동작 원리<a class="anchor after" aria-hidden="true" tabindex="-1" href="#동작-원리"><span class="anchor-icon">#</span></a></h2>
<p>서버 컴포넌트가 어떻게 브라우저에 도달하는지 알면 제약이 왜 생기는지 이해할 수 있습니다.</p>
<h3 id="rsc-payload">RSC Payload<a class="anchor after" aria-hidden="true" tabindex="-1" href="#rsc-payload"><span class="anchor-icon">#</span></a></h3>
<p>서버 컴포넌트는 서버에서 실행되어 <strong>RSC Payload</strong>라는 형식으로 직렬화됩니다. 내부적으로 Flight라고 부르는 이 형식은 HTML이 아니라, React 엘리먼트 트리를 한 줄씩 기록한 텍스트입니다. 아래 서버 컴포넌트가 어떤 RSC Payload로 바뀌는지 따라가 보겠습니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="tsx"><code><span class="line"><span style="color:#66707B;--shiki-dark:#BDC4CC">// Page.tsx (서버 컴포넌트)</span></span>
<span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">import</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> Counter </span><span style="color:#A0111F;--shiki-dark:#FF9492">from</span><span style="color:#032563;--shiki-dark:#ADDCFF"> './Counter'</span><span style="color:#66707B;--shiki-dark:#BDC4CC"> // 'use client'</span></span>
<span class="line"></span>
<span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">const</span><span style="color:#622CBC;--shiki-dark:#DBB7FF"> Page</span><span style="color:#A0111F;--shiki-dark:#FF9492"> =</span><span style="color:#A0111F;--shiki-dark:#FF9492"> async</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> () </span><span style="color:#A0111F;--shiki-dark:#FF9492">=></span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> {</span></span>
<span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">  const</span><span style="color:#023B95;--shiki-dark:#91CBFF"> note</span><span style="color:#A0111F;--shiki-dark:#FF9492"> =</span><span style="color:#A0111F;--shiki-dark:#FF9492"> await</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> db.notes.</span><span style="color:#622CBC;--shiki-dark:#DBB7FF">get</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">(</span><span style="color:#023B95;--shiki-dark:#91CBFF">1</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">)</span></span>
<span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">  return</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> (</span></span>
<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">    &#x3C;</span><span style="color:#024C1A;--shiki-dark:#72F088">article</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">></span></span>
<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">      &#x3C;</span><span style="color:#024C1A;--shiki-dark:#72F088">h1</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">></span><span style="color:#A0111F;--shiki-dark:#FF9492">{</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">note.title</span><span style="color:#A0111F;--shiki-dark:#FF9492">}</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">&#x3C;/</span><span style="color:#024C1A;--shiki-dark:#72F088">h1</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">></span></span>
<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">      &#x3C;</span><span style="color:#024C1A;--shiki-dark:#72F088">Counter</span><span style="color:#023B95;--shiki-dark:#91CBFF"> initialCount</span><span style="color:#A0111F;--shiki-dark:#FF9492">={</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">note.likes</span><span style="color:#A0111F;--shiki-dark:#FF9492">}</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> /></span></span>
<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">    &#x3C;/</span><span style="color:#024C1A;--shiki-dark:#72F088">article</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">></span></span>
<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">  )</span></span>
<span class="line"><span style="color:#0E1116;--shiki-dark:#F0F3F6">}</span></span></code></pre>
<p><code>note.title</code>이 <code>"Hello"</code>, <code>note.likes</code>가 <code>3</code>이라고 하면 서버는 아래와 같은 RSC Payload를 만듭니다. 실제 출력은 더 길지만 구조를 보기 위해 단순화했습니다.</p>
<pre><code>0:["$","article",null,{"children":[["$","h1",null,{"children":"Hello"}],["$","$L1",null,{"initialCount":3}]]}]
1:I["./Counter.js",["chunk.js"],"default"]
</code></pre>
<p><img src="/assets/img/posts/react/rsc_payload_mapping.svg" alt="서버 컴포넌트 트리가 RSC Payload로 바뀌는 모습" loading="lazy" decoding="async" width="960" height="410"></p>
<p>한 줄이 하나의 항목이고, 각 항목은 <code>번호:내용</code> 형태입니다. 엘리먼트는 <code>["$", 타입, key, props]</code> 배열로 기록됩니다. <code>$</code>는 "이것은 React 엘리먼트다"라는 표시이고, 그 뒤로 <code>React.createElement(타입, props)</code>의 인자가 순서대로 옵니다.</p>
<ul>
<li><code>0:</code>으로 시작하는 줄은 <code>Page</code>가 반환한 엘리먼트 트리입니다. <code>"article"</code>, <code>"h1"</code> 처럼 일반 HTML 엘리먼트는 태그 이름이 그대로 기록되고, 그 props(<code>children</code>)도 그대로 기록됩니다. <code>h1</code>의 <code>children</code>이 <code>"Hello"</code>인 것은 서버에서 <code>note.title</code>을 이미 읽어 값으로 바꿔 넣었기 때문입니다. 데이터베이스에서 읽는 코드는 남지 않고 결과만 남습니다.</li>
<li><code>"$L1"</code>은 클라이언트 컴포넌트 <code>Counter</code>의 자리입니다. <code>Counter</code>는 RSC Payload를 만드는 단계에서는 실행되지 않으므로 렌더링 결과 대신 "1번 항목에 정의된 컴포넌트가 여기 온다"는 참조로 기록됩니다.
<ul>
<li><code>$</code>: 이 문자열은 값이 아니라 참조라는 표시입니다.</li>
<li><code>L</code>: 필요할 때 지연(Lazy)해서 해석하라는 참조 종류입니다.</li>
<li><code>1</code>: 가리키는 항목 번호입니다.</li>
</ul>
</li>
<li><code>{"initialCount":3}</code>은 <strong>서버 컴포넌트가 <code>Counter</code>에 넘긴 props</strong>입니다. <code>&#x3C;Counter initialCount={note.likes} /></code>에서 <code>note.likes</code>가 서버에서 <code>3</code>으로 계산되어 값으로 기록된 것입니다. 브라우저의 <code>Counter</code>는 이 값을 props로 받아 렌더링됩니다.</li>
<li><code>1:I[...]</code>는 <code>$L1</code>이 가리키는 클라이언트 컴포넌트가 어느 파일(<code>./Counter.js</code>)의 어느 export(<code>default</code>)이고, 그 코드를 받으려면 어떤 청크(<code>chunk.js</code>)를 내려받아야 하는지를 기록한 모듈 참조입니다.</li>
</ul>
<p><code>$</code> 뒤의 글자에 따라 참조 종류가 다릅니다. 항목 종류와 참조 형식은 <a href="#%EB%B6%80%EB%A1%9D-rsc-payload-%ED%98%95%EC%8B%9D">부록</a>에 정리했습니다.</p>
<p>props가 RSC Payload에 값으로 기록된다는 점이 중요합니다. 서버 컴포넌트에서 클라이언트 컴포넌트로 넘기는 props는 이렇게 텍스트에 담겨 브라우저로 가기 때문에, 앞서 본 것처럼 함수나 클래스 인스턴스는 넘길 수 없고 문자열·숫자·객체처럼 직렬화 가능한 값만 넘길 수 있습니다.</p>
<p>HTML 대신 이 형식을 사용하는 이유는 <strong>React 트리 구조를 유지하기 위해서</strong>입니다. HTML로 받으면 브라우저는 그것이 어떤 컴포넌트였는지 알 수 없습니다. RSC Payload는 React가 그대로 읽어 가상 DOM 트리로 복원할 수 있고, 클라이언트 컴포넌트의 상태를 유지한 채 서버 컴포넌트 부분만 갈아 끼울 수 있습니다.</p>
<h3 id="클라이언트에서의-처리">클라이언트에서의 처리<a class="anchor after" aria-hidden="true" tabindex="-1" href="#클라이언트에서의-처리"><span class="anchor-icon">#</span></a></h3>
<p>서버에서 <code>Page</code>가 반환한 엘리먼트 트리는 텍스트(RSC Payload)로 바뀌어 브라우저로 전달됩니다. 브라우저의 React는 이 텍스트를 한 줄씩 읽어 서버에 있던 것과 같은 모양의 엘리먼트 트리(이하 복원된 트리)를 다시 만듭니다. 이때 복원된 트리는 메모리에만 들고 있고, 아직 화면에 그려지진 않습니다.</p>
<p>복원 과정에서 <code>"article"</code>, <code>"h1"</code> 같은 일반 엘리먼트는 그대로 트리에 넣습니다. 클라이언트 컴포넌트 참조(<code>$L1</code>)를 만나면 <code>1:I[...]</code>에 적힌 청크를 내려받아 실제 <code>Counter</code> 컴포넌트로 바꾸고, RSC Payload에 기록된 props(<code>{ initialCount: 3 }</code>)를 넘깁니다. 서버 컴포넌트가 렌더링한 부분은 JavaScript 실행 없이 트리에 그대로 들어가고, 클라이언트 컴포넌트만 브라우저에서 실행됩니다.</p>
<p>마지막으로 React는 복원된 트리를 화면에 반영합니다. 이 단계는 첫 요청인지 페이지 이동인지에 따라 다르게 진행됩니다.</p>
<ul>
<li><strong>첫 요청</strong>: SSR로 만든 HTML이 이미 화면에 그려져 있으므로, 복원된 트리를 그 HTML에 연결합니다. 연결이 끝나면 클릭 같은 상호작용에 반응할 수 있게 됩니다. 이 과정이 하이드레이션입니다.</li>
<li><strong>페이지 이동</strong>: HTML 없이 RSC Payload만 오므로, 복원된 트리를 지금 화면의 트리와 비교해 달라진 부분의 DOM만 새로 만들거나 고칩니다. 바뀌지 않은 클라이언트 컴포넌트는 건드리지 않으므로 입력 중이던 값이나 열어 둔 메뉴 같은 상태가 그대로 남습니다. RSC Payload는 화면 전체가 아니라 바뀌는 부분만 받습니다. 두 페이지가 공유하는 레이아웃은 다시 받지 않습니다.</li>
</ul>
<h3 id="streaming과-suspense">Streaming과 Suspense<a class="anchor after" aria-hidden="true" tabindex="-1" href="#streaming과-suspense"><span class="anchor-icon">#</span></a></h3>
<p>서버 컴포넌트는 <a href="/tech/react/suspense/">Suspense</a>와 함께 동작합니다. <code>async</code> 서버 컴포넌트가 데이터를 기다리는 동안 상위의 <code>Suspense</code>가 <code>fallback</code>을 먼저 보내고, 데이터가 준비되면 그 부분의 RSC Payload를 이어서 보냅니다.</p>

<p>이때 브라우저가 요청을 두 번 보내는 것은 아닙니다. 요청도 응답도 하나인데, 서버가 응답 본문을 다 만든 뒤 한꺼번에 보내는 대신 준비된 줄부터 먼저 보내고 연결을 열어 둔 채 나머지를 이어서 보냅니다. 그래서 브라우저가 받은 응답 본문은 시간에 따라 이렇게 자라납니다.</p>

<p>처음 도착한 0번 줄에서 <code>header</code>는 기다릴 것이 없어 바로 렌더링 결과가 들어 있고, <code>Comments</code> 자리에는 결과 대신 <code>"$L2"</code> 참조만 있습니다. 2번 줄은 아직 없으므로 가장 가까운 <code>Suspense</code>가 <code>fallback</code>을 그려 스켈레톤이 보입니다. 서버에서 <code>await</code>가 끝나면 같은 응답에 2번 줄이 덧붙고, React는 이 줄을 받는 순간 <code>$L2</code>를 그 트리로 채워 스켈레톤을 댓글로 바꿉니다. 페이지를 다시 요청하거나 전체를 다시 그리는 것이 아니라 비워 뒀던 자리만 채웁니다.</p>
<p><img src="/assets/img/posts/react/rsc_streaming_timeline.svg" alt="스트리밍 타임라인" loading="lazy" decoding="async" width="960" height="450"></p>
<p>RSC Payload가 한 줄씩 기록되는 텍스트 형식인 이유가 여기에 있습니다. 한 덩어리 JSON이었다면 응답이 끝나야 파싱할 수 있지만, 한 줄이 하나의 완결된 항목이라 도착한 줄부터 읽을 수 있습니다. 각 줄이 번호로 자기 자리를 알고 있어서 <code>Suspense</code>가 여러 개일 때 데이터가 준비되는 순서대로 번호와 무관하게 도착해도 문제없습니다.</p>
<p>첫 요청(SSR)에서는 HTML도 같은 방식으로 스트리밍됩니다. 스켈레톤이 들어간 HTML을 먼저 보내고, 나중에 실제 내용과 그것을 스켈레톤 자리로 옮기는 작은 <code>&#x3C;script></code>를 이어서 보냅니다.</p>
<p>스트리밍은 동적 렌더링에서 일어납니다. 동적 렌더링에서는 <code>await</code>를 기다리는 시간이 요청 처리 중에 생기므로 그 시간을 스트리밍으로 메우지만, 정적 렌더링에서는 <code>await</code>가 빌드 중에 이미 끝나 있습니다. 요청이 오면 완성된 RSC Payload 파일을 그대로 보내므로 기다릴 것이 없고, 한 번에 다 도착합니다.</p>
<blockquote>
<p><strong>동적 렌더링과 정적 렌더링</strong></p>
<p>서버 컴포넌트를 언제 실행하느냐에 따른 구분입니다. 동적 렌더링(Dynamic Rendering)은 사용자 요청이 올 때마다 서버 컴포넌트를 실행해 그 결과를 응답합니다. 로그인한 사용자마다 내용이 다른 페이지처럼 요청 시점의 정보가 필요할 때 사용합니다. 정적 렌더링(Static Rendering)은 빌드 시점에 서버 컴포넌트를 한 번 실행해 결과(HTML과 RSC Payload)를 파일로 저장해 두고, 요청이 오면 그 파일을 그대로 응답합니다. 블로그 포스트처럼 누가 보든 같은 페이지에 사용합니다. Next.js는 요청 시점의 정보(쿠키, 헤더, 검색 파라미터 등)를 사용하지 않는 페이지를 기본적으로 정적 렌더링합니다.</p>
</blockquote>
<h2 id="ssr과의-차이">SSR과의 차이<a class="anchor after" aria-hidden="true" tabindex="-1" href="#ssr과의-차이"><span class="anchor-icon">#</span></a></h2>
<p>RSC를 처음 접하면 SSR과 혼동하기 쉽습니다. 둘은 다른 문제를 해결하는 다른 기술이고, 함께 사용됩니다.</p>

<p>Next.js App Router에서 첫 요청을 처리하는 과정을 보면 둘이 어떻게 함께 쓰이는지 알 수 있습니다.</p>
<ol>
<li>서버 컴포넌트를 실행해 RSC Payload를 만듭니다.</li>
<li>RSC Payload와 클라이언트 컴포넌트를 사용해 HTML을 만듭니다. (SSR)</li>
<li>HTML과 RSC Payload를 함께 브라우저로 보냅니다. 별도 요청이 아니라 HTML 응답 안에 RSC Payload가 <code>&#x3C;script></code> 태그로 실려 갑니다. HTML은 JavaScript 실행 전에 화면을 바로 그리기 위한 것이고, RSC Payload는 React가 그 HTML이 어떤 트리였는지 알고 하이드레이션하기 위한 것입니다.</li>
<li>브라우저는 HTML을 먼저 그리고, RSC Payload로 React 트리를 복원한 뒤 클라이언트 컴포넌트만 하이드레이션합니다.</li>
</ol>

<p>SSR 없이 RSC만 사용할 수도 있습니다. 이 경우 브라우저는 빈 HTML과 RSC Payload를 받아 클라이언트에서 트리를 그립니다. 서버 컴포넌트의 번들 절감 효과는 그대로 얻을 수 있지만 첫 화면 표시는 느려집니다.</p>
<h2 id="server-actions">Server Actions<a class="anchor after" aria-hidden="true" tabindex="-1" href="#server-actions"><span class="anchor-icon">#</span></a></h2>

<p><code>'use client'</code>가 "이 파일은 클라이언트 영역"을 뜻하는 것과 달리, <code>'use server'</code>는 "이 함수는 서버에서 실행된다"를 뜻합니다. 서버 컴포넌트 파일에 <code>'use server'</code>를 선언하는 것이 아니라는 점에 주의해야 합니다. 서버 컴포넌트는 지시어 없이 기본값이고, <code>'use server'</code>는 클라이언트에서 호출할 수 있는 서버 함수를 만드는 지시어입니다.</p>
<p>클라이언트 컴포넌트가 <code>addNote</code>를 import 하지만, 브라우저로 가는 번들에 <code>addNote</code>의 코드가 들어가지는 않습니다. 빌드할 때 번들러가 <code>'use server'</code> 파일에서 export 한 함수마다 고유한 ID를 붙입니다. 그리고 클라이언트 번들에는 원래 함수 대신, 서버에 "이 ID의 함수를 실행해 달라"고 요청을 보내는 가짜 함수를 넣습니다. 데이터베이스에 접근하는 진짜 코드는 서버에만 있습니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="ts"><code><span class="line"><span style="color:#66707B;--shiki-dark:#BDC4CC">// 클라이언트 번들에 실제로 들어가는 코드 (개념 코드)</span></span>
<span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">export</span><span style="color:#A0111F;--shiki-dark:#FF9492"> const</span><span style="color:#023B95;--shiki-dark:#91CBFF"> addNote</span><span style="color:#A0111F;--shiki-dark:#FF9492"> =</span><span style="color:#622CBC;--shiki-dark:#DBB7FF"> createServerReference</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">(</span><span style="color:#032563;--shiki-dark:#ADDCFF">'a1b2c3...'</span><span style="color:#0E1116;--shiki-dark:#F0F3F6">)</span></span>
<span class="line"><span style="color:#66707B;--shiki-dark:#BDC4CC">// 호출하면 → fetch(현재 URL, { method: 'POST', headers: { 'Next-Action': 'a1b2c3...' }, body: 직렬화된 인자 })</span></span></code></pre>
<p>클라이언트에서 <code>addNote(formData)</code>를 호출하면 이 가짜 함수가 서버로 POST 요청을 보냅니다. 서버는 요청에 담긴 ID로 실제 <code>addNote</code>를 찾아 실행하고, 반환값을 직렬화해 응답합니다. <code>revalidatePath</code>를 호출했다면 갱신된 RSC Payload도 같은 응답에 함께 내려와 화면이 갱신됩니다. 인자와 반환값은 RSC Payload와 같은 규칙으로 직렬화되므로 직렬화할 수 있는 값이어야 합니다. 앞서 함수는 직렬화할 수 없다고 했는데, Server Function만 예외인 이유가 이것입니다. 함수 본문 대신 ID 하나만 직렬화하면 되기 때문입니다. <a href="#%EB%B6%80%EB%A1%9D-rsc-payload-%ED%98%95%EC%8B%9D">부록</a>의 <code>$F</code> 참조가 그 자리입니다.</p>
<p>이 때문에 <code>'use server'</code> 파일에는 몇 가지 제약이 있습니다.</p>
<ul>
<li>export 할 수 있는 것은 <code>async</code> 함수뿐입니다. 클라이언트에서 호출하면 항상 네트워크를 타기 때문입니다. 상수나 동기 함수를 export 하면 빌드 에러가 납니다.</li>
<li>export 한 함수는 모두 클라이언트에서 호출할 수 있는 엔드포인트가 됩니다. ID만 알면 누구나 요청을 보낼 수 있으므로, 함수 안에서 인증과 권한 검사를 직접 해야 합니다. 내부에서만 쓰는 헬퍼는 export 하지 않아야 합니다.</li>
</ul>
<p>이런 제약이 있지만 장점이 분명합니다. 데이터를 추가하거나 수정, 삭제할 때마다 API 엔드포인트를 만들고 <code>fetch</code>로 요청을 보내던 코드가 함수 호출 하나로 줄어듭니다. 데이터를 읽는 일은 서버 컴포넌트가 직접 하면 되므로, Server Actions는 데이터를 쓰는 쪽을 담당합니다.</p>
<h2 id="주의할-점">주의할 점<a class="anchor after" aria-hidden="true" tabindex="-1" href="#주의할-점"><span class="anchor-icon">#</span></a></h2>
<p>RSC를 실제 프로젝트에 적용하면서 자주 겪는 문제들입니다.</p>
<h3 id="서버-전용-코드의-유출">서버 전용 코드의 유출<a class="anchor after" aria-hidden="true" tabindex="-1" href="#서버-전용-코드의-유출"><span class="anchor-icon">#</span></a></h3>
<p>클라이언트 컴포넌트에서 서버 컴포넌트를 import 하면, 그 컴포넌트가 <code>async</code>처럼 클라이언트에서 할 수 없는 일을 하고 있을 때는 에러로 드러납니다. 하지만 서버 컴포넌트가 사용하던 데이터베이스 모듈 같은 일반 모듈은 import 해도 에러 없이 조용히 클라이언트 번들에 들어갑니다. 그러면 데이터베이스 접속 정보 같은 비밀 값이 브라우저로 노출될 수 있습니다. <code>server-only</code> 패키지를 서버 전용 모듈에 import 해 두면, 그 모듈이 클라이언트 번들에 포함될 때 빌드 에러가 발생합니다.</p>

<p>서버 컴포넌트인 <code>Layout</code>과 <code>Header</code>는 쿠키에서 테마를 읽습니다. <code>ThemeProvider</code>는 서버에서 읽은 테마를 <code>initialTheme</code>으로 받아 <code>useState</code>의 초기값으로 씁니다. 사용자가 테마를 바꾸면 클라이언트에서 상태를 바꾸는 동시에 Server Action으로 쿠키도 갱신합니다. <code>next/headers</code>의 <code>cookies()</code>는 서버 전용 API라서 클라이언트 컴포넌트에서는 직접 쓸 수 없기 때문입니다. Server Action이 쿠키를 바꾸면 Next.js는 갱신된 RSC Payload를 응답에 함께 내려보내므로, <code>Header</code>의 로고도 다음 요청을 기다리지 않고 바로 새 테마로 바뀝니다.</p>
<p>정리하면 서버 컴포넌트와 클라이언트 컴포넌트 사이에서 값을 주고받는 방법은 다음과 같습니다. 클라이언트에서 서버로 가는 값은 "지금 당장" 서버 컴포넌트에 전달되는 것이 아니라, 다음 요청에 실려 가서 서버 컴포넌트가 그때 읽는다는 점이 중요합니다.</p>

<h3 id="같은-데이터를-여러-서버-컴포넌트에서-조회할-때">같은 데이터를 여러 서버 컴포넌트에서 조회할 때<a class="anchor after" aria-hidden="true" tabindex="-1" href="#같은-데이터를-여러-서버-컴포넌트에서-조회할-때"><span class="anchor-icon">#</span></a></h3>
<p>앞의 테마 예제에서 <code>getTheme</code>은 <code>Layout</code>과 <code>Header</code>에서 각각 호출되지만, 쿠키를 읽는 비용은 무시할 만합니다. 반면 로그인한 사용자 정보처럼 데이터베이스를 조회해야 하는 값을 여러 서버 컴포넌트가 필요로 한다면, 호출할 때마다 조회가 반복됩니다. 이때는 그 함수를 <code>React.cache</code>로 감쌉니다. 한 요청, 즉 한 화면을 그리는 동안 같은 인자로 여러 번 호출해도 처음 한 번만 실행되고 결과가 재사용됩니다. 요청이 끝나면 캐시도 사라지므로 다음 요청에서는 다시 조회하고, 다른 사용자의 데이터와 섞이지도 않습니다.</p>

<h3 id="서드파티-라이브러리">서드파티 라이브러리<a class="anchor after" aria-hidden="true" tabindex="-1" href="#서드파티-라이브러리"><span class="anchor-icon">#</span></a></h3>
<p><code>'use client'</code>가 없는 서드파티 컴포넌트 라이브러리를 서버 컴포넌트에서 import 하면, 그 라이브러리가 <code>useState</code> 같은 훅을 사용하는 경우 에러가 발생합니다. 라이브러리가 RSC를 지원하기 전까지는 <code>'use client'</code>를 선언한 파일에서 한 번 감싸서 다시 export 해 사용합니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="tsx"><code><span class="line"><span style="color:#032563;--shiki-dark:#ADDCFF">'use client'</span></span>
<span class="line"></span>
<span class="line"><span style="color:#A0111F;--shiki-dark:#FF9492">export</span><span style="color:#0E1116;--shiki-dark:#F0F3F6"> { Carousel } </span><span style="color:#A0111F;--shiki-dark:#FF9492">from</span><span style="color:#032563;--shiki-dark:#ADDCFF"> 'some-carousel-library'</span></span></code></pre>
<h3 id="클라이언트-컴포넌트도-서버에서-실행된다">클라이언트 컴포넌트도 서버에서 실행된다<a class="anchor after" aria-hidden="true" tabindex="-1" href="#클라이언트-컴포넌트도-서버에서-실행된다"><span class="anchor-icon">#</span></a></h3>
<p><code>'use client'</code>를 선언했다고 해서 서버에서 실행되지 않는 것은 아닙니다. SSR 단계에서 클라이언트 컴포넌트도 서버에서 한 번 실행되어 HTML을 만듭니다. <code>'use client'</code>는 "브라우저에서도 실행된다"는 뜻이지 "브라우저에서만 실행된다"는 뜻이 아닙니다. 따라서 클라이언트 컴포넌트에서 <code>window</code>를 렌더링 중에 바로 참조하면 서버에서 에러가 발생합니다. 브라우저 API는 <code>useEffect</code> 안에서 사용해야 합니다.</p>
<h3 id="use-client를-빠뜨리면-언제-에러가-날까"><code>'use client'</code>를 빠뜨리면 언제 에러가 날까<a class="anchor after" aria-hidden="true" tabindex="-1" href="#use-client를-빠뜨리면-언제-에러가-날까"><span class="anchor-icon">#</span></a></h3>
<p><code>useState</code>를 쓰는 컴포넌트를 서버 컴포넌트에서 import 하면서 <code>'use client'</code>를 빠뜨리면 에러가 납니다. 다만 어느 시점에 나는지는 무엇을 잘못했는지와 배포 방식에 따라 다릅니다.</p>

























<table><thead><tr><th align="left">잘못한 것</th><th align="left">정적 렌더링</th><th align="left">동적 렌더링</th></tr></thead><tbody><tr><td align="left"><code>useState</code> 같은 훅 사용</td><td align="left">빌드 에러</td><td align="left">빌드 에러</td></tr><tr><td align="left"><code>onClick</code> 같은 함수 props 전달</td><td align="left">빌드 에러</td><td align="left">요청 시 런타임 에러 (500)</td></tr><tr><td align="left">서드파티 라이브러리 안의 훅 사용</td><td align="left">빌드 에러</td><td align="left">요청 시 런타임 에러 (500)</td></tr></tbody></table>
<p>에러 시점은 "컴파일할 때 알 수 있는가, 렌더링해 봐야 아는가"로 갈립니다.</p>
<ul>
<li><strong>훅 사용</strong>: 컴파일러가 잡습니다. 서버 영역의 파일이 <code>react</code>에서 <code>useState</code>를 import 하는지는 코드를 실행하지 않아도 import 문만으로 알 수 있기 때문에, 배포 방식과 무관하게 빌드 단계에서 에러가 납니다.</li>
<li><strong>함수 props 전달</strong>: import 문만 봐서는 알 수 없습니다. 실제로 렌더링해서 RSC Payload를 만들다가 함수를 직렬화하려는 순간에야 드러나므로, 에러 시점이 렌더링 시점을 따라갑니다. 정적 렌더링은 빌드 중에 페이지를 렌더링하므로 빌드에서 걸리고, 동적 렌더링은 요청이 들어와 그 페이지를 렌더링할 때 납니다.</li>
<li><strong>서드파티 라이브러리 안의 훅 사용</strong>: 컴파일러의 훅 검사는 앱 코드에만 적용되고 <code>node_modules</code>는 검사하지 않습니다. 그래서 서드파티 컴포넌트 안의 훅은 실제로 렌더링해야 드러나고, 에러 시점은 함수 props와 같아집니다.</li>
</ul>
<p>빌드나 런타임에 에러가 난다고 해서 개발 중에 발견하기 어려운 것은 아닙니다. 개발 서버(<code>next dev</code>)는 페이지를 요청하는 순간 그 페이지를 컴파일하고 렌더링하므로, 훅 에러든 함수 props 에러든 브라우저에서 페이지를 여는 즉시 에러 오버레이로 확인할 수 있습니다. 개발 중에 한 번도 열어 보지 않은 페이지에서만 발견이 늦어지는데, 이런 페이지는 CI 빌드와 E2E 테스트로 거를 수 있습니다.</p>
<h3 id="스트리밍과-프록시-버퍼링">스트리밍과 프록시 버퍼링<a class="anchor after" aria-hidden="true" tabindex="-1" href="#스트리밍과-프록시-버퍼링"><span class="anchor-icon">#</span></a></h3>
<p>스트리밍은 서버가 응답을 조각으로 보내야 동작하는데, 서버와 브라우저 사이에 있는 프록시, CDN, 로드 밸런서 중에는 응답을 전부 모았다가 한 번에 전달하는 것들이 있습니다. 이런 버퍼링이 끼어 있으면 서버가 스트리밍해도 브라우저에는 렌더링이 끝난 뒤에 한꺼번에 도착하고, 스켈레톤은 보이지 않은 채 응답 시간만 길어집니다. 코드와 서버 설정이 모두 정상이라 원인을 찾기 어려운 문제입니다.</p>
<p>Vercel이나 Node 서버를 직접 띄우는 경우에는 문제가 없습니다. Nginx 같은 프록시를 앞에 둔다면 해당 경로의 버퍼링을 꺼야 합니다.</p>
<pre class="shiki shiki-themes github-light-high-contrast github-dark-high-contrast" style="background-color:#ffffff;--shiki-dark-bg:#0a0c10;color:#0e1116;--shiki-dark:#f0f3f6" tabindex="0" data-language="text"><code><span class="line"><span>location / {</span></span>
<span class="line"><span>  proxy_pass http://next;</span></span>
<span class="line"><span>  proxy_buffering off;</span></span>
<span class="line"><span>}</span></span></code></pre>
<h3 id="서버-부하">서버 부하<a class="anchor after" aria-hidden="true" tabindex="-1" href="#서버-부하"><span class="anchor-icon">#</span></a></h3>
<p>서버 컴포넌트를 사용하면 서버가 하는 일이 늘어납니다. 이전에는 서버가 데이터만 주고 렌더링은 수많은 브라우저가 나눠서 했는데, 이제 서버 컴포넌트 부분의 렌더링을 서버가 떠안습니다. 요청마다 렌더링하는 동적 페이지라면 서버 CPU 사용량이 늘어납니다.</p>
<p>React와 Next.js는 이 비용을 상쇄하는 장치를 함께 제공합니다.</p>
<ul>
<li><strong>정적 렌더링과 캐시</strong>: 요청마다 내용이 바뀌지 않는 페이지는 빌드 시점이나 첫 요청 때 한 번만 렌더링하고, 결과인 HTML과 RSC Payload를 캐시합니다. 이후 요청에는 캐시를 그대로 응답하므로 렌더링 비용이 들지 않습니다. 모든 페이지가 정적 렌더링이라면 빌드 결과물을 정적 파일로 CDN에 올려 두는 것만으로 서비스할 수 있어, 렌더링하는 서버를 운영할 필요가 없습니다.</li>
<li><strong>API 계층의 부담 감소</strong>: 렌더링 비용이 늘어난 만큼 다른 쪽에서 줄어드는 부분도 있습니다. 브라우저가 API를 여러 번 호출하던 것이 서버 안에서의 함수 호출로 바뀌므로, 요청마다 반복되던 인증 확인과 응답 직렬화가 줄어듭니다. 화면에 필요한 데이터만 꺼내 쓰면 되니 범용 API가 돌려주던 불필요한 데이터도 없어집니다.</li>
<li><strong>부분 갱신</strong>: 페이지 이동이나 갱신 시 바뀐 서버 컴포넌트 부분의 RSC Payload만 만들므로, 전체 페이지를 다시 SSR 하는 것보다 가볍습니다.</li>
</ul>
<p>정리하면 동적 페이지는 서버가 더 일하지만, 대부분의 페이지를 정적 렌더링과 캐시로 돌릴 수 있다면 전체 비용은 오히려 줄어듭니다. 반대로 모든 페이지가 사용자마다 다르고 캐시할 수 없는 서비스라면 서버 비용 증가를 감수해야 합니다. RSC가 모든 서비스에 맞는 선택은 아닌 이유 중 하나입니다.</p>
<h2 id="부록-rsc-payload-형식">부록: RSC Payload 형식<a class="anchor after" aria-hidden="true" tabindex="-1" href="#부록-rsc-payload-형식"><span class="anchor-icon">#</span></a></h2>
<p>RSC Payload 형식은 React 내부 구현이라 버전에 따라 언제든 바뀔 수 있습니다. 구조를 이해하는 용도로만 봐 주세요. Next.js에서는 페이지 요청에 <code>RSC: 1</code> 헤더를 붙이거나, 브라우저 개발자 도구의 네트워크 탭에서 페이지 이동 시 발생하는 <code>?_rsc=...</code> 요청의 응답을 보면 실제 RSC Payload를 확인할 수 있습니다.</p>
<h3 id="항목row">항목(Row)<a class="anchor after" aria-hidden="true" tabindex="-1" href="#항목row"><span class="anchor-icon">#</span></a></h3>
<p>RSC Payload는 줄 단위의 텍스트이고, 한 줄이 하나의 항목입니다. 본문에서 본 두 줄을 다시 보겠습니다.</p>
<pre><code>0:["$","article",null,{"children":[...]}]
1:I["./Counter.js",["chunk.js"],"default"]
</code></pre>
<ul>
<li>줄 맨 앞의 <code>0</code>, <code>1</code>이 항목의 번호입니다. 다른 줄에서 <code>$L1</code>처럼 이 번호로 항목을 가리킵니다. 번호는 16진수라서 실제 RSC Payload에서는 <code>a:</code>, <code>$Lb</code> 같은 줄도 보입니다.</li>
<li>콜론 바로 뒤에 대문자 한 글자가 있으면 그 글자가 항목의 종류를 나타내는 태그입니다. <code>1:I[...]</code>의 <code>I</code>는 import 정보라는 뜻입니다.</li>
<li><code>0:[...]</code>처럼 콜론 뒤에 태그 없이 바로 JSON이 오면, 그 줄은 React 엘리먼트 트리입니다. JSX를 실행한 결과인 중첩된 엘리먼트 객체를 JSON으로 적은 것입니다. 트리 대신 props로 넘긴 숫자나 객체 같은 값이 단독으로 오기도 합니다.</li>
</ul>
<p>자주 보이는 태그는 다음과 같습니다. 이 밖에도 디버그 정보(<code>D</code>)나 바이너리 데이터용 태그가 더 있습니다.</p>



































<table><thead><tr><th align="left">형태</th><th align="left">종류</th><th align="left">설명</th></tr></thead><tbody><tr><td align="left"><code>0:[...]</code></td><td align="left">모델</td><td align="left">JSON으로 기록된 엘리먼트 트리, 또는 props 값입니다. <code>0</code>번이 보통 페이지의 루트입니다.</td></tr><tr><td align="left"><code>1:I[...]</code></td><td align="left">Import</td><td align="left">클라이언트 컴포넌트의 모듈 참조입니다. <code>[모듈 id, [청크 목록], export 이름]</code> 순서로 기록됩니다. 모듈 id는 번들러가 정하며 보통 파일 경로 형태입니다.</td></tr><tr><td align="left"><code>:HL[...]</code></td><td align="left">Hint</td><td align="left">스타일시트나 스크립트를 미리 불러오라는 리소스 힌트입니다. 다른 항목이 참조할 일이 없어 번호가 없고, <code>H</code> 뒤에 힌트 종류 글자가 붙습니다. <code>HL</code>은 preload, <code>HC</code>는 preconnect 입니다.</td></tr><tr><td align="left"><code>3:T...</code></td><td align="left">Text</td><td align="left">긴 문자열입니다. JSON 이스케이프 비용을 줄이기 위해 길이와 함께 따로 기록됩니다.</td></tr><tr><td align="left"><code>4:E{...}</code></td><td align="left">Error</td><td align="left">서버 렌더링 중 발생한 에러입니다. 클라이언트에서 가장 가까운 Error Boundary로 던져집니다.</td></tr></tbody></table>
<p>스트리밍으로 나중에 도착한 항목도 같은 번호 규칙으로 연결됩니다. 먼저 받은 트리에 <code>$L2</code>가 있고 <code>2:</code> 항목이 아직 없다면, 뒤에 <code>2:</code> 줄이 도착하는 순간 그 자리에 채워집니다.</p>
<h3 id="엘리먼트">엘리먼트<a class="anchor after" aria-hidden="true" tabindex="-1" href="#엘리먼트"><span class="anchor-icon">#</span></a></h3>
<p>React 엘리먼트는 <code>["$", 타입, key, props]</code> 배열로 기록됩니다. <code>React.createElement(타입, { key, ...props })</code>의 인자를 순서대로 적은 것입니다.</p>
<pre><code>["$","h1",null,{"children":"Hello"}]
["$","$L1",null,{"initialCount":3}]
["$","$Sreact.suspense",null,{"fallback":[...],"children":"$L2"}]
</code></pre>
<ul>
<li>타입이 문자열이면 <code>"h1"</code> 같은 HTML 엘리먼트입니다.</li>
<li>타입이 <code>$L1</code> 같은 참조이면 클라이언트 컴포넌트입니다. 서버 컴포넌트는 서버에서 실행되어 이미 사라졌으므로 타입으로 등장하지 않습니다.</li>
<li><code>Suspense</code> 같은 React 내장 타입은 심볼이라 <code>$S</code> 참조로 기록됩니다. 다만 <code>key</code>가 없는 <code>Fragment</code>(<code>&#x3C;>...&#x3C;/></code>)는 자식을 묶는 역할뿐이라 엘리먼트로 기록하지 않고, 그 자리에 자식 배열을 바로 적습니다.</li>
<li><code>props</code>의 <code>children</code>에는 문자열, 엘리먼트, 배열이 그대로 중첩됩니다.</li>
</ul>
<h3 id="참조">참조<a class="anchor after" aria-hidden="true" tabindex="-1" href="#참조"><span class="anchor-icon">#</span></a></h3>
<p>RSC Payload 안의 문자열이 <code>$</code>로 시작하면 값이 아니라 참조입니다. <code>$</code> 뒤의 한 글자가 참조의 종류를 결정하고, 그 뒤에 항목 번호나 값이 옵니다.</p>





























































<table><thead><tr><th align="left">형태</th><th align="left">뜻</th></tr></thead><tbody><tr><td align="left"><code>$$...</code></td><td align="left"><code>$</code>로 시작하는 진짜 문자열. <code>$$abc</code>는 문자열 <code>$abc</code>입니다.</td></tr><tr><td align="left"><code>$1</code></td><td align="left">1번 항목을 바로 참조합니다. 같은 값을 여러 곳에서 쓸 때 중복 기록을 피하기 위해 사용됩니다.</td></tr><tr><td align="left"><code>$L1</code></td><td align="left">1번 항목을 지연(Lazy) 참조합니다. 필요할 때 해석하며, 클라이언트 컴포넌트 참조가 대표적입니다.</td></tr><tr><td align="left"><code>$@1</code></td><td align="left">1번 항목을 Promise로 참조합니다. 서버 컴포넌트가 클라이언트 컴포넌트에 Promise를 props로 넘겼을 때 쓰이며, 클라이언트에서는 <code>use()</code>로 읽습니다. 항목이 도착하면 Promise가 resolve 됩니다.</td></tr><tr><td align="left"><code>$F1</code></td><td align="left">1번 항목의 Server Function 참조입니다. <code>'use server'</code> 함수를 props로 넘기면 함수 본문이 아니라 서버의 어떤 함수를 호출할지에 대한 ID만 기록됩니다.</td></tr><tr><td align="left"><code>$S이름</code></td><td align="left"><code>Symbol.for(이름)</code> 심볼입니다. <code>$Sreact.fragment</code>, <code>$Sreact.suspense</code> 처럼 React 내장 타입에 쓰입니다.</td></tr><tr><td align="left"><code>$D...</code></td><td align="left"><code>Date</code> 값입니다. ISO 문자열이 뒤따릅니다.</td></tr><tr><td align="left"><code>$n...</code></td><td align="left"><code>BigInt</code> 값입니다.</td></tr><tr><td align="left"><code>$undefined</code></td><td align="left"><code>undefined</code>입니다. JSON에 없는 값이라 따로 표기합니다.</td></tr><tr><td align="left"><code>$NaN</code>, <code>$Infinity</code>, <code>$-Infinity</code>, <code>$-0</code></td><td align="left">JSON으로 표현할 수 없는 숫자들입니다.</td></tr><tr><td align="left"><code>$Q1</code>, <code>$W1</code></td><td align="left">1번 항목으로 기록된 <code>Map</code>, <code>Set</code>입니다.</td></tr><tr><td align="left"><code>$K1</code>, <code>$B1</code></td><td align="left">1번 항목으로 기록된 <code>FormData</code>, <code>Blob</code>입니다. 주로 Server Function의 인자로 쓰입니다.</td></tr><tr><td align="left"><code>$T1</code></td><td align="left">임시 참조(Temporary Reference)입니다. 클라이언트에서 Server Function에 넘긴 직렬화 불가능한 값을 응답에서 그대로 돌려받기 위한 자리입니다.</td></tr></tbody></table>
<p>이 표는 "서버 컴포넌트에서 클라이언트 컴포넌트로 어떤 props를 넘길 수 있는가"에 대한 정확한 답이기도 합니다. props는 RSC Payload에 글자로 적혀야 하는데, RSC Payload에 적을 수 있는 값은 크게 두 종류입니다. JSON이 원래 표현할 수 있는 문자열, 숫자, 불리언, <code>null</code>, 배열, 일반 객체와, 이 표의 <code>$</code> 참조로 표현되는 값입니다. 그래서 <code>Date</code>, <code>Map</code>, <code>Set</code>, <code>Promise</code>, Server Function은 전용 참조가 있어 넘길 수 있고, 일반 함수는 해당하는 참조가 없어 넘길 수 없습니다. 표에 적지 않은 <code>TypedArray</code>, <code>ReadableStream</code>, <code>AsyncIterable</code>도 전용 항목 형식이 있어 넘길 수 있습니다.</p>
